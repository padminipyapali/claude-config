# Process Patterns

Cross-project learnings about the development process: review efficiency,
planning discipline, iteration velocity, and automation opportunities.

## Metric Definitions

The single "fix-up ratio" (fix commits / total commits) conflated pre-merge catches (good — the review loop working) with post-merge failures (bad — quality escaping all gates). As of 2026-02-28, the metric is split into 4 distinct metrics. See `~/.claude/commands/post-mortem.md` Step 6 for computation details.

1. **Post-merge fix rate.** Commits after merge that fix the same feature. This is the true quality failure rate. 0% is ideal. Any value > 0% means quality escaped all review gates.
2. **Pre-merge catch rate by step.** Which step (4a simplify, 4b internal, 4c CodeRabbit, 4d adversarial, post-push) caught each issue. Tells you where your review pipeline is strong vs. weak.
3. **Pre-merge iteration count.** How many review-fix-review round trips before merge. 1 = healthy, 2 = normal for large PRs, 3+ = high friction or mental model mismatch.
4. **Fix-up taxonomy.** Classify each fix by category (validation, a11y, defensive-coding, correctness, dead-code, test-quality, documentation, style, infrastructure). Recurring categories across PRs indicate systemic gaps.

The legacy `fixupCommitRatio` field is retained in the metrics JSON for backward compatibility with existing dashboard charts. New analysis should use the 4-metric framework.

**Why the old metric was misleading:** A 75% fix-up ratio on a PR where the local review loop caught 3 issues (good!) looked the same as a 75% ratio where all 3 fixes were post-push (bad). The old metric also didn't distinguish infrastructure commits (marker files, gitignore) from substantive code fixes, inflating the ratio on PRs with full step compliance. <!-- Source: command-center #52, 2026-02-28 -->

## Review Efficiency

- **Bot-only review catches real bugs but inflates round count.** CodeRabbit found 4 correctness issues on first review of PR #131, producing 2 review rounds and 75% fix-up ratio. All fixes were mechanical (<20 min total), but the commit noise adds up. Expect 2+ rounds as baseline when only bot reviews. <!-- Source: post-mortem, second-brain #131, 2026-02-16 -->
- **Self-merge with bot-only review misses architectural feedback.** Bot reviewers catch syntax and correctness but can't assess "is this the right abstraction?" or "does this belong in this file?" No human review means architecture debt accumulates silently. <!-- Source: post-mortem, second-brain #131, 2026-02-16 -->
- **Critically evaluate automated reviewer comments before fixing.** CodeRabbit frequently flags non-issues — nitpicks on docs wording, overly conservative null guards on typed fields, style suggestions that don't improve the code. Categorize each finding as **must fix** (real bug, security, correctness), **should fix** (valid improvement), or **disagree** (explain why and skip). Blindly fixing all comments wastes time and can make code worse. <!-- Source: lexica review workflow, 2026-02 -->
- **CodeRabbit "outside diff range" comments are valid and actionable.** Comments marked "outside diff range" flag bugs in existing code related to the PR's changes. Don't dismiss them as out-of-scope — they catch real issues that the PR's changes expose or interact with. <!-- Source: lexica PR #23 review, 2026-02 -->
- **CodeRabbit prompt injection warnings on XML tags are usually false positives.** When code uses XML tags with HTML entity escaping inside Claude API user messages (the recommended Anthropic approach), CodeRabbit flags "potential prompt injection." Safe to disagree when the escaping is already in place. <!-- Source: lexica review, 2026-02 -->

## Session Start Discipline

- **Check for missing CLAUDE.md before any code changes.** A project with code but no CLAUDE.md is an un-initialized project — the `/project-setup` rule applies even if the codebase looks established. The session start protocol checks for repo conflicts and uncommitted changes, but not for missing project infrastructure. When a detailed implementation plan is ready, the temptation is to jump straight to coding. But `/project-setup` must run first: it installs the adversarial review hook, CodeRabbit config, and conventions that the implementation PR depends on. The first feature PR without these guardrails ships without the review infrastructure meant to catch issues. **Structural fix:** Add an explicit check to the session start protocol: "Does this project have a CLAUDE.md? If not, run `/project-setup` before any code changes." <!-- Source: summer-camps project setup skipped before PR #1, 2026-02-26 -->

## Planning Discipline

- **Thorough planning reduces implementation rework.** PR #131 had a detailed plan (entry points, DRY analysis, adversarial review section, performance/cost) and zero redesign commits. All fix commits were review-driven, not planning gaps. The plan paid off. <!-- Source: post-mortem, second-brain #131, 2026-02-16 -->

## Follow-Up Discipline

- **Dedicated follow-up PRs for post-push findings close the loop fastest.** folio PR #2 (3 LOC, 9 min to merge) addressed a specific post-push finding from PR #1 (inline DATE parsing in TrendChart). The fix was scoped to exactly one concern, verified complete via codebase grep, and merged with 0% fix-up ratio. This is the ideal pattern: post-push findings become their own focused PR rather than being deferred to a tracker or bundled into the next feature. The tight feedback loop (PR #1 merged -> PR #2 fixes finding within hours) prevents the finding from going stale. <!-- Source: post-mortem, folio #2, 2026-02-23 -->

- **Multi-finding follow-up PRs work just as well as single-finding ones.** second-brain PR #267 (279 LOC, 6 min to merge) fixed 3 post-mortem findings from PR #260 (XSS, SQL bug, DST edge case) in a single atomic commit. Results: 0% fix-up ratio, 100% shift-left rate (4 pre-push catches, 0 post-push findings), 87.5% step compliance. The full review loop (4a-4d) still caught 4 additional issues even on a "known scope" follow-up. Contrast with the source PR #260: 25% step compliance, 0% shift-left rate, 6 post-push findings. The cost of skipping reviews on #260 was paid back with a dedicated follow-up PR that ran the full process. <!-- Source: post-mortem, second-brain #267, 2026-02-26 -->

- **Post-mortem infrastructure gaps should be addressed in dedicated tooling PRs.** folio PR #1 post-mortem noted "step 4e (lint) skipped because ESLint not configured." PR #3 directly closed that gap with a dedicated ESLint config PR. The turnaround was same-day (PR #1 merged, PR #3 created hours later). This is the ideal pattern for infrastructure debt: post-mortem identifies gap -> dedicated PR fixes it -> future PRs benefit from the tooling. Compare with feature PRs that bundle tooling fixes, which conflate concerns and make review harder. <!-- Source: post-mortem, folio #3, 2026-02-23 -->

## Scope Decisions

- **Deferring trivial interface extractions creates fix commits.** command-center PR #21 deferred `IVelocityService` interface extraction (~3 lines) as "scope creep" during local review. CodeRabbit then flagged it post-push, requiring a fix commit. For extractions under 10 lines that match an established project convention, include them in the original PR. The "scope creep" label should be reserved for behavioral additions, not pattern compliance. <!-- Source: post-mortem, command-center #21, 2026-02-19 -->
- **Bundling tooling setup with feature PRs inflates LOC and review scope.** PR #228 bundled stylelint config + CSS autofix (commit 2, ~1100 LOC of CSS changes) with a performance optimization (commit 1, ~300 LOC). CodeRabbit's pre-merge check flagged "out-of-scope changes." The tooling work inflated LOC from ~500 to ~1600, pushing it past the 600 LOC threshold and generating style-only review findings that wouldn't exist in a focused PR. When adding a new lint tool, create a separate tooling PR for the config + autofix, then reference it from the feature PR. This is the inverse of PR #213's pattern (scope creep from UI changes) -- here the scope creep is infrastructure. <!-- Source: post-mortem, second-brain #228, 2026-02-25 -->
- **"Keep-in-sync" comments are a code smell -- extract instead.** second-brain PR #198 duplicated `buildTodoInlineButtons` across telegram.ts and todo-list-handler.ts with "keep in sync" comments. The adversarial review identified the duplication but deemed it acceptable. CodeRabbit flagged it post-push, requiring a fix commit that extracted the shared utility (net -9 lines). When identical logic exists in 2+ files and is under ~30 lines, always extract to a shared utility rather than commenting "keep in sync." The comment is a maintenance liability that the extraction eliminates. <!-- Source: post-mortem, second-brain #198, 2026-02-21 -->
- **Out-of-scope commits bundled into focused removal PRs.** PR #265 (remove QUERY from feed) included an unrelated commit (688e88c) adding a GitHub Actions auto-review-fix workflow. This inflates the diff (134 LOC vs ~90 LOC without it) and muddies the PR's purpose. The workflow commit should have been its own PR. When a tangentially-inspired automation idea surfaces during a focused PR, defer it to a separate PR rather than bundling it. <!-- Source: post-mortem, second-brain #265, 2026-02-26 -->

## Adversarial Review Gaps

- **JSDoc is the dominant post-push finding category for new component PRs.** nanny-app PR #35 had 4 of 7 post-push findings related to missing JSDoc on exported components/functions. The adversarial checklist Tier 4 "Documentation sync" mentions JSDoc but has no mechanical grep step. A Tier 0 grep for exported functions/components without JSDoc in changed `.tsx` files would catch this class. <!-- Source: post-mortem, nanny-app #35, 2026-02-20 -->
- **Adversarial review can identify but incompletely fix error handling patterns.** nanny-app PR #35's adversarial review listed "async error handling" as a finding and partially addressed it, but the core bug (onComplete() called unconditionally after catch) shipped. The Tier 1.2 mechanical verification ("For each catch, what happens on the happy path after it?") was not fully executed. When adversarial review identifies a class of issue, verify the FIX is complete -- not just that the issue was acknowledged. <!-- Source: post-mortem, nanny-app #35, 2026-02-20 -->
- **JSDoc audit scope: fix the diff, miss the file.** PR #185's adversarial review caught "stale JSDoc" as a pre-push finding and fixed it, but Copilot found a different JSDoc inaccuracy in the same file (`MessageIntent` doc comment listed only `CHAT` but type also includes `TODO_LIST`, `DAILY_SUMMARY`, `MORNING_BRIEF`, `CALENDAR`). When fixing JSDoc as an adversarial finding, audit ALL doc comments in the changed file — not just the one directly affected by the diff. <!-- Source: post-mortem, second-brain #185, 2026-02-20 -->
- **useMemo dependency completeness is a recurring React review gap.** nanny-app PR #28 shipped incomplete useMemo dependencies in both Dashboard and HoursTracker -- memoized getPayPeriod(new Date(), config) without a date-based dependency key, causing stale results after midnight. Local adversarial review missed this in both components. The checklist needs a React-specific check: "For useMemo wrapping Date computations, verify a day-based key (e.g., getTodayISO()) is in the dependency array." <!-- Source: post-mortem, nanny-app #28, 2026-02-20 -->
- **JS Date constructor silent normalization bypasses NaN guards.** nanny-app PR #28's anchor validation checked for NaN but not calendar-invalid dates (e.g., '2026-02-30' -> March 2). new Date(year, month-1, day) silently normalizes, so the malformed fallback never triggers. Fix: after construction, verify getFullYear/getMonth/getDate match input components. Add to Tier 3 defensive coding checks. <!-- Source: post-mortem, nanny-app #28, 2026-02-20 -->
- **Checklist items present but not mechanically executed.** "UTC suffix in test Date strings" was literally in Tier 3 of the adversarial review checklist, yet test dates without Z suffix shipped. The bottleneck is execution discipline, not checklist coverage. Fix: run grep patterns, not just read items. <!-- Source: post-mortem, second-brain #131, 2026-02-16 -->
- **Unmount guard pattern known but not applied to new code.** PR #140's adversarial review reported 0 findings, but CodeRabbit caught a missing `isMountedRef` unmount guard — a pattern already documented in `react-patterns.md` and used by 3 sibling hooks in the same file. The adversarial review needs to cross-reference new async hooks against sibling patterns in the same file. <!-- Source: post-mortem, second-brain #140, 2026-02-17 -->
- **Copy-and-adapt defeats adversarial review discipline.** PR #143 adapted the inline-edit pattern from PR #142 to the TODO panel. The adversarial review claimed to find and fix 3 issues (Escape propagation, keyboard a11y, state cleanup), but all 3 shipped incomplete — CodeRabbit caught `role="button"` on span, Escape only on textarea, and missing save-guard. The checklist items (Tier 3: "Semantic elements", "Escape in edit-within-panel") have precise wording that would have prevented these. Root cause: "I already fixed this" cognitive shortcut when adapting patterns. Fix: re-run the checklist against the NEW instance, not assume coverage from the prior fix. <!-- Source: post-mortem, second-brain #143, 2026-02-17 -->
- **New gap: String truncation arithmetic.** When slicing + appending to fit a max length, verify `slice_length + suffix_length <= limit`. Added to knowledge but not yet in adversarial checklist. <!-- Source: post-mortem, second-brain #131, 2026-02-16 -->
- **New gap: User-facing text compound wrapping.** When a helper function adds decoration (e.g., parentheses) and callers add more, the result compounds (e.g., `((all day))`). Review all format helper return values against their call sites. <!-- Source: post-mortem, second-brain #131, 2026-02-16 -->
- **New gap: Test value swap vs. behavioral assertion.** When updating tests for a behavioral change, the adversarial review should verify whether the test asserts the OLD behavior with a new value or the NEW behavior entirely. PR #145 changed `"Interesting thought!"` to `"Thought saved."` in `toHaveBeenCalledWith` but did not change the assertion to `not.toHaveBeenCalled`, which was the actual behavioral change specified in the requirement. Value swaps are mechanical; behavioral verification requires reading the spec. <!-- Source: post-mortem, second-brain #145, 2026-02-17 -->
- **New gap: Test env variable isolation.** When tests mutate `process.env.*` (set in `beforeEach`, deleted in a test), the adversarial review should verify cleanup in `afterEach`. Without restore, env mutations leak to subsequent test files. The test-only category in the checklist lacks test isolation checks. <!-- Source: post-mortem, second-brain #148, 2026-02-17 -->
- **New gap: Missing error branch test coverage.** When a route has distinct error paths (timeout/AbortError -> 504, non-404 error -> 502), tests should cover each branch. The adversarial review should verify that all catch/error branches in new route handlers have corresponding test cases. <!-- Source: post-mortem, second-brain #148, 2026-02-17 -->
- **Test mock target verification.** When mocking service methods in test files, verify the mock targets the correct method for the code path under test. PR #159 mocked `findTodosForDate` (Due Today section) when the tested behavior used `findAllOpenTodos` (Open section) — a critical-severity finding caught post-push. The adversarial review should trace each mock to the production code path it simulates. <!-- Source: post-mortem, second-brain #159, 2026-02-19 -->
- **New gap: Conditional column selection for type-discriminated queries.** When a SQL query spans multiple entry types and adds a column only relevant to a subset (e.g., `extracted_text` only used for MEDIA entries), the adversarial review should flag unconditional SELECT as a bandwidth/performance concern. The current checklist covers index usage and WHERE clause optimization but not column-level selectivity for polymorphic result sets. <!-- Source: post-mortem, second-brain #162, 2026-02-19 -->
- **Local vs. post-push review find different issue classes.** PR #159 ran full local review (9 issues found pre-push) but CodeRabbit found 8 more post-push. Local review caught trigger gaps, query fields, JSDoc, sort logic. Post-push review caught test mock correctness, assertion shape completeness, type mismatches, and input validation. The adversarial review checklist is effective for production code but weak on test code quality (mock correctness, assertion completeness, fixture consistency). <!-- Source: post-mortem, second-brain #159, 2026-02-19 -->
- **RESOLVED: CSS custom property validation — automated via stylelint plugin.** Undefined `var()` references silently produce invalid styles. This gap was identified after PR #164 and confirmed again in PRs #317 and #320 (3 occurrences across CSS-heavy PRs). PR #323 closed the loop by adding `stylelint-value-no-unknown-custom-properties` to catch `var(--undefined)` at lint time, promoting adversarial review check 0.18 to CI automation. Also fixed 2 existing `--bg-secondary` uses (never defined) by replacing with `--surface`. This is the ideal gap-resolution pattern: repeated post-mortem finding -> adversarial checklist item -> lint-time automation. Future CSS PRs will catch undefined custom properties before push. <!-- Source: post-mortem, second-brain #164, 2026-02-20; confirmed #317, 2026-03-02; #320, 2026-03-02; resolved #323, 2026-03-02 -->
- **New gap: aria attribute pairing.** `aria-expanded` without `aria-controls` is incomplete. The checklist covers semantic elements (Tier 3) but not aria attribute completeness for collapsible/expandable patterns. <!-- Source: post-mortem, second-brain #164, 2026-02-20 -->
- **New gap: Popover/portal state cleanup on mode transitions.** When a component has multiple interactive modes (view, edit, date-picker-open), entering one mode should reset state for other modes. PR #186's DatePicker stayed logically "open" (showDatePicker=true) when user clicked Edit, causing it to reappear after editing ended. The adversarial review should verify: "When entering any interactive mode, are competing mode states reset?" <!-- Source: post-mortem, second-brain #186, 2026-02-20 -->
- **New gap: Popover repositioning on scroll/resize.** Portal-rendered popovers that compute position once on mount become disconnected from their trigger on scroll or window resize. The adversarial review should check: "Does this portal/popover recalculate position on scroll/resize, or at minimum close on scroll?" Both Copilot and CodeRabbit flagged this independently. <!-- Source: post-mortem, second-brain #186, 2026-02-20 -->
- **New gap: Silent error revert in optimistic UI.** Optimistic updates that revert on failure without any user-visible feedback create confusion — the user sees a change, then it silently disappears. The adversarial review should check: "After optimistic revert, is there user-facing error feedback (toast, inline error, etc.)?" <!-- Source: post-mortem, second-brain #186, 2026-02-20 -->
- **New gap: Defensive filtering for migration-gated type removal.** When removing a value from a type union AND gating the DB cleanup on a manual migration, code that queries the DB should defensively filter by supported types (e.g., `type IN (...)`) until the migration is confirmed run. Without this, legacy rows of the removed type can surface at runtime and crash downstream code that no longer handles them. Copilot caught two instances in search.ts. <!-- Source: post-mortem, second-brain #191, 2026-02-20 -->
- **New gap: Documentation count/state consistency on removal PRs.** When removing an entity from the system, docs that reference counts (e.g., "seven intents") or assert universal behavior (e.g., "AI responses persisted for all types") need updating. The adversarial review Tier 4 doc sync check should mechanically grep for count references and universal claims in docs touched by the diff. **Confirmed again (3rd occurrence):** PR #265 removed QUERY from feed and updated 2 docs, but 4 stale QUERY-in-feed references survived across PRODUCT_SPEC.md and async-research-agent/spec.md. The adversarial review caught 1 of 4. A mechanical `grep -rn "QUERY" docs/` would have caught all 4 in <2 minutes. <!-- Source: post-mortem, second-brain #191, 2026-02-20; confirmed #265, 2026-02-26 -->
- **Adversarial review "identified but not fixed" is worse than "not identified."** PR #198's adversarial review explicitly noted `buildTodoInlineButtons` duplication but chose to keep it with "keep-in-sync" comments. CodeRabbit flagged the same issue post-push. When the adversarial review identifies code duplication of identical functions, the default action should be extraction -- not documentation of the duplication. "We know about this and chose not to fix it" is a 0% catch rate for the finding, same as not seeing it at all. <!-- Source: post-mortem, second-brain #198, 2026-02-21 -->
- **"Covered but not actioned" is a repeating adversarial review failure mode (2nd occurrence).** PR #206's adversarial review explicitly identified "completed_at trigger fires on UPDATE only" as Finding #4 (LOW) but chose not to fix it. CodeRabbit flagged the same issue post-push. This confirms PR #198's pattern. When the adversarial review identifies an issue, the default should be to FIX it. "Low priority" or "non-blocking" is not a valid skip reason -- the 5-minute local fix always costs less than the 15-minute post-push round-trip (review + fix commit + re-review wait). <!-- Source: post-mortem, second-brain #206, 2026-02-22 -->
- **TOCTOU race on count-based limits in transactions is a blind spot.** PR #208's adversarial review ran the full DB checklist but missed that `SELECT COUNT(*) ... INSERT` inside a serializable transaction still allows concurrent transactions to read the same count before either commits. Advisory locks (`pg_advisory_xact_lock(hashtext($1))`) are needed to serialize the critical section. The Tier 2 DB checklist covers "check-then-insert in transaction" but not count-based limits specifically. This is a distinct pattern from dedup (which unique indexes solve) — count limits need serialization. <!-- Source: post-mortem, second-brain #208, 2026-02-22 -->
- **New gap: Telegram inline keyboard cleanup after callback handling.** PR #209 shipped callback handlers (`handleResearchCallback`) that edited message text after confirm/cancel/error but did not clear the inline keyboard (`reply_markup: { inline_keyboard: [] }`), allowing users to re-trigger callbacks after they were already processed. The adversarial checklist has no specific item for clearing interactive UI elements after handling. This is a Telegram-specific variant of "UI state cleanup after action completion." Consider adding to Tier 3 or to a new Telegram-specific section. <!-- Source: post-mortem, second-brain #209, 2026-02-23 -->
- **Adversarial review execution gap is systemic, not per-PR (6th consecutive occurrence).** PRs #199, #206, #209, #211, #237, and #256 all had post-push findings that mapped to existing adversarial checklist items. PR #256 had 75% coverage potential but 0% actual shift-left rate for those items because the adversarial review was "pending" at PR creation. The gap is not checklist completeness (items exist) but mechanical execution (items not applied OR the review step is skipped entirely). The adversarial review needs a structural intervention — either automated grep-based verification for high-frequency miss categories (XML escaping, whitespace guards, error fallback paths, delete-before-ready patterns) or a mandatory pass/fail evidence log that must reference grep output per item. Without this, the gap will persist regardless of checklist additions. <!-- Source: post-mortem, second-brain #237, 2026-02-25; strengthened #256, 2026-02-26 -->
- **React state management is the #1 adversarial review blind spot for UI PRs (4+ occurrences).** PR #215 had 5 of 11 post-push findings in React-specific patterns absent from the checklist: render-phase setState (calling setState during render body instead of useEffect), instance-unique element IDs (hardcoded `id="..."` and `name="..."` collide across multi-instance components), duplicate React keys from data-derived values (`key={value}` where array items can repeat), and local submitted flags to bridge parent-child state refresh gaps. PR #272 confirms: 3 of 12 post-push findings were stale async response / session switching race conditions in hooks. These patterns account for 36-45% of post-push findings on UI PRs. Candidate checklist additions: (1) grep for `set[A-Z]` calls outside useEffect/handler bodies in `.tsx`, (2) grep for hardcoded `id="` and `name="` in `.tsx`, (3) grep for `key={` where value is a raw data field (not index or computed unique), (4) grep for `useCallback` with state setters that don't guard against stale session/context refs. <!-- Source: post-mortem, second-brain #215, 2026-02-24; confirmed #272, 2026-02-26 -->
- **Client-server return type contract parity.** When a server route can return multiple response shapes (e.g., full object on success, minimal `{ id }` on fallback), the client API helper's TypeScript return type must be a union covering all shapes. Structural typing silently allows accessing fields that don't exist on the fallback shape. Check during Step 4b internal review when both routes-api and web client files are in the diff. <!-- Source: post-mortem, second-brain #273, 2026-02-26 -->
- **Fallback-value-as-noop in async fire-and-forget.** When a function returns a fallback on failure (e.g., existing summary when LLM call fails), callers in fire-and-forget paths must compare the returned value against the prior state before triggering downstream side effects (counter resets, DB writes). PR #275 reset `turns_since_summary` to 0 even when `generateRollingSummary` returned the unchanged fallback — effectively losing checkpoint tracking without producing a new summary. The adversarial review's "side-effect ordering" item covered this territory but the specific fallback-value comparison was missed. <!-- Source: post-mortem, second-brain #275, 2026-02-26 -->
- **Test assertion completeness for URL/input validation functions.** When implementing a URL validation function (e.g., `isSafeUrl` accepting http/https, rejecting javascript:/data:), the adversarial review should verify tests cover ALL allowed AND disallowed schemes explicitly. PR #274's `isSafeUrl` allowed http:// but only tested https:// -- CodeRabbit caught the gap post-push. The test-only category checklist lacks a mechanical check for "validation function branch coverage." Candidate Tier 0 grep: for each function with "safe"/"valid"/"allowed" in its name, verify test file covers all branches of the conditional. <!-- Source: post-mortem, second-brain #274, 2026-02-26 -->
- **setTimeout heuristics for async state clearing are a covered-but-missed optimistic UI pattern.** PR #287 used `setTimeout(() => { setPendingReply(null); ... }, 300)` to delay clearing optimistic state until refetch completed. CodeRabbit caught this post-push and suggested `await refetch()` instead. The adversarial review checklist Tier 1.5 covers optimistic UI but lacked a specific sub-item for await-vs-setTimeout. The local review caught 2 of 3 total findings (67% shift-left) but missed this one. Added sub-item 5 to Tier 1.5. <!-- Source: post-mortem, second-brain #287, 2026-02-28 -->
- **Refactored private helpers need dedicated contract tests.** PR #291 extracted `getThreadFamilyIds` from inline logic in `getRelatedEntries`. Local adversarial review (step 4d) reported 0 findings, but CodeRabbit flagged the absence of focused tests locking in the exclusion-set semantics (self, parent, children). When extracting logic into a new private helper, the helper's input-output contract needs its own tests -- implicit coverage through the original caller is insufficient because the refactoring changes which code path exercises the logic. <!-- Source: post-mortem, second-brain #291, 2026-02-28 -->
- **"Deletion-only" is not a valid reason to skip CodeRabbit when type unions or schema are modified.** PR #297 removed the research feature and narrowed `CuratorSuggestionType` from 3 to 2 values. CodeRabbit was skipped locally ("deletion-only PR, no new logic"), but CodeRabbit's post-push review caught the SQL CHECK constraint / TS union mismatch — an item explicitly in the adversarial review Tier 4 ("Type sync between SQL and TypeScript"). The adversarial review claimed 20/20 but missed this, confirming the "covered but not executed" pattern (9th occurrence). Any diff touching type definitions, enum values, or database constraints should always go through CodeRabbit regardless of net LOC direction. <!-- Source: post-mortem, my_mind_evolved #297, 2026-03-01 -->
- **Inter-terminal state transitions are a blind spot for derived field consistency.** PR #313 added WONT_FIX as a new terminal status alongside DONE. The DB trigger correctly handled transitions FROM non-terminal states (OPEN/IN_PROGRESS -> WONT_FIX) but omitted snooze clearing on DONE<->WONT_FIX inter-terminal transitions. The adversarial review reported 11/11 items with grep evidence yet missed this — the derived-field-consistency check was executed for new-to-terminal paths but not terminal-to-terminal paths. When adding a new terminal state, explicitly enumerate and verify ALL inter-terminal transitions for derived field consistency, not just entry transitions. This is the 10th occurrence of the "covered but not executed" pattern. <!-- Source: post-mortem, second-brain #313, 2026-03-01 -->

- **100% adversarial claim with 0% actual catch rate is the worst credibility gap (11th occurrence).** my_mind_evolved PR #353 claimed 22/22 checklist items with grep evidence (Tier 0: 11/11, Tier 1-4: 11/11), yet CodeRabbit found 5 issues post-push, 3 of which map to existing checklist items (Tier 0.13 focus-visible parity, Tier 0.16 stale async guards, "stale closure in background refresh"). A mechanical focus-visible grep should have caught the missing `:focus-visible` on `.retry-inline-button`. The claimed 22/22 is not credible. This confirms the systemic pattern: the adversarial review execution gap persists at a structural level -- the problem is not checklist completeness but genuine mechanical execution of checks that already exist. <!-- Source: post-mortem, my_mind_evolved #353, 2026-03-04 -->

- **IntersectionObserver + React state creates a distinct bug class.** PR #353's infinite scroll had 4 correctness findings from the interaction between IntersectionObserver lifecycle, React async state updates, and error recovery paths: retry storms (observer re-fires when loading flips false after error), stale teardown races (background refresh .finally() clearing newer guard), permanent stuck state (error guard blocks re-observation with no recovery path), and HTML content model violations. These bugs emerge from the combination of browser APIs and React's async state model, not from either in isolation. When IntersectionObserver or MutationObserver is combined with React state guards, review the full interaction matrix: what happens when each guard flips in each combination? <!-- Source: post-mortem, my_mind_evolved #353, 2026-03-04 -->

- **Theming PRs that add tokens but hardcode values in components are a CSS token consistency antipattern.** sleep-tracker PR #25 added `--avatar-grad-*` and `--nudge-*` tokens to `globals.css` but initially hardcoded the hex values in `AppHeader.tsx` and `GentleNudge.tsx` instead of referencing the tokens. CodeRabbit caught both instances post-push. The adversarial review checklist (Tier 3, CSS token consistency) covers this, but no local review was run. When a PR's explicit objective is tokenizing design values, a targeted grep for hardcoded hex values (`#[0-9A-Fa-f]{3,8}`) in changed `.tsx` files would catch this mechanically. <!-- Source: post-mortem, sleep-tracker #25, 2026-03-04 -->

## Step 2b (Hardening) Skip Criteria

- **Don't skip step 2b when the diff includes test files or React list renderings.** summer-camps PR #3 skipped 2b ("presentational components, no async, no user input") but the skip missed test file quality (non-null assertions, weak shape assertions) and React key patterns (string content as keys). Revised heuristic: skip 2b only when the diff contains zero `.test.*` files AND zero `.tsx` list renderings (`.map(` calls). The original justification was correct for production component code but the scope of "hardening" extends to test robustness and React reconciliation safety. <!-- Source: post-mortem, summer-camps #3, 2026-03-01 -->

## Process Compliance

- **Small changes are not exempt from the development flow.** PR #153 (6 LOC, 1 file) skipped steps 3 (lint + test), 4 (code review loop), and went straight to push. The CLAUDE.md development flow applies regardless of change size — the steps exist for consistency, not just for catching bugs in large PRs. ## Multi-PR Feature Coordination

- **Cross-package API path verification on multi-PR features.** When a feature spans multiple PRs (e.g., backend route in one PR, frontend call in another), the second PR's internal review (step 4b) must explicitly grep the other package for the endpoint path and verify they match. Unit tests pass independently on each side because each tests its own hardcoded path string — the contract between packages is invisible to automated checks. PR #275 (second-brain) registered the server route as `/capture-idea` while PR #277 added the frontend call as `/idea`. Both PRs passed all tests. The mismatch wasn't caught until production showed a 404. A process-level guard (grep the sibling package during review) is cheaper and more effective than a dedicated contract test for a solo-dev monorepo. <!-- Source: post-mortem, second-brain #280, 2026-02-27 -->

## PR Sizing

- **Local review shift-left effectiveness degrades above ~600 LOC.** Across 15 tracked PRs with local review data, PRs under 600 LOC achieve 67-100% shift-left rates (catching that fraction of total issues before push), while PRs over 600 LOC drop to 14-59%. The two cleanest large PRs — #142 (654 LOC, 100% shift-left, 0% fix-up) and #157 (587 LOC, 100% shift-left, 0% fix-up) — both sat right at the threshold. Meanwhile, PRs at 887-1565 LOC consistently hit 2-3 CodeRabbit CHANGES_REQUESTED rounds and 50-80% fix-up ratios. **Counterexample:** PR #205 (761 LOC, 20 files) achieved 89% shift-left rate despite exceeding the 600 LOC threshold. Contributing factors: well-defined auth domain, standard patterns, full step compliance. **Recommendation:** Split features over 600 LOC into 2-3 focused PRs. A 1500 LOC feature split into three 500 LOC PRs would likely push each PR's shift-left rate above 80%, reducing total review rounds from ~6 to ~3. <!-- Source: cross-PR analysis of 15 PRs with local review data, 2026-02-20; counterexample: second-brain #205, 2026-02-22 -->
