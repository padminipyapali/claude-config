# Testing Patterns

Cross-project learnings for testing strategy, mocking, and assertions.

## Test Strategy

- **"Include tests" means flow-level tests.** Pure-function tests on extracted helpers cannot catch missing code paths.
- **Byte-identity anchoring for engines that wrap proven artifacts.** When building an engine whose job is to reproduce already-proven outputs (a template renderer over proven prompts, a build script over a frozen dataset), the highest-value tests are golden-master replays (template + original slot values → byte-identical proven output) plus parse/serialize round-trips on the real repo files. This doubles as a data audit: plush-press #15's strict parser surfaced two latent data bugs in existing files (`../`-prefixed attachment paths; invalid YAML in `story-page.md`) that no unit test would have found. <!-- Source: post-mortem, plush-press #15, 2026-06-10 -->

## Test Design

- **JSDoc on test helper factories.** `create*` test helpers should document default values and override behavior.
- **Tests use `vi.waitFor()` for async side effects.** When testing fire-and-forget patterns (`.catch()` call sites), the fire-and-forget promise resolves asynchronously even when mocks are synchronous. Assertions on those calls need a microtask flush before checking: `await new Promise(r => setTimeout(r, 0))`. Without the flush, the assertion runs before the mock is called, producing false negatives. `vi.waitFor()` is also acceptable but less explicit about the cause. This applies to any code that calls an async function without `await` (fire-and-forget) — the test must yield to the event loop before asserting on the mock. <!-- Strengthened: PR review, second-brain #246, 2026-02-25 -->
- **Restore mutated `process.env` in afterEach.** Tests that `delete` or override env vars can leak state into other test files. Capture the original value in `beforeEach`, restore it in `afterEach`. <!-- Source: PR review, second-brain #148, 2026-02-17 -->
- **`vi.mock()` specifier must exactly match the production import path.** In Vitest ESM, `vi.mock('./auth')` does NOT intercept `import ... from './auth.js'` — the mock registry matches by resolved module ID, and different specifiers can resolve to different IDs. Use the exact same string as the production import (including `.js` extension). Same applies to `vi.importActual()` and dynamic `import()` in tests. Mechanical check: diff each `vi.mock()` argument against the corresponding production `import` statement. <!-- Source: PR review, leaflet #21, 2026-03-10 -->
- **Untranspiled-ESM native modules break node-only Jest suites — map them to a hand stub via `moduleNameMapper`.** Expo/React-Native packages like `expo-haptics` ship untranspiled ESM, so the moment a production module that imports one gets pulled into a node-environment Jest suite, unrelated suites fail to parse it. When the dependency is a fire-and-forget side-effect with no return-value contract (haptics, analytics pings), the cheapest fix is a no-op stub file (`src/utils/testStubs/<pkg>Stub.ts`) wired through `jest.config.ts` `moduleNameMapper: { '^expo-haptics$': '<rootDir>/src/utils/testStubs/expoHapticsStub.ts' }` — faster than expanding `transformIgnorePatterns` to transpile the real ESM. Two guards: (1) the stub must mirror the FULL API surface the wrappers touch (e.g. `selectionAsync`, `notificationAsync` + `NotificationFeedbackType`, `impactAsync` + `ImpactFeedbackStyle`), or call sites throw on missing members; (2) keep the real behavior independently asserted in the dedicated wrapper test, which should use `jest.mock('<pkg>', factory)` — that takes precedence over `moduleNameMapper` within the file, so the mapper stub does NOT shadow it and the actual `impactAsync("Light")`/`notificationAsync("Success")` assertions still run. Verify empirically that the wrapper test still asserts the real calls after adding the mapper. <!-- Source: post-mortem, baby-name-picker #115, 2026-05-29 -->
- **A TypeScript Jest config (`jest.config.ts`) requires `ts-node` as an EXPLICIT devDependency for clean installs.** Jest parses `*.config.ts` via `ts-node`, which it treats as an optional peer — so a local `node_modules` that happened to pull `ts-node` in transitively will run tests fine, while a clean `npm ci` (CI) fails with `'ts-node' is required for the TypeScript configuration files`. Declare `ts-node` in `devDependencies` explicitly; never rely on transitive presence. General rule: before declaring a build/test command CI-ready, verify against a pristine tree (`rm -rf node_modules && npm ci`), not an accreted local one — "verified locally" ≠ "verified on a clean install." <!-- Source: post-mortem, baby-name-picker #150, 2026-06-02 -->
- **CI-parity for tests that shell out to a runtime the runner must supply (generalized beyond `ts-node` to ANY subprocess interpreter).** A jest/vitest test that invokes `python3`, `ruby`, `go`, etc. via `child_process` passes locally because the dev machine has the interpreter, but will fail on a CI runner that lacks it. The pre-push checklist for such a test: (1) is the interpreter guaranteed on the chosen runner image? `ubuntu-latest` ships `python3` (and `ruby`, `go`) by default — confirm against the runner's documented toolset, don't assume; (2) does the same project already have GREEN tests shelling to the same interpreter? Prior art is the strongest parity signal — baby-name-picker #169 cleared its `python3` subprocess test by confirming 4 existing tests already shell `python3` and CI was green; (3) is the invoked script dependency-free (stdlib-only)? A script importing third-party packages reintroduces the clean-install trap at the interpreter level (`pip install` not run on the runner); (4) does the subprocess call have a timeout so a hung interpreter fails fast instead of stalling the whole suite (#169 added a 30s `subprocess` timeout)? Same root cause as the `ts-node` trap — "the test passes locally" says nothing about whether the runner can supply the dependency — but the surface is broader than node config loaders. <!-- Source: post-mortem, baby-name-picker #169, 2026-06-02 -->
- **Annotate untyped test fixture factories with their target type so a new REQUIRED field fails at compile time, not at runtime.** baby-name-picker #170 added a required `softnessPreference` field to `TasteProfile`; an untyped `makeProfile()` fixture (returning an object literal with no `: TasteProfile` annotation) silently omitted the new field, and the gap only surfaced as a runtime crash inside a test rather than a `tsc` error. The critic caught and fixed the latent crash, but the durable fix is structural: annotate every fixture factory with its return type (`function makeProfile(): TasteProfile { ... }`), so the next required-field addition is caught by the type checker across ALL fixtures at once. Untyped fixtures are a silent exemption from the "grep every constructor of a widened type" sibling-sweep — the compiler can't help you if the fixture isn't typed. When widening a type, also grep for untyped factories producing it (`makeX`, `createX`, `buildX` returning object literals) and annotate them. <!-- Source: post-mortem, baby-name-picker #170, 2026-06-02 -->
- **Verify mock targets match the production code path.** When mocking a service method for a test, trace the test's assertion back to the production code to confirm the mock intercepts the correct method. PR #159 mocked `findTodosForDate` when the tested feature used `findAllOpenTodos` — the test would have passed vacuously or failed confusingly. This is especially common when a service has multiple similar-sounding query methods (findForDate, findAllOpen, findByStatus). <!-- Source: post-mortem, second-brain #159, 2026-02-19 -->
- **Assert full object shapes in test expectations, not just IDs or callbacks.** When testing structured output (inline buttons, API response objects, data integrity), assert the complete object shape including labels/text and field types, not just identifiers or key presence. Use `toMatchObject` with `expect.any(String)` / `expect.any(Array)` type matchers over `toHaveProperty` loops — the former catches type regressions and missing fields, the latter only checks existence. Partial assertions miss label regressions and field omissions. <!-- Source: post-mortem, second-brain #159, 2026-02-19; strengthened: PR review, summer-camps #3, 2026-02-28 -->
- **Test boundary values explicitly for threshold/gap logic.** When testing any algorithm that splits, groups, or compares against a threshold (time gaps, count limits, size limits), always include three test cases: (1) exactly at the threshold, (2) one unit below, (3) clearly above. A test covering only "clearly above" and "clearly below" misses off-by-one bugs at the boundary. This is the minimum required for gap-grouping, session-splitting, rate-limiting, and any comparison using `>`, `>=`, `<`, or `<=`. <!-- Source: PR review, command-center #23, 2026-02-19 -->

- **Test fixture must omit the property being tested for defaults.** When testing "defaults X to Y", the test fixture must NOT include property X. If `makeSession()` already sets `source: "agent"`, a test titled "defaults source to agent" is tautological — it tests the fixture, not the code. Delete the property from the fixture before calling the function under test so the defaulting logic is actually exercised. <!-- Source: PR review, command-center #34, 2026-02-21 -->

- **Fake timers with `shouldAdvanceTime: true` for React Testing Library.** Vitest fake timers (`vi.useFakeTimers()`) hang indefinitely with `@testing-library/react` because RTL uses `setTimeout`/`setInterval` internally for `waitFor` and cleanup. Pass `vi.useFakeTimers({ shouldAdvanceTime: true })` to let RTL's internal timers progress while still controlling time in your tests. Always pair with `vi.useRealTimers()` in `afterEach`. Without `shouldAdvanceTime`, tests that render React components with fake timers will freeze. <!-- Source: PR review, second-brain #186, 2026-02-19 -->

- **Test mutually exclusive UI states with both PRESENCE and ABSENCE assertions.** When testing UI states that replace one element with another (e.g., "Explore button" replaced by "badge when research is complete"), test cases must assert BOTH the presence of the new element AND the absence of the old one. Testing only presence misses cases where both render simultaneously. Pattern: assert `getByRole("button", { name: /explore/i })` fails (or use `queryByRole`), AND assert `getByText(/ready/i)` succeeds. This applies to any conditional UI branch where two elements are mutually exclusive (loading spinner vs. content, edit mode vs. view mode, error state vs. success state). <!-- Source: CodeRabbit review, second-brain #213, 2026-02-23 -->

- **Test every error path in try/catch blocks, not just the primary one.** When a try block contains multiple `await` calls (e.g., `findUser()` then `linkUser()`), each can fail independently. A test for `findUser()` throwing doesn't cover `linkUser()` throwing -- both reach the same catch block but via different code paths. Write a separate test for each `await` that can throw, mocking the preceding calls to succeed and the target call to reject. This is especially important for linking/creation flows where the first call is a lookup and the second is a write. <!-- Source: PR review, second-brain #234, 2026-02-25 -->

- **Use specific patterns in negative assertions, not short substrings.** `not.toContain("View")` will break when any unrelated text contains the word "View" (e.g., "Weekly Review"). Use `not.toMatch(/View \d+ more in dashboard/)` or assert absence of the specific element/pattern you care about. The shorter the negative assertion string, the more likely it matches unintended content. <!-- Source: PR review, second-brain #276, 2026-02-26 -->

- **Test assertion depth: assert behavior, not just rendering.** For each test in a UI component suite, verify it asserts behavior (callback called with correct args, state changed, error displayed) — not just rendering (element in document). Tests that only check `getByText("Button label")` without simulating clicks or asserting callback invocations pass vacuously even when the interaction is broken. Mechanical check: for each `it()` block, verify at least one of: `toHaveBeenCalledWith`, `userEvent.click` + state assertion, `waitFor` + error text assertion. Pure presence-only tests ("renders X") should be the minority, not the majority. <!-- Source: CodeRabbit review, leaflet #36, 2026-03-12 (3 of 12 findings were this class) -->

- **Guard mock array access with `toHaveBeenCalledTimes` before indexing `mock.calls[N]`.** Accessing `vi.mocked(fn).mock.calls[0][0]` without first asserting `expect(fn).toHaveBeenCalledTimes(1)` gives an opaque `TypeError: Cannot read properties of undefined` when the mock wasn't called. The guard assertion gives a clear failure message ("expected 1 call, received 0") with the correct line number. Pattern: always assert call count before indexing into `mock.calls`. This applies to any mock introspection — `calls`, `results`, `instances`. <!-- Source: PR review, second-brain #324, 2026-03-02 -->
- **No non-null assertions (`!`) in tests — use explicit assertions instead.** `find(...)!` and `obj.field!` in tests produce opaque runtime crashes (`Cannot read property of undefined`) instead of clear test failures when data is malformed. Replace with nullable assignment + explicit assertion: `const item = list.find(pred); expect(item).toBeDefined();` then use `item?.field` or `item?.children ?? []` for safe access. This surfaces data problems as assertion failures with proper line numbers and messages. Mechanical check: grep test files for `!;` and `!.` non-null assertions. <!-- Source: PR review, summer-camps #3, 2026-02-28 -->

- **Lint-as-test against stale date constants in production entry points.** When a clock dep defaults to a literal `new Date("YYYY-MM-DD...")` ("simulated now" for test convenience), the CLI silently freezes once real time advances past that date. The fix is a regression test that (a) greps every production entry-point script (`scripts/*.ts`, `src/scheduler/*.ts`) for `new Date("20...")` literals and fails if any exist, and (b) calls the entry point's default factory and asserts the returned timestamp lies between two real-wall-clock samples taken around the call. Test-fixture date literals belong only in `__tests__/`. This converts "spotted by a human when the recap window looked wrong" into a unit-test failure. <!-- Source: post-mortem, family-digest #37, 2026-05-16 -->

- **Assert mock call parameters, not just call counts or response values.** When mocking a DB query or service call, asserting `toHaveBeenCalled()` or checking only the HTTP response is insufficient -- a regression that drops `user_id` scoping from a query would still pass. Assert the SQL shape (`expect.stringContaining('WHERE user_id = $1')`) and bind parameters (`expect.arrayContaining(['user-id'])`) to verify security contracts and data integrity. Pattern: `expect(mockQuery).toHaveBeenCalledWith(expect.stringContaining('INSERT INTO'), [userId, topic, ...])`. This is the DB-layer equivalent of "assert full object shapes" -- response-only tests miss internal contract regressions. <!-- Source: PR review (CodeRabbit), leaflet #22, 2026-03-10 -->

## Async Test Patterns

- **Negative async assertions need settle time.** Polling helpers like `waitFor` pass immediately for negative assertions ("should NOT have been called") because the condition is true from the start. Use an explicit timeout to let promises settle before asserting: `await new Promise(r => setTimeout(r, 50)); expect(mock).not.toHaveBeenCalled();`. Without the settle delay, the assertion passes vacuously even if the mock IS called a microtask later.

## Mocking Pitfalls

- **Remove copy-pasted `vi.mock()` blocks that the test file doesn't use.** When creating a new test file by copying an existing one, dead mock blocks for unused modules (Firebase, auth providers, etc.) survive because they don't cause test failures. They add false coupling — if the mocked module's API changes, the dead mock breaks the unrelated test. Mechanical check: for each `vi.mock()` in a test file, grep the file for actual usage of the mocked module's exports. If none, remove the mock block. <!-- Source: CodeRabbit review, sleep-tracker #14, 2026-03-03 -->

- **File-injected/mocked tests cannot see bundler-runtime path bugs — any code that resolves paths relative to module location needs one smoke pass against the REAL dev server.** plush-press #25: `resolveRepoRoot` computed the repo root two-levels-up from the module dir; every unit/route test passed because tests injected paths or ran the module from its source location. Under `next dev`, Turbopack relocates the compiled module into `.next/`, so the root resolved inside the build directory and every books/prompts route 404'd — found only by driving the live dev server (Playwright/curl), not by the 175-test suite. Rule: for filesystem-resolution code in bundled apps (Next.js, Vite, webpack), the test gate is a real-server smoke (start `next dev`, hit one route that touches the resolved path); unit tests alone are a false green. Fix pattern lives in typescript-patterns.md (marker-directory walk-up). <!-- Source: post-mortem, plush-press #25, 2026-06-11 -->

- **`vi.doMock` does not affect already-resolved static imports.** `vi.doMock()` only applies to subsequent dynamic `import()` calls, not modules already loaded via static `import` at the top of the file. If you import `Foo` statically and then `vi.doMock("foo-module", ...)`, the imported `Foo` still points to the real module. Either use `vi.mock()` (hoisted to file top) or manually override the dependency on the instance (e.g., `(obj as any).client = mockClient`). Dead `vi.doMock` blocks are common — they appear to work only because a manual override elsewhere does the real mocking. <!-- Source: PR review, command-center #40, 2026-02-27 -->

## Test Cleanup

- **Restore mutated browser globals in `afterEach` — `vi.restoreAllMocks()` does NOT undo direct property assignments.** When tests assign directly to browser globals (`navigator.clipboard = { writeText: vi.fn() }`, `navigator.share = vi.fn()`, `window.matchMedia = vi.fn()`), `vi.restoreAllMocks()` only restores Vitest-created spies/stubs. Direct assignments persist across tests, causing order-dependent flakiness. Fix: either (A) use `vi.stubGlobal('navigator', ...)` which integrates with Vitest cleanup, or (B) capture the original value in `beforeEach` and restore in `afterEach`. Never restore inside the test body — early failures skip the restore. Pattern: `let origClipboard: Clipboard; beforeEach(() => { origClipboard = navigator.clipboard; }); afterEach(() => { Object.defineProperty(navigator, 'clipboard', { value: origClipboard, writable: true }); });`. <!-- Source: CodeRabbit review, leaflet #36, 2026-03-12 -->

- **`vi.restoreAllMocks()` belongs in `afterEach`, never inside individual tests.** Placing `vi.restoreAllMocks()` at the end of a specific test is fragile — if the test fails or is skipped, mocks leak into subsequent tests. Move to `afterEach(() => { vi.restoreAllMocks(); })`. Same applies to `vi.useRealTimers()`, `vi.unstubAllEnvs()`, and any state restoration. General rule: cleanup that undoes test-specific mutations goes in `afterEach`, not in the test body. <!-- Source: PR review, second-brain #256, 2026-02-25 -->

## Mock Data Type Safety

- **Match exact types in mock data — `vi.fn()` bypasses type checking.** When constructing mock return values (e.g., `vi.mocked(service.query).mockResolvedValue({...})`), match the exact TypeScript type for every field. Common trap: `completedAt: new Date().toISOString()` produces a `string`, but the interface declares `completedAt: Date`. Tests pass because `vi.fn()` and `as unknown as` casts bypass compile-time checking, but the mock shape silently diverges from production data. If the implementation later accesses `.getTime()` or other Date methods, the test will fail with a confusing runtime error instead of catching the mismatch early. <!-- Source: PR review, second-brain #199, 2026-02-21 -->
