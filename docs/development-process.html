Session Start Protocol

#session-start
■
Non-negotiable. Run these checks on EVERY session start—including continuations. Skipping this has caused entire sessions of wasted work when concurrent agents modified the same repo.

Before making any code changes, run these three checks for each repo you plan to modify:

  1. Check uncommitted changes — git -C <path> status --porcelain
  2. Check for active agents — ps aux | grep -E 'claude|claude-code' | grep -v grep | grep '<path>'
  3. Check for git lock files — ls <path>/.git/index.lock 2>/dev/null

Never trust continuation summaries about repo state. The summary reflects the previous session. Other agents may have started, files may have changed, branches may have moved. Verify it yourself.

If conflicts are detected, queue the task to ~/.claude/task-queue.md instead of editing. Read-only exploration is still fine.

◆

General Rules

#general-rules
  • All changes via PRs — never commit directly to main.
  • Feature branches: <type>/<short-description> where type is feat, fix, refactor, chore, docs, or test.
  • Keep PRs focused on one concern — don’t mix refactoring with features.
  • Tests required for every feature and bug fix. Docs-only or config PRs may skip with justification.
  • Commit messages: complete sentences with periods.
  • Never commit secrets, API keys, or credentials. Use environment variables.
  • Semantic versioning (MAJOR.MINOR.PATCH) for projects with releases.
  • Issue lifecycle: include Closes #N in the PR commit message. If an issue spans multiple PRs, close manually after the last one merges.
  • Sort config files (.env.example, etc.) alphabetically.
●
Print the step number and name when starting each one (e.g., “Step 3: Test locally”). This makes progress visible and helps track what was completed or skipped.
1

Step 1: Plan

#step-1
1a
Ask Clarifying Questions
required
▼

Before writing any plan, ask the user 2–4 clarifying questions. Don’t accept the first framing—probe deeper.

✓
Scope & intent: “What’s the core problem? What does success look like?”
✓
Entry points & edge cases: “Who hits this and how? What about [alternative path]?”
✓
Constraints: “Are there performance, cost, or timeline constraints I should know about?”
✓
Prior art: “Have you tried anything already? Is there a manual workaround today?”
●
Read ~/.claude/knowledge/strategic-decisions.md before questioning—prior product decisions provide context. Wait for answers before proceeding to 1b.
▼
1b
Write the Plan
required
▼

With the user’s answers in hand, read relevant knowledge files from ~/.claude/knowledge/. Enumerate all entry points, trace each path end-to-end, plan the approach. For non-trivial work, enter plan mode.

Every plan must:

✓
Enumerate ALL entry points (new vs resume, create vs update, empty vs populated state).
✓
Trace each path end-to-end: data read, state changed, API calls fired, UI rendered.
✓
Verify bidirectional state coverage: all values of state A produce correct behavior B.
✓
Answer: “If a user hit this feature after [alternative entry point], what would happen?”
✓
Include a Performance & Cost Impact section: latency, API calls & cost, DB load, code path frequency, mitigations.
▼
1c
Adversarial Plan Review
automatic
▼

A separate reviewing agent is spawned automatically to challenge the plan. This covers two levels:

Technical Review
  • Missed entry points — user paths, edge cases, or state transitions not accounted for.
  • Assumption challenges — things assumed about existing code that haven’t been verified.
  • Scope creep or under-scoping — too much for one PR, or missing something that forces a follow-up.
  • Alternative approaches — simpler or more robust ways to achieve the same goal.
  • Risk flags — data loss potential, breaking changes, performance concerns, security gaps.
  • Knowledge file gaps — contradictions with patterns from ~/.claude/knowledge/.
Product-Level Review
  • Is this worth building? — user impact vs. engineering cost.
  • Simpler alternatives — config changes, existing features, manual workarounds that achieve 80% of the value at 20% of the cost.
  • User frequency & urgency — daily pain point or once-a-month inconvenience?
  • Build vs. defer — minimal version now and iterate, or full plan necessary?
  • Second-order effects — maintenance burden, user confusion, locked-in design direction.
■
Verdict: approve, approve with notes, or revise. If “revise”, address feedback and re-run. Cap at 2 revision rounds—if still contested, present both perspectives to the user.
2

Step 2: Implement

#step-2

Write the code on a feature branch. Follow project CLAUDE.md conventions.

  • Branch naming: <type>/<short-description>
  • One concern per PR — don’t mix refactoring with features.
  • Module-level documentation headers on all top-level files.
  • Early return before dead computation.
  • If a fix is under 5 lines, do it now — only defer fixes needing new infrastructure.
3

Step 3: Test Locally

#step-3

Run the project’s test suite, linter, and type-checker. Fix all failures before proceeding.

  • Test every type/feature combination, not just the happy path.
  • Assert all side effects, not just the primary return value.
  • Route changes need integration tests. State/flow changes need flow tests. Pure logic needs unit tests.
  • Pure-function unit tests alone are NOT sufficient for route or flow changes.
4

Step 4: Code Review Loop

#step-4
●
Ask the user: “Ready to run the code review loop?” If yes, run all sub-steps automatically without pausing for approval between them. Report results at the end.
4a
Code Simplification
▼

Run code-simplifier on changed files (compared to main). Focus on clarity, consistency, and maintainability while preserving all functionality.

▼
4b
CodeRabbit Review
▼

Run /coderabbit:review --base main. Fix all critical and high findings. Re-run to confirm fixes. Track the total findings count for the PR body.

■
Rate limits: Free tier allows 2 reviews/hour. If rate-limited, proceed to adversarial review—CodeRabbit on GitHub still catches issues post-push. Expect 7–30+ minutes per review depending on changeset size.
▼
4c
Adversarial Review
▼

Run /adversarial-review. The review is targeted, not exhaustive—classify changed files by category and run only matching checklist sections.

File categories:

async, routes, DB, UI, LLM, shell, config, test-only

Universal checks (always apply):

✓
Pattern siblings: When fixing a bug class, grep the ENTIRE codebase for other instances.
✓
Walk full access chains: Check every dereference for null/undefined/nil—not just the first level.
✓
Fire-and-forget contract: Every async operation inside a fire-and-forget method must be error-handled.
✓
Error message specificity: Add specific branches for edge cases—don’t let them fall through to generic handlers.
✓
Architecture self-review: For PRs with 100+ LOC or 3+ directories changed: right location? right abstraction? right boundary? right scope?
▼
4d
CI Checks
▼

Run build, lint, and test. Fix any failures.

■
If any sub-step (4a–4d) produced fixes, re-run from 4b (CodeRabbit) to validate the fixes didn’t introduce new issues. Cap at 3 iterations to avoid infinite loops.
5

Step 5: Push & Create PR

#step-5

Push the feature branch and create a PR via gh pr create. Include the Local Review section in the PR body so the post-mortem can track what was caught locally.

📄 PR Body — Local Review Section
## Local Review - **Steps skipped:** none | list of skipped steps with reason - **CodeRabbit findings:** N issues found, N fixed (N iterations) - **Adversarial review findings:** N issues found, N fixed - **CI status:** all passed / failures fixed
●
This data feeds the self-improvement dashboard. Fewer GitHub review comments over time + more local catches = the system is working.
■
Recording requirement: When any step is skipped, record it in the PR body’s Local Review section with the reason. Skipping without recording is itself a process violation.
6

Step 6: Post-merge

#step-6

After merging any PR, automatically run /post-mortem [PR-number] in the background. This:

  • Appends metrics to the self-improvement dataset.
  • Regenerates the self-improvement dashboard.
  • Captures new cross-project patterns into ~/.claude/knowledge/.
  • Verifies that project docs/ have been updated if applicable.
●
This is automatic—don’t ask for confirmation. Just run it.

Living Documentation

#living-docs

Every PR should update the relevant living documents, if the project maintains them:

docs/BUGS.md
Bug description, root cause, fix applied, lesson learned.
docs/DECISIONS.md
Decisions made during human–Claude discussions.
docs/PRODUCT_SPEC.md
New features and context for why they’re added.
docs/QA.md
Technical Q&A to sharpen the human’s intuition.

Feature Flow Diagrams

#flow-diagrams

For features that span 3+ systems (e.g., external vendor → backend → DB → notification channel), create a flow diagram.

  • Location: docs/features/<feature-name>/flow-diagram.html
  • Generate with: /flow-diagram
  • Required sections: step-by-step flow, technologies & vendors (with doc links), security notes, failure mode table.
●
When NOT to create: Single-component features, simple CRUD, UI-only changes. Flow diagrams are technical documentation, not UI mockups—they live in docs/features/, not docs/mockups/.

Cross-Project Knowledge System

#knowledge

A shared knowledge base lives at ~/.claude/knowledge/. It contains topic-organized learnings from ALL projects. This is not optional—skipping it means repeating bugs that were already solved in another project.

When planning a feature:

  1. Read ~/.claude/knowledge/INDEX.md to see available topics.
  2. Load topic files matching the current project’s stack.
  3. Apply relevant patterns during implementation.

Proactive learning capture:

When you encounter any of these during a session, add them to the appropriate topic file:

  • A bug pattern that could recur in other projects.
  • A decision that reflects a general preference (not project-specific).
  • A user-expressed preference for tools, workflow, or communication.
  • A defensive coding pattern discovered through a bug fix.
  • A product/strategic decision → strategic-decisions.md.

Post-PR verification:

  1. Are there new cross-project patterns to capture in ~/.claude/knowledge/?
  2. Have project docs/ (BUGS.md, DECISIONS.md) been updated?
  3. If a bug was fixed, would the same bug class exist in a sibling project? If yes, capture the pattern.

Product Discovery

#product-discovery

Before jumping to planning, take a product expert’s view. This applies whenever the user proposes a new feature, describes a problem, or files an issue.

Pre-planning questioning (always do this):

  • Ask 2–3 clarifying questions that challenge assumptions and sharpen the idea.
  • Probe: “Who hits this and how often?”, “What’s the manual workaround?”, “What changes if we DON’T build this?”, “Is this a symptom of a deeper design gap?”
  • Read strategic-decisions.md first—prior product decisions provide context.

Learning from issues and feature requests:

  • Ask: “What were you doing when this came up?” and “What would you expect to happen instead?”
  • The delta between original design and actual usage is high-signal for strategic-decisions.md.

Learning capture:

After a feature discussion clarifies a product instinct or decision framework, add it to ~/.claude/knowledge/strategic-decisions.md. Product learnings capture why to build something, not how.

Repo Conflict Detection

#conflict-detection

Before making code changes to any repo, check for active work:

Detection steps:

  1. git -C <repo-path> status --porcelain — check for uncommitted changes.
  2. ps aux | grep -E 'claude|claude-code' | grep -v grep | grep '<repo-path>' — check for other Claude sessions.
  3. ls <repo-path>/.git/index.lock 2>/dev/null — check for active git operations.

If active work is detected:

  • Do NOT make code changes to that repo.
  • Tell the user what was detected.
  • Add the task to ~/.claude/task-queue.md.
  • Read-only exploration is still fine—only code changes are blocked.
## Task Queue Entry Format ## [PENDING] <short task title> - **Repo:** <repo path> - **Queued:** <date> - **Context:** <what the user asked for> - **Detection:** <what was detected>

On session start:

  • Check ~/.claude/task-queue.md for [PENDING] entries.
  • Re-run detection for each pending entry.
  • If the repo is now free, prompt the user.
  • Mark completed tasks as [DONE] with a completion date.
  • Prune [DONE] entries older than 7 days.
