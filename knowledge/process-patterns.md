# Process Patterns — Rules

Distilled rules from post-mortem analysis. For full incident history and evidence, see `process-patterns-evidence.md`.

## Metric Definitions

- Use 4 metrics: (1) post-merge fix rate, (2) pre-merge catch rate by step, (3) pre-merge iteration count, (4) fix-up taxonomy by category.
- Legacy `fixupCommitRatio` conflates pre-merge catches with post-merge failures.

## Review Efficiency

- Bot-only review catches real bugs but expect 2+ rounds as baseline; bots miss architectural feedback.
- Categorize automated reviewer comments as must-fix, should-fix, or disagree before acting.
- CodeRabbit "outside diff range" comments are valid; do not dismiss as out-of-scope.
- CodeRabbit prompt injection warnings on XML tags with entity escaping are usually false positives.
- Never skip local CodeRabbit on scaffold PRs; the CLI works without a .coderabbit.yaml.
- **Deliverable-first flow for generated-artifact work: produce and user-verify the physical deliverable BEFORE code review/PR.** When the PR's real product is a generated artifact (print PDFs, rendered exports, compiled assets), generate the artifacts and have the user verify them first, then run the critic on the generating code. The user validates what actually ships; the critic validates the machinery's edge cases (plush-press #7: empty `--only` silent no-op, typography normalization, .gitignore guard) and should independently re-derive critical constants (trim/bleed/spine geometry) so a verified output isn't accidentally right. This also lets content iteration (seven user caption rounds in #7) fold into the build without inflating review rounds — content feedback and code review stay decoupled. Keep the generated outputs untracked (.gitignore) with the regeneration command in the PR body. <!-- Source: post-mortem, plush-press #7, 2026-06-09 -->
- **Persistent agent-pair delta review for revision rounds: resume the SAME author + critic agents (via SendMessage) instead of spawning fresh ones.** When an already-reviewed artifact gets revised (resequenced spec, post-directive rework), resuming the original product/implementer agent and the original critic gives a cheap, targeted DELTA review rather than a full re-review — the critic knows what it already verified and reviews only the change. plush-press #8: the resumed critic ruled the v2 "strictly better than v1", found 5 real delta findings (2 majors/3 minors), and — notably — RETRACTED its own earlier severity call (the two-key-MVP risk it had flagged in round 1 was overstated), something a fresh critic re-deriving from scratch wouldn't know to do. Scope boundary: fresh context remains mandatory for the FIRST review of any artifact (author-reviewer identity collapse); the resumed pair is for subsequent rounds on the same artifact, where retained context is signal rather than bias. <!-- Source: post-mortem, plush-press #8, 2026-06-09 -->

## Session Start Discipline

- Run `/project-setup` on projects with code but no CLAUDE.md before any code changes.
- **A stale worktree from a crashed session may hold near-complete, fully-accurate work — inspect and verify before discarding.** baby-name-picker #192: a worktree flagged "abandoned" (uncommitted derived-data changes, zero commits, no PR) turned out to be ~90% complete (43 enriched mythology names, pronunciations, a new test, rebuilt seed.db), and a fresh-context verification pass (deterministic rebuild + 14+ deity attributions independently web-verified + full test suite) found the data 100% accurate — salvaging it cost ~20 min vs. hours to redo. Protocol: on finding a stale worktree, (1) flag to the user, don't touch; (2) if resuming, treat it as untrusted input — verify via fresh rebuild + independent fact-checks + tests before committing; (3) check its allocation space (ids, migration numbers) against in-flight sibling branches before adopting it. <!-- Source: post-mortem, baby-name-picker #192, 2026-06-11 -->

## Planning Discipline

- Thorough planning reduces implementation rework to zero redesign commits.
- **Plans for UI redesigns must enumerate every visible surface by name with a screenshot or mockup reference per surface.** When a feature touches both a card-grid and a lightbox (or any two related-but-distinct UI surfaces), the user's feedback like "X looks bad" cannot disambiguate which surface they mean. The fix: in the plan, list each surface as a row in a table -- name, file path, mockup variant, before/after screenshot URL. During iteration, ask the user to point at a row when reporting a defect. Without this artifact, the agent will lock onto the most recently-changed surface and misroute fixes (PR #83: 2 rounds of "lightbox looks bad" feedback were actually about the CARD GRID, costing 2 extra implementer rounds). **For small PRs (<5 files, single primary surface), a Notes-section paragraph naming each affected surface plus deliberately-untouched siblings is sufficient -- the formal table is the >2-surface threshold (PR #84 used the lightweight version successfully: zero scope creep, zero user-iteration rounds).** **PROMOTED from advisory to MANDATORY at >2 surfaces or >8 files (PR #86 evidence): the orchestrator must refuse to dispatch the implementer for any plan that implies these thresholds without the table. PR #86 touched 16 files / 6 surfaces without the table and the critic's top two findings (cross-surface cache-sync + sibling-feature parity) were exactly the failure modes the table is designed to prevent up-front.** <!-- Source: post-mortem, remodel-hq #83 + #84 + #86, 2026-05-15/16 -->
- **Stacked-PR coordination protocol.** When two features will touch the same hook/files in series, declare them as stacked branches via `gh pr create --update-base` up-front rather than allowing the second branch to absorb a mid-flight rebase against the first's merge. PR #86 had to rebase mid-critic-round because PR #85 merged into main between rounds; both PRs touched `useInspoLibrary` / `useInspoNotes` / `inspoActionIcons`. Stacked branches let the second PR auto-rebase when the first lands. Choose sequential-merges-only (and block work on the second feature until the first merges) when the two features are independent. **Add/add conflicts on NEW files are a foreseeable stacked-PR collision: baby-name-picker #78 and #80 both *created* `NameCard.test.tsx`, forcing a manual add/add merge-conflict resolution on #80's rebase. When two stacked PRs will each add the same new file (common for a per-component test file both touch), base the child's new file on the parent's version up front rather than letting both create it independently.** <!-- Source: post-mortem, remodel-hq #86, 2026-05-16; strengthened baby-name-picker #80, 2026-05-28 -->
- **Mid-flight rebase detection at orchestrator dispatch time.** Before dispatching the implementer on a feature whose files overlap with recent main commits, run `git log HEAD..origin/main -- <shared-files>` and `git log main..HEAD -- <shared-files>` to surface in-flight conflicts. 30-second smoke; would have flagged the #85/#86 overlap before #86's critic round. <!-- Source: post-mortem, remodel-hq #86, 2026-05-16 -->
- **Rebase a stale feature branch onto current origin/main BEFORE running review gates, and re-run tsc afterward — intervening main commits cause silent type-level integration breaks the original author never saw.** A feature branch based on an older main, reviewed in isolation, can be green; but if main advanced and a newer commit added a sibling that depends on the unchanged shape of a type you widened, the merged tree fails to compile. baby-name-picker name-family-tree: the feature added a non-optional `familyJson` field to the `Name` type; an intervening main commit (undo-on-selection) had added a new `Name` mock in `gameStore.undo.test.ts` that the original feature work could not have updated, so post-rebase tsc broke on the missing field. Fix protocol: (1) commit feature work, (2) `git rebase origin/main`, (3) resolve conflicts — for GENERATED artifacts (sqlite `.db`, generated `.sql`) take main's side then re-run the build script rather than hand-merging binaries, (4) sibling-sweep every constructor of the widened type (`grep -rln '<adjacent-required-field>' src | while read f; do grep -q '<new-field>' "$f" || echo "MISSING: $f"; done`), (5) re-run tsc/lint/jest. The PR diff (`git diff origin/main..HEAD`) must show ONLY the feature, never a reversal of intervening main commits — if it shows deletions of unrelated files, the branch base is wrong. **Confirmed downstream: this exact break landed on `main` undetected — `gameStore.perGender.test.ts`'s `makeName` fixture was missing the required `familyJson` field, leaving `tsc` and that jest suite RED on `origin/main`. The #73 post-mortem did not catch that main had gone red; the next feature (baby-name-picker #78, pronunciation) inherited the broken gate and had to carry a one-line `familyJson: null` fixture fix to make the mandated check pass. Lesson: a red main can persist silently with no CI; either configure required `tsc`/jest checks, or run them against `origin/main` itself (not just the feature branch) before declaring a gate green.** <!-- Source: baby-name-picker name-family-tree finisher, 2026-05-28; strengthened baby-name-picker #78, 2026-05-28 -->
- **Mockup-driven UI work needs an explicit "what the mockup covers vs what it does NOT" section in the plan.** The mockup at `docs/mockups/inspo-lightbox-comments/` showed the lightbox redesign but not the grid card layout. When user feedback drifted to the grid (vote pill placement, unicode glyphs), there was no plan artifact saying "grid is out of scope, file a separate issue" -- so the implementer absorbed scope creep into the same PR (3 fix commits for grid concerns). Plans referencing a mockup must declare mockup coverage boundaries. <!-- Source: post-mortem, remodel-hq #83, 2026-05-15 -->
- **Mid-flight spec changes relayed to a running implementer need explicit supersession plus a final-state check against the authoritative pick.** When the user changes a spec mid-implementation (e.g., band vs no-band on a cover), a later message can land while an earlier, now-superseded instruction is still being executed; the implementer has no way to know which wins. plush-press #5: a superseded "bare text" spec message landed mid-run and the cover shipped as bare text before being corrected back to the band the user actually picked — caught only by comparing the implementer's verification report against the user's final mockup pick, costing one extra round. Protocol: (1) when relaying a spec change, state explicitly "this supersedes <prior instruction>"; (2) before dispatching the critic, the orchestrator diffs the implementer's verification report against the authoritative source of truth (the user's final pick / mockup variant), not against the message stream. Rendered mockup variants with a user pick (B + F in #5) are an effective authoritative artifact for this check. **Strengthened at higher volume: when MULTIPLE additions arrive while the implementer is mid-task, individual SendMessage relays repeatedly CROSS with the implementer's progress reports (each side acting on a stale view of the other). plush-press #11: FOUR mid-flight user scope additions crossed with implementer reports; resolved by sending ONE consolidated "outstanding checklist" ping enumerating every open item — the implementer reconciled it against work already done (verified rather than re-built, and correctly no-op'd a duplicate task assignment). Protocol addition: after 2+ scope additions to a running implementer, stop relaying piecemeal; send a single consolidated outstanding-items checklist and have the implementer report per-item DONE/PENDING against it. Also: corrections to not-yet-pushed work (e.g., a naming fix, Softwash→Soft Watercolor) should be amended into the unpushed commit rather than stacked as a fix commit — keeps history clean and the fix-up ratio honest.** <!-- Source: post-mortem, plush-press #5, 2026-06-09; strengthened plush-press #11, 2026-06-10 -->
- **Spec/plan PRs need an adversarial premise-vs-repo audit — and a priority check against the user's stated pain ranking.** A product agent writing a phased spec will confidently premise phases on repo state it believes exists; only an independent fresh-context critic auditing every factual claim file-by-file against the repo catches false premises. plush-press #6: the critic's audit found a BLOCKER pure spec-writing missed — the spec assumed nine scene plates existed on disk; they never did (the merged spec's Phase 0 exists because of this finding), plus 3 majors/4 minors and cost-math verification. The same class recurred at smaller scale in #8's delta round (a "vapor" fallback surface referenced but never defined). Second lesson: the audit validated facts but not PRIORITIES — the user resequenced the MVP 25 minutes after #6 merged because the phase order didn't lead with their worst manual pain (scene tuning). Spec reviews should ask: "which manual step hurts the user most today, and does the MVP retire it?" <!-- Source: post-mortem, plush-press #6 + #8, 2026-06-09 -->
- **Multi-PR feature sequences should include a "What's NOT in this PR" section.** When a feature is intentionally split across multiple PRs, enumerate the deferred items in the current PR body (e.g., "Gmail send (PR 2d), HTML email (PR 2d), launchd auto-trigger (PR 2d)..."). This makes scope boundaries reviewable, preempts "where's X?" review questions, and creates an explicit checklist for the follow-up PR. Generalizable to any feature that ships in multiple parts. <!-- Source: post-mortem, family-digest #12, 2026-04-22 -->
- **For "the feature is silent / shows nothing" bugs, read the gate/threshold logic in code and confirm the inputs' true scope BEFORE choosing a fix — the bug is often presentational, and recalibrating the gate would be the wrong fix.** baby-name-picker #197: a user past the 20-comparison floor with eclectic taste got a silent "keep comparing" with no number and no read. The tempting fix is to loosen the confidence gate so eclectic taste "passes". Reading the classifier first showed the gate was CORRECT — it deliberately forbids the Free Spirit (eclectic) fallback from ever being "confident" — so the real defect was that the screen had a read it already held (the leading archetype) and threw it away, falling through to a countdown-less teaser. The fix was purely presentational: a `profileState` discriminator (`needs_more`/`tentative`/`confident`) that surfaces the leading archetype as a tentative read, with the gate/threshold untouched and a regression test pinning "eclectic stays non-confident". The diagnosis also disconfirmed a plausible-but-wrong hypothesis by reading the data source — `totalComparisons` is GLOBAL across decks (raw COUNT, no gender filter), not per-deck, so "they just haven't compared enough in THIS deck" was ruled out before any code changed. Reusable rule: when a feature renders empty/dead, (1) read the actual gate/threshold that decides the empty branch, (2) confirm the scope of every input it reads (global vs scoped, per-deck vs total) against the source, (3) ask "is the gate wrong, or is the presentation discarding a value the gate already produced?" — recalibrating a correct gate to paper over a presentation bug is a classic wrong fix. <!-- Source: post-mortem, baby-name-picker #197, 2026-06-17 -->

## Follow-Up Discipline

- Post-push findings should become their own focused follow-up PR rather than being deferred to a tracker or bundled into the next feature.
- Multi-finding follow-up PRs work just as well as single-finding ones; fix all post-mortem findings atomically.
- Infrastructure gaps identified in post-mortems should be addressed in dedicated, same-day tooling PRs.
- **Recommendation drift across consecutive PRs is the dominant post-mortem failure mode.** When a post-mortem recommendation does not land before the next PR ships in the same project, escalate it from prose recommendation to a project artifact (PR template file at `.github/PULL_REQUEST_TEMPLATE.md`, CI workflow file, lint rule, hook). Two consecutive PRs that ignore the same recommendation indicate the recommendation lives in the wrong place — move it from a markdown file to a file the toolchain enforces. **Three consecutive PRs ignoring the same recommendation (confirmed in family-digest #1 → #3 → #4: PR template, CodeRabbit CLI, CI configuration) means the next post-mortem must DEMAND artifact conversion as the first recommendation rather than restating the prose recommendation a fourth time.** **Confirmed across four consecutive PRs in family-digest #1 → #3 → #4 → #12: prose recommendations alone never land — only committed artifacts (template files, workflows, hooks, lint rules) close the loop.** When the open-to-merge window is also short (PR #12: ~18 minutes), CI workflows must additionally be configured as required checks, otherwise a fast self-merge bypasses them even when they exist. <!-- Source: post-mortem, family-digest #3, 2026-04-22; strengthened family-digest #4, 2026-04-22; strengthened family-digest #12, 2026-04-22 -->
- **The recurring "no CI gate" recommendation finally LANDED in baby-name-picker #150 — and the gate validated itself on its first run by catching its own RED.** The "red main can persist silently with no CI" recommendation had drifted across four consecutive post-mortems (#87/#126/#141/#149) plus the name-family-tree finisher (line 28). #150 converted it to a committed artifact: `.github/workflows/ci.yml` (Node 20, `npm ci` → `typecheck` → `lint` → `jest --ci --watchAll=false`), a new `typecheck` npm script, and a tsconfig `web` exclude. Per the line-37 escalation rule, this is the correct terminal move — prose became a toolchain-enforced file. Note: the gate is on `pull_request`/`push` but is NOT yet a *required* check, so a fast self-merge could still bypass a RED (the line-37 family-digest #12 caveat still applies here — follow up by marking the check required in branch protection). **Repeated in plush-press #24 (2026-06-11): the CI recommendation again drifted across exactly three consecutive post-mortems (#15, #16, #23) before landing as a config-only artifact PR — a single `.github/workflows/ci.yml` (Node 20, scoped to `studio/`, `npm ci` → typecheck → lint → build → test, npm cache, per-ref concurrency cancellation), green on its own first run. Pattern now confirmed in two projects: the drift count to artifact conversion is consistently 3-4 post-mortems; cite this entry at drift #1 to land it sooner. Same residual caveat applies — the check is not yet *required* in branch protection, and the PR self-merged in under 6 minutes, exactly the window a required check exists to close.** <!-- Source: post-mortem, baby-name-picker #150, 2026-06-02; strengthened plush-press #24, 2026-06-11 -->
- **"Verified locally" ≠ "verified on a clean install" — env-dependent transitive deps hide until a pristine environment runs.** baby-name-picker #150 (the CI-gate PR itself) was caught RED by its own gate on the first run: `jest.config.ts` needs `ts-node` to parse, which was present transitively in the local dev `node_modules` but NOT installed by a clean `npm ci`, so the author's local verification (even after running `npm ci`) passed while CI failed with `'ts-node' is required for the TypeScript configuration files`. The pre-merge iteration count was 2: commit 1 added the workflow, run 1 failed, commit 2 added `ts-node` as an explicit `devDependency`, run 2 went green. Lesson: a local `node_modules` accreted from prior installs is NOT a clean install — before declaring a build/test command green for CI, verify against a pristine tree (`rm -rf node_modules && npm ci`). TypeScript config files (`jest.config.ts`, `*.config.ts`) consumed by tools that shell out to `ts-node` are the classic trap: the tool declares `ts-node` an optional peer, so it only surfaces when something else in the tree happens to pull it in. Declare such loaders as explicit `devDependencies`, never rely on transitive presence. This is also the strongest possible argument FOR the CI gate: the gate's value was proven on its own first run by catching a defect that two rounds of local verification missed. <!-- Source: post-mortem, baby-name-picker #150, 2026-06-02 -->
- **PRs that introduce or modify paid external API calls require a "Performance & Cost Impact" section** in the PR body, even when planning quality is otherwise complete. Cover: $/invocation, expected invocations per period, rate-limit posture, and failure mode (throw vs partial content vs cached fallback). The first PR adding a paid API is the one most likely to skip this, because the cost envelope feels small at single-user scale — capture it anyway as the baseline for future cost-regression detection. <!-- Source: post-mortem, family-digest #3, 2026-04-22 -->

## Scope Decisions

- For interface extractions under 10 lines that match established project conventions, include them in the original PR; reserve "scope creep" for behavioral additions.
- Never bundle tooling setup (lint configs, auto-fixes) with feature PRs; create a separate tooling PR.
- When identical logic exists in 2+ files and is under ~30 lines, extract to a shared utility instead of adding "keep-in-sync" comments.
- When a tangential automation idea surfaces during a focused PR, defer it to a separate PR.
- **Ship the `.gitignore` guard for a secrets directory BEFORE the first key exists, as its own config micro-PR.** The ignore rule is the only gate that works by construction (no reliance on review catching a staged key); landing it pre-creation means there is never a window where `git add .` could stage credentials. Verify with `git check-ignore <path>` on the branch as the PR's test. <!-- Source: post-mortem, plush-press #13, 2026-06-10 -->
- **For a derived-signal feature (a new score/column feeding new logic), split into a data PR then a logic PR.** baby-name-picker #169/#170 cleanly split a phonetic-texture taste signal: PR A (#169) shipped ONLY the build-time scorer + the `sound_softness` column for all 1311 names and touched zero classifier code; PR B (#170) wired that column into the taste classifier. Benefits proven here: (a) each PR stayed small and single-concept (A: +1929 data/script LOC mostly generated; B: +272 LOC of actual logic), (b) A's correctness (band separation of scores) was reviewable in isolation without classifier noise, (c) B could calibrate its thresholds against A's ALREADY-SHIPPED real distribution rather than a hypothetical one, (d) zero post-merge fixes on either. The split test: if the new logic's thresholds/behavior depend on the empirical distribution of the new data, ship the data first so the logic PR calibrates against reality. Each PR must still independently pass CI (A added its column + tests; B added classifier tests). <!-- Source: post-mortem, baby-name-picker #169 + #170, 2026-06-02 -->
- **Calibrate heuristic thresholds against the REAL shipped distribution, not a guessed value.** When a feature gates on a numeric threshold for a heuristic signal (a "softness floor," a "confidence floor," a similarity cutoff), compute the threshold from the actual catalog/dataset percentiles rather than picking a round number. baby-name-picker #170 set `SOFT_FLOOR=0.75` deliberately between the catalog's median (0.66) and p75 (0.82) and `SOFT_DELTA_FLOOR=0.12` to require a genuine preference rather than a mild lean — both named, tunable constants justified by the real distribution shipped in #169. A guessed threshold either over-fires (catches noise) or under-fires (never triggers); a percentile-anchored one is defensible and re-tunable. This is only possible when the data exists first (see the data-then-logic split above). <!-- Source: post-mortem, baby-name-picker #170, 2026-06-02 -->
- **A pure copy-rename can ride along in a feature PR when it is the same vocabulary the feature touches; a copy-rename of an UNRELATED surface should be its own PR.** #148 bundled three changes — dual-pronunciation display (feature), 22 pronunciation data corrections (data), and the per-name tag rename EUPHONY→INVENTED (copy). The display + data pair is one concept (correct pronunciations + how to show them) and belongs together. The tag rename is arguably separable, but it rode along cleanly because (a) it was 1-token-per-file across 5 already-touched-or-adjacent render surfaces, (b) it carried its own branch-test updates, and (c) the critic explicitly verified rename scope (the brand wordmark on the Euphony *invitation* card was deliberately NOT renamed). The right test for "can this copy change ride along?": is it a mechanical find-replace within surfaces the PR is already reasoning about, with a clear keep/change boundary the critic can verify? If yes, bundling avoids a near-zero-value second PR. If the rename touches surfaces unrelated to the feature, split it. Net call for #148: bundling was acceptable; the only cost was 3 stale "EUPHONY" code comments left as known cosmetic nits. <!-- Source: post-mortem, baby-name-picker #148, 2026-06-01 -->
- **Annotate `Steps skipped:` even on trivial fixes.** Single-line CSS or copy fixes (<=3 LOC, 1 file) often skip Local Review and adversarial review legitimately. Without an explicit `Steps skipped: <list> -- reason: <rationale>` line in the PR body, post-mortems can't distinguish intentional skips from process drift. Always include the line, even if the reason is 'trivial CSS leading fix, no logic paths.' **CONVERSE confirmed in baby-name-picker #172 (2026-06-02, +10/-6, 1 file): a 2-line style change (`detailCard maxHeight:"100%"→flex:1`, `detailScroll flexShrink:1→flex:1`) ran the FULL orchestrator team + focused critic + CI loop and shipped clean (critic PASS, 0 findings, 925 jest pass, CI green, 0 post-merge fixes) — but its PR body had NO `Steps skipped:` line, NO `## Local Review` section, and NO `## Step Timing` section, so the post-mortem had to reconstruct review provenance entirely from the orchestrator's hand-off narrative. The lesson holds in both directions: whether a trivial fix takes the heavy lane OR a light lane, the PR body must record WHICH lane it took (`Steps skipped:` line) so the metric pipeline isn't blind. Proportionality observation (not yet a rule): for a pure presentational tweak the heavy team+critic loop is arguably more ceremony than the diff warrants — but its marginal cost here was tiny (~3 min open-to-merge) and the critic added real value by correctly SEPARATING code-verifiable claims (the `flex:1` mechanics, scope containment, unchanged dismiss threshold — all jest/tsc-checkable) from the one device-confirm item ("does `flex:1` actually fill, and does a short-content name look right" — unverifiable by jest, needs an on-device eyeball). That code-verifiable-vs-device-confirm split is the right critic posture for layout PRs (cf. orchestrator-protocol line 50 "Default to Snapshot for UI polish" and the routed-screen visual-gate degradation at line 218); a lighter lane would have to preserve it. <!-- Source: post-mortem, second-brain #603, 2026-05-06; converse-confirmed baby-name-picker #172, 2026-06-02 -->
- **Rule a sibling-code bug fix INTO the feature PR when the new feature makes the latent bug user-reachable; defer it only if it stays latent.** plush-press #25: the merged PR-1c `listScenes` treated plain docs (`backdrops/scene-prompts.md`, `shared scenes/README.md`) as scenes — harmless while the API had no UI, but the new roster rendered them as clickable, GENERATABLE scenes (a paid-API action on a non-scene). The fresh-context critic explicitly ruled the front-matter filter into the PR over single-concern purity: shipping the UI without it ships a broken user surface, and the fix's correctness was only observable through the UI under review anyway. The test: "does THIS PR's feature turn the sibling bug from latent into user-facing?" If yes, the fix rides along (with its own tests — #25 added junk-doc fixtures); if the bug stays unreachable, defer to its own PR per the usual single-concern rule. <!-- Source: post-mortem, plush-press #25, 2026-06-11 -->
## Adversarial Review Gaps

### Critic Blind Spots
- **Test-discovery colocation bias.** Critic agents default to assuming Jest/Vitest colocated `*.test.ts` next to source files and report "no tests exist" when projects use the alternative `src/__tests__/<area>/foo.test.ts` mirror-tree, `tests/` directory, language-specific conventions (Go `*_test.go`, Rust `tests/`, pytest `tests/` dir), or any non-colocated layout. Before claiming any test gap, the critic must read the project's test-runner config (`vitest.config.*`, `jest.config.*`, `pyproject.toml`, etc.) AND `find . -type d \( -name __tests__ -o -name tests -o -name test -o -name spec \) -not -path '*/node_modules/*'` to enumerate the actual test layout. The orchestrator-protocol "Critic's Fresh Context" section now mandates this. <!-- Source: post-mortem, family-digest #4, 2026-04-22 -->
- **Critic false-negatives that survive only because the orchestrator has ground-truth project knowledge are a fragile gate.** When the orchestrator overrules a critic finding based on its own familiarity with the codebase (rather than the critic re-verifying), capture the missed check as an explicit critic-prompt requirement. Otherwise the same blind spot will recur the next time a less-familiar orchestrator inherits the team. <!-- Source: post-mortem, family-digest #4, 2026-04-22 -->

- **Mechanical-integrity verification is NOT correctness verification — on data/content PRs the critic must spot-check SEMANTICS against sources, not just structure.** baby-name-picker #87 ("audit batch 1") shipped with a fresh-context critic verdict that read as a clean SHIP: it verified the rebuilt `seed.db` was byte-faithful to the SQL, 0 null `origins_json`, 0 invalid JSON, no field-shift, and the Indic sweep didn't over-correct long vowels — then flagged exactly 2 judgment items (Iniya, Zhi), both resolved. Every one of those checks is STRUCTURAL. None asked "is the new etymology actually *true*?" So 11 semantic regressions sailed through (real origins stripped, homophone glosses injected — see the flattened-view entry in Data Quality) and required three remediation PRs (#89/#90/#92). The false confidence was acute *because* the critic looked thorough on integrity. Rule: when a PR changes data or content (not control flow), a structural/mechanical pass is necessary but NOT sufficient — the critic must additionally (a) sample a handful of changed rows and verify each new value against the cited external source, and (b) treat "the build is reproducible and the JSON is valid" as table-stakes, never as the correctness gate. Phrase the critic's mandate as "verify the changes are RIGHT," not "verify the artifact is well-formed." **CONFIRMED APPLIED in baby-name-picker #126 (2026-05-30): a user-reported wrong pronunciation (Nandhini `nahn-DHI-nee`) was fixed by FIRST source-grounding the correction (Wiktionary IPA `/ˈnɑn.dɪ.niː/`), and the critic INDEPENDENTLY re-fetched Wiktionary to corroborate the front-stress claim before SHIP (explicitly noting and weighing a dissenting aggregator snippet rather than rubber-stamping), plus a two-sided guard test pinning the new values and forbidding the old. This is the #87 anti-pattern inverted: semantic correctness was the review gate, mechanical integrity was table-stakes.** **CONFIRMED APPLIED AGAIN, at additive scale, in baby-name-picker #141 (2026-06-01, +158/-6, 1240→1290 names): 50 generator-surfaced candidates were salvaged into the catalog only after each was independently verified for (a) a genuine real-name attestation, (b) an accurate sourced meaning, and (c) its TRUE origin — explicitly corrected away from the generator's guessed sound-world (Maewyn→Welsh, Mehra→Persian, Senya→Russian, Xanthia→Greek, Caelina→Latin), which is exactly the "is this etymology actually true?" question #87 skipped. 34 weaker candidates were DROPPED for failing attestation/meaning — i.e. a high-recall-then-verify-and-drop gate, the additive analogue of #87's needed correctness pass. The critic verified source-JSON↔SQL byte-for-byte (mechanical, table-stakes) AND spot-checked meanings for accuracy (semantic, the gate). ### Systemic Execution Gap
- The problem is not checklist completeness but mechanical execution. Run grep patterns mechanically; require grep-based evidence per item.
- When adversarial review identifies an issue, the default is to FIX it; "low priority" is not a valid skip reason.
- When it identifies duplication, extract; do not document it with "keep-in-sync" comments.
- Claims of 100% execution with 0% catch rate indicate performative review.
- If CodeRabbit was deferred/skipped, steps-skipped must reflect that.
- The internal critic (Step 4b) catches real bugs the checklist misses for React UI PRs.

### Review Completeness
- When fixing JSDoc, audit ALL doc comments in the changed file.
- When adapting code from another component, re-run the full checklist against the NEW instance.
- Verify the FIX is complete, not just that the issue was acknowledged.
- When removing an entity, grep docs for stale count references and universal claims.

### React-Specific Gaps
- React state management is the #1 blind spot: render-phase setState, instance-unique IDs, duplicate keys, stale async guards.
- For useMemo wrapping Date computations, verify a day-based key is in the dependency array.
- Cross-reference new async hooks against sibling patterns (e.g., unmount guards).
- When IntersectionObserver/MutationObserver combines with React state guards, review the full interaction matrix.
- Module-level caches in React hooks must be keyed by user identity.
- Replace `setTimeout` for async state clearing with `await refetch()`.

### Test Gaps
- Adversarial review is weak on test code quality (mock correctness, assertion completeness, fixture consistency).
- Trace each test mock to the production code path it simulates.
- Verify tests assert behavior (callback called, state changed), not just rendering.
- Verify tests of validation functions cover ALL allowed AND disallowed inputs.
- When updating tests for behavioral changes, verify the test asserts NEW behavior, not old behavior with a swapped value.
- Verify test cleanup in `afterEach` when tests mutate `process.env.*`.
- Verify all catch/error branches in route handlers have test cases.
- Extracted private helpers need dedicated contract tests.

### Correctness Gaps
- `new Date(year, month-1, day)` silently normalizes invalid dates; verify components match after construction.
- Verify `slice_length + suffix_length <= limit` for truncation.
- Review format helper return values against call sites to prevent compound wrapping.
- `SELECT COUNT(*) ... INSERT` in transactions still allows TOCTOU races; use advisory locks.
- When removing a type union value with migration-gated cleanup, defensively filter queries by supported types.
- When fire-and-forget returns a fallback, callers must compare against prior state before side effects.
- When adding a new terminal state, verify ALL inter-terminal transitions for derived field consistency.
- For date-scoped endpoints, sweep every `new Date()`, `toISOString()`, and SQL date filter for timezone issues.
- Server routes with multiple response shapes need union return types on the client.

### UI/CSS Gaps

- When entering any interactive mode, reset competing mode states.
- Portal/popover components must reposition on scroll/resize or close on scroll.
- Optimistic reverts need user-facing error feedback.
- Telegram callback handlers must clear inline keyboards after handling.

## Automation Opportunities

- **Guard fetch(variable) in server routes.** When server-side code fetches a DB- or user-provided path, the value may be relative (e.g. seeded /inspo/foo.png) and fetch() has no base URL — all requests silently 404. Either resolve against request.nextUrl.origin for public/ assets, or validate the path is absolute before fetch. - **Integration test with seeded data shape, not just uploaded data shape.** PR #18 shipped a zip-download feature that worked for absolute Supabase URLs (uploaded photos) but broke for 354 seeded photos with relative paths. The data shape that dominates the table was never tested. Gate: any feature reading from a table with both seeded and user-created rows must be tested against at least one of each. <!-- Source: post-mortem, remodel-hq #19, 2026-04-21 -->
- UTC suffix enforcement: use Tier 0 grep checks in the adversarial review (deferred CI-level lint).
- Run Biome lint before push to catch a11y issues like `noStaticElementInteractions`.
- Add Stylelint to local pre-PR checks for web projects; compose into the main `npm run lint` script.
- Pin devDependency versions consistently (all exact or all caret); mixed strategies generate review noise.
- A missing .coderabbit.yaml drops shift-left rate from ~80% to ~33%; add `profile: "assertive"` with project-specific `path_instructions`.
- **Auto-fixers can silently break test hoisting — always re-run the FULL test suite after `--fix`, and scope import-ordering rules off test files.** Introducing ESLint to baby-name-picker (#86), an `eslint --fix` reordered imports past `jest.mock()` factory blocks in 14 test files, breaking 2 suites: Jest hoists `jest.mock()` calls above imports, and the mock factories reference variables/imports declared below them, so an alphabetical/`import/first` reorder that moves real imports above the mock factory changes evaluation order and the factories blow up (or mock the wrong module). Two reusable rules for introducing ANY linter/formatter/codemod to a project: (1) **a clean `--fix` exit is not proof of correctness — re-run the full test suite after every auto-fix pass and diff the result**, because formatters optimize for source-text rules and are blind to runtime hoisting/evaluation-order semantics (Jest mock hoisting, decorator order, side-effecting import order, polyfill-before-use); (2) **scope import-ordering / import-placement rules OFF test files** (or any file that relies on hoisting), since the "imports must come first" invariant is intentionally violated by the mock-factory pattern. - **CodeRabbit CLI fails with "Payload too large" on diffs containing multi-MB binary files — keep binary/art assets in separate commits or PRs from text changes.** plush-press #3 (docs-only restructure) hit a deterministic CodeRabbit CLI failure on both attempts because the diff included multi-MB PNG `git mv` renames; CLI v0.5.3 has no flag to scope the review to text files only. - **Adversarial review marker is keyed by `$CWD`, not git-root.** When the orchestrator writes the marker for the main-repo path but the push fires from inside a `.claude/worktrees/<name>` subdir, the hook re-hashes the worktree path and blocks the push. - **Rasterize app icons from an SVG logomark with headless Chromium (Playwright) when no native SVG rasterizer is installed.** baby-name-picker #195 needed to regenerate 5 icon assets (iOS `icon.png`, splash, Android adaptive foreground + monochrome, favicon, plus the web favicon) from an updated SVG monogram, but the machine had no `rsvg-convert`, ImageMagick, or Pillow. ## Iteration Velocity

- Full local review loop achieves 0% fix-up ratio for well-planned PRs under 600 LOC.
- **User-perceived-latency feedback is a process smell, not a feature request.** When the user reports "this feels slow" on a write path (vote, favorite, comment) and the fix is a one-line optimistic-update swap, the root cause is that the write-path hook (`useAtelierData`, `useInspoFavorites`, `useInspoNotes`) did not default to optimistic updates. PR #83: 1 fix commit ("optimistic vote/favorite updates") could have been preempted if the hook factory enforced optimistic-by-default with an explicit `pessimistic: true` opt-out. Treat repeated "feels slow" feedback across multiple write paths as a hook-factory design gap, not per-call optimization. <!-- Source: post-mortem, remodel-hq #83, 2026-05-15 -->
- **Surface-misidentification during iteration is an avoidable rework category.** When user feedback references a feature area ("the lightbox") but actually concerns a sibling surface (the card grid), each misidentified round costs ~1 implementer cycle. Mitigations: (1) plan-time surface table (see Planning Discipline), (2) ask the user "which screen -- card grid or lightbox?" before dispatching the implementer, (3) capture a screenshot in the feedback channel. PR #83 lost 2 implementer rounds to this. <!-- Source: post-mortem, remodel-hq #83, 2026-05-15 -->
- 0% fix-up ratio can mask ignored CHANGES_REQUESTED findings; always verify they were addressed.
- Copy-and-adapt is higher-risk for review quality than greenfield.
- Marker/infrastructure commits inflate fix-up ratio; exclude from calculations.
- Net-deletion refactor PRs have lowest review friction; custom UI with portals has highest.
- Scaffolding PRs benefit from sequential additive commits for high shift-left rates.
- Copilot "suppressed low-confidence" findings can be 100% legitimate; always read them.
- Fix commits touching React state cause cascading reviews; budget extra time.
- Test LOC should be factored into PR sizing at ~1.5x feature LOC.
- CSS theme PRs need automated WCAG contrast checks, not manual "verified" claims.
- When CodeRabbit CLI times out, retry with backoff (3 attempts, 2-min wait); add hard timeout (`timeout 600`). **Strengthened: the CLI can also hang INDEFINITELY with zero output rather than erroring — plush-press #23 watched it for 52 minutes producing nothing before killing it manually. ## Data Quality / Audits

- **Brand-rename safety when the brand string collides with domain data: carve out the data surfaces in the brief and require grep-proof before push.** baby-name-picker #195 renamed the app Sona→Ria, but "Sona" is also a real Hindi baby name living in the catalog (`scripts/seed-data.sql`, the rebuilt binary `assets/seed.db`, and `seed-additions.test.ts`). A blind find/replace would have silently corrupted product data on a "data is the product" app. The change shipped clean because the brief **explicitly enumerated the keep-vs-change boundary** (rename every *brand* surface; preserve the *catalog* name) and the critic verified it with two greps: `grep "Sona"` must still hit the seed/test data (proof of preservation) AND must NOT hit any active brand surface (proof of completeness). **Reusable recipe for any rename where the token also appears as domain data:** (1) list the data surfaces that must NOT change in the spawn brief; (2) require a paired grep at review — one asserting the data token survives, one asserting it's gone from brand surfaces; (3) prefer routing brand strings through a single source (here `web/lib/brand.ts` `BRAND_NAME`) so the brand surface is a small, greppable set distinct from the data. This is the same keep/change-boundary test as the #148 copy-rename ride-along, sharpened for the case where the cost of getting the boundary wrong is corrupted user-facing data, not just stale comments. <!-- Source: post-mortem, baby-name-picker #195, 2026-06-16 -->

- **Multi-agent, web-grounded, adversarially-verified audit is the reusable pattern for data-quality at scale — and the antidote to the "audit on a flattened view shipped wrong data" failure (#87).** baby-name-picker's native-pronunciation initiative built a harness that researched ~465 names and is the model to copy whenever a large bundled dataset needs correcting: (1) **source-grounded, never model-opinion** — every proposed change is backed by an external authority (Wiktionary IPA / Behind the Name / Forvo / Wikipedia); a change with no citable source is NOT made; (2) **adversarial verification per change** — each proposed change goes to an *independent skeptic* agent whose job is to refute it, and only un-refutable changes survive as confirmed corrections; (3) **conservative `uncertain` flag on source disagreement** — where authorities conflict, the harness does NOT guess, it flags the name and routes it to a human; (4) **human-in-the-loop gate** — an interactive review tool (approve/reject/keep/change + JSON export) ratifies decisions before anything touches the seed source; (5) **critic verifies the SHIPPED structured artifact, not a flattened view** — "exactly N rows changed in column X (matching the N ids), every other column byte-identical, row count unchanged." This is the structural opposite of #87, which trusted a derived view + model judgment and shipped wrong etymology data silently. <!-- Source: post-mortem, baby-name-picker native-pronunciation initiative (#92/#95/#98/#110/#111/#113), 2026-05-29 -->
- **A standing "merge it" / pre-authorization authorizes the MECHANISM, not any specific change the mechanism emits — automated applies must be checked against known prior human decisions before applying.** In the pronunciation sweep the user pre-authorized "merge batch 4 when done"; batch 4's audit mechanically proposed reverting **Esha `EE-shah` → `AY-shah`** — re-introducing the *exact* user-reported bug that PR #92 had fixed earlier the same day. The audit wasn't wrong by its own rules; it had no memory of the human decision. The orchestrator caught it only because it recognized the name from session history, excluded it, and added an id-based regression test. Lesson: **even verified, source-grounded, human-pre-approved automated changes must diff against the set of recorded prior decisions and hard-fail on a contradiction.** Pre-authorization must be scoped ("apply the batch EXCEPT where it contradicts a recorded decision"). Don't let the safety net depend on the same agent happening to hold the prior session in context. Concrete fix: maintain a machine-readable **decision ledger** (id + value + do-not-revert + PR ref); any apply step diffs proposed changes against it and blocks on conflict. The id-based regression test that guarded Esha is the first ledger row. Generalizes to ANY pre-authorized automated-apply pipeline (data sweeps, codemods, dependency bumps). <!-- Source: post-mortem, baby-name-picker native-pronunciation initiative (#111 vs #92), 2026-05-29 -->
- **When an audit produces (old, new) pairs and BOTH values are meaningful to a user, model the correction as enrichment (add a column / link), not a destructive mutation.** Instead of overwriting anglicized pronunciations with native ones and discarding the originals, the user kept both: a new `pronunciation_anglicized` column preserved the originals (back-filling the ones already overwritten) and the detail view shows NATIVE (canonical) + ANGLICIZED ("the form you'll usually hear it"). ## PR Sizing

- Shift-left effectiveness degrades above ~600 LOC (67-100% under, 14-59% over); split into 2-3 PRs.
- PRs over 1200 LOC need 3+ review rounds regardless of local review quality.
- **A genuinely-atomic feature is the legitimate exception to the 600-LOC cap — but it must pay for the exception with a frozen artifact + a type that forces total consumer handling.** Euphony shipped at ~2869 LOC in 1 review round (critic found 1 should-fix, fixed pre-push) with 0 post-merge fixes. It held together because the diff was almost-uncuttable along behavioral lines (a `DisplayName = Name | InventedName` discriminated union threads through deck, Elo, NameCard, favorites, top-picks, and taste analytics — splitting it would have shipped a type the codebase couldn't compile against half-way). What made the large PR safe was NOT its size but two structural choices: (1) the bulk of the +2715 was a bundled JSON data asset + its build script, not hand-written logic; (2) the union made the compiler enumerate every consumer, converting "did we handle the new case everywhere?" from a manual review burden into a build error. Before granting a >600-LOC exception, demand both: most of the bulk is data/generated, and a type makes new-case omissions un-compilable. Absent those, split. <!-- Source: post-mortem, baby-name-picker #146, 2026-06-01 -->
- **Scaffold variant of the >600-LOC exception: exclude generated lockfiles from LOC accounting.** plush-press #15 read as +8769 but 7154 of it was the generated `package-lock.json`; the hand-written diff was ~1.6k LOC (engine ~726, tests ~483, config/docs/seeds the rest). The safety payment was byte-replay tests (golden-master reproduction of the proven prompts) instead of a totality-forcing type — 1 review round, 0 escapes. When judging PR size, count hand-written LOC; when the bulk is a scaffold + lockfile, demand a strong replay/round-trip test suite as the exception's payment. <!-- Source: post-mortem, plush-press #15, 2026-06-10 -->
- Reinforced by plush-press #16 (+2614/-182, 1 review round, 15/15 findings fixed pre-push, 0 post-push): the bulk was new isolated modules (providers/, routing, chain state) behind a typed `ImageProvider` interface with per-candidate result types and an exhaustive-never routing switch — the same "type forces total consumer handling" structure that made the #146 exception safe. <!-- Source: post-mortem, plush-press #16, 2026-06-10 -->
- **API-surface variant of the >600-LOC exception: a coherent route surface with thin handlers and concentrated services can ship whole — the payment is per-entry-point tests + a typed error spine + a fresh-context critic.** plush-press #23 (+2298, ~1080 hand-written LOC, 10 routes) exceeded the cap because the studio API is one wiring layer: splitting it would have shipped routes whose siblings (generate→lock, scenes→render) couldn't be exercised. It held safe in 1 critic round (0 must-fix / 3 should-fix / 6 nits, all fixed pre-push, 0 post-push) via three structural payments: (1) routes stayed thin — all flow logic lived in 3 lib services, so the review surface was services + a validation module, not 10 bespoke handlers; (2) a typed `CodedError` spine mapped every error class to an HTTP status in ONE place, making "did every route handle every failure?" a single-file check (the critic's top finding was precisely the spot still doing message sniffing instead); (3) every PR-body-enumerated entry point (fresh launch, resume, missing key, typo'd ids, partial candidate failure, duplicate, bounds) carried a named test — 60 new tests, zero real API calls. When granting an API-surface exception, demand all three; absent thin-routes + single error spine, split by route group. <!-- Source: post-mortem, plush-press #23, 2026-06-10 -->
- **Feature-level signal: a multi-PR studio feature ships cleanest as vertical waves (data → draft → ops → UI capstone), each its own self-merged PR with a critic lens MATCHED to that wave's dominant risk — and the capstone reuses, not rebuilds, the proven sibling loop.** The plush-press Characters studio completed across exactly four waves: #34 data layer (list/create/update/routes), #33 Claude-vision draft route, #35 generate/tune/lock ops, #37 the 01 Characters UI capstone — plus #36, a shared upload endpoint reused by both the scene and character paths. Cross-PR metrics for the arc: every wave 1 review round, 0 post-merge fixes, 0 GitHub-review comments, CI green; total escaped findings across the whole studio = 0. Three reusable signals: (1) **Matched critic lens per wave.** The data/ops waves (#34/#35) drew correctness critics that each caught the SAME recurring class (dir-slug ≠ bible-filename, hit 3×, masked by symmetric fixtures — see the dir-slug entry); the upload wave (#36) drew a security-focused critic that verified write-confinement at real runtime; the UI capstone (#37) drew a real-data/render critic that caught the HEIC default-path defect. The lens that fits the wave's risk caught the wave's one real issue each time. (2) **The capstone reuses the proven loop rather than re-deriving it.** #37's UI is explicitly "mirrors the 02 Scenes loop," and it generalized the EXISTING `GeneratePanel`/`TunePanel` via a discriminated `context` prop with the scene path kept byte-identical — so the capstone's regression risk was discharged by a byte-identical-existing-path proof, not by re-testing the whole loop (a cheap, durable way to extend a shared component to a 2nd context; pairs with the #28/#31 N-contexts rule). (3) **The bug that survived to the capstone was a real-data one, not a logic one** — the backend waves were logic-clean; the only UI-wave finding was that the operator's actual data format (HEIC) hit an unservable surface. Net: vertical waves + matched lenses + reuse-over-rebuild produced a 5-PR feature with zero post-merge churn; the standing watch-item for the NEXT such feature is the operator-real-data render check at the UI wave, since that is the one class the backend lenses structurally cannot see. <!-- Source: post-mortem, plush-press #36 + #37 (Characters studio capstone), 2026-06-16 -->

## Process Rule Enforcement

- **When a critic commits a post-PASS fix, the adversarial-review marker must be refreshed for the NEW head before push.** The push hook (`require-adversarial-review.sh`) keys the marker to `md5(worktree-path)` and verifies it matches `HEAD`. If the critic returns PASS, then commits its own one-line fix on top, `HEAD` advances past the reviewed commit and the marker no longer matches — the hook correctly blocks the push. In baby-name-picker #195 the critic's footer-copyright fix (`© Ria` → `© Keya LLC`) landed after its PASS, stranding the marker. Resolution: the orchestrator self-eyeballed the trivial one-line delta (the "self-eyeball" tier of the Critic Round Tiers) and re-wrote the marker keyed to the new HEAD. **Reusable fix: make the critic write/refresh the review marker as the LAST step of any fix it commits, not at PASS time — so the marker always tracks the actual reviewed head.** Until that's automated, the orchestrator must re-issue the marker after any post-PASS critic commit. **RECURRED in baby-name-picker #197 (2026-06-17): the critic's contained fix (filter dominance-asserting tells out of the open-ended Free Spirit read + 2 regression tests) was committed AFTER its PASS, again stranding the marker; the orchestrator self-eyeballed the contained delta and re-wrote the marker. Two consecutive baby-name-picker PRs (#195, #197) now confirm this is structural, not incidental — the prose "re-issue manually" mitigation is being followed but the root cause (critic writes the marker at PASS time, then commits on top) keeps recurring. Per the line-221 escalation rule, prioritize the automated fix: have the critic refresh the marker as the FINAL action of any post-PASS commit.** <!-- Source: post-mortem, baby-name-picker #195, 2026-06-16; recurred #197, 2026-06-17 -->

- **Promote prose recommendations to enforceable artifacts after 3 consecutive violations.** When the same prose process rule is violated in 3+ PRs in a row (e.g., missing Local Review / Steps skipped / Perf & Cost annotations across #603, #606, #609), escalate from prose to artifact (PR template, lint rule, hook). Prose alone is insufficient at violation rate >2/window. <!-- Source: post-mortem, second-brain #614, 2026-05-06 -->

## Stale-Base Detection

- **Detect stale base before push, not at critic-time.** When `main` advances during the implementation window, the resulting spurious diff is currently caught only by the critic agent's review pass. Two occurrences in one session (#614 and prior) indicate the manual catch path is leaky. Add a Tier 0 pre-push check: `git fetch && [ "$(git merge-base HEAD origin/main)" = "$(git rev-parse origin/main)" ]`.
- **Parallel features touching the same low-level files will conflict at merge — sequence them or expect a resolution + re-test pass.** #146 (Euphony) and #145 (`spellings_json`) developed in parallel and both edited `src/types/name.ts`, `src/db/queries.ts`, and `src/db/__tests__/queries.test.ts`; #145 merged first, so #146 absorbed a 3-file conflict resolved in its own merge commit (both features coexist, test count rose to 833). The conflict was benign here only because both changes were additive to the same files. When two in-flight branches are known to touch shared schema/type/query files, either land them strictly sequentially (rebase the second after the first merges) or budget for a conflict-resolution + full-suite re-run before merging the second. The pre-push stale-base check above would have surfaced this before the critic pass. <!-- Source: post-mortem, baby-name-picker #146 vs #145, 2026-06-01 --> <!-- Source: post-mortem, second-brain #614, 2026-05-06 -->
- **Catalog/seed PRs are a recurring serial-collision hotspot — serialize them, or expect rebuild+rebase as the standard resolution.** Every PR that adds or edits names in baby-name-picker touches the same fixed set: the rebuilt binary `assets/seed.db`, the source `scripts/seed-data.sql`, the catalog count-constants embedded in test fixtures (`src/db/__tests__/seed-*.test.ts`), and the coverage baseline JSON (`docs/research/seed-coverage-baseline.json`). Because that set is identical for *any* catalog change, two catalog PRs open at once WILL collide — this has now recurred across **#149, #155, and the Option-C/#163 stale-base note** (#155 sat open ~15h while #160-162 + #166/Anavi advanced main, forcing a merge-up + seed.db rebuild + id renumber 1320-1322 before it could land; #163 likewise needed a merge-up off a base stale behind #161). The collision is structural, not incidental: a generated SQLite binary cannot be hand-merged, and the count-constants must be recomputed against the *final* catalog size. **Reusable mitigations, in priority order:** (1) **Serialize catalog PRs** — treat the catalog as a single-writer resource; open the next catalog PR only after the prior one merges, so each branches off a current main and never collides. (2) **If parallel is unavoidable, merge catalog PRs promptly** — the conflict probability scales with how long the branch sits open; #155's 15h open window is exactly when 3 sibling catalog PRs landed. (3) **Standard resolution recipe when a collision happens:** merge-up `origin/main` → take main's side for the generated artifacts (`assets/seed.db`, never hand-merge the binary) → re-run the deterministic build script → renumber the new rows' ids to follow main's now-higher max id → recompute every count-constant → re-run tsc/lint/jest. This is the same generated-artifact protocol as the rebase entry above (take-theirs-then-rebuild for `.db`/`.sql`), specialized to the catalog. The orchestrator should run the pre-dispatch stale-base check (`git log HEAD..origin/main -- assets/seed.db scripts/seed-data.sql`) before starting ANY catalog implementer, and explicitly sequence catalog work in the task queue. **Recurred with a new dimension in #192/#193 (2026-06-11): two catalog branches developed in PARALLEL collided not just on the generated artifacts but on the id ALLOCATION SPACE itself (both started at id 1425), forcing a renumber + amend + one `reset --hard` reflog recovery. Resolution followed the standard recipe (disjoint ranges 1425-1504 / 1505-1547, second-merger rebased with union merge + counts recomputed + orchestrator independently re-verified the rebuilt DB before merge — clean, ~4 min conflict-to-merge). When parallel catalog branches are unavoidable, reserve disjoint id ranges in each implementer's SPAWN BRIEF (see orchestrator-protocol Communication Flow #8) — mid-flight range reassignments race in-flight commits.** <!-- Source: post-mortem, baby-name-picker #155 (+ recurrence #149, #163), 2026-06-02; strengthened #192/#193, 2026-06-11 -->
- **Local-ahead-of-remote is the mirror of stale-base — verify the pushed head equals the local tip before merging.** A silently failed push + squash-merge orphans commits: plush-press #12's second commit existed locally but never reached GitHub, the squash-merge shipped the stale head, and the content had to be recovered by cherry-pick in a focused restore PR (#14). "Push command exited" is unverified until the remote SHA is confirmed. Pre-merge check: `git rev-parse <branch>` must equal `gh pr view N --json headRefOid` (or `git ls-remote origin refs/heads/<branch>`). <!-- Source: post-mortem, plush-press #14, 2026-06-10 -->

## Review Discipline

- **For a new write-path route, exercise every declared entry/error branch against the live server before merge — this is what makes self-merge safe in a solo workflow.** plush-press #32 (createBook + `POST /api/books`, self-merged ~3.5 min, 0 review comments, 0 post-merge fixes) shipped clean precisely because the PR body recorded a real-runtime pass, not just green tests: POST created `books/<slug>/{backdrops,shelf,README.md}` on disk, `GET /api/scenes?book=<slug>` returned empty (not 404) confirming the new-empty-book path, a duplicate POST returned 409, and the throwaway book was cleaned up + the commit verified to hold exactly the intended files. When there is no peer reviewer, the runtime walk of all entry points (create / duplicate-conflict / consume-empty) IS the review gate — tests assert the units, runtime proves the artifact that ships behaves. Record the runtime evidence in the PR body so the gate is auditable. <!-- Source: post-mortem, plush-press #32, 2026-06-16 -->
- Never merge immediately after CHANGES_REQUESTED; acknowledge findings before merging.
- For PRs over 300 lines, wait 10+ minutes for CodeRabbit before merging.
- Space out PR submissions by 10+ minutes to avoid rate limits.
- CodeRabbit monorepo sandbox produces false test failures; document or configure to skip.
- When a bot finding contradicts the linked issue, verify the issue text first.
- Expect 2 CodeRabbit rounds for 700+ LOC PRs, 3+ when local review is skipped or PR exceeds 1200 LOC.
- **Dev-server hangs on rapid file rewrites.** When an iteration cycle rewrites many files quickly (rapid critic-fix loops), the Next.js dev-server compiler worker can hang silently -- TCP stays open, requests accept, but the worker never responds. The page in the browser shows zero-styled HTML. Recovery: `lsof -ti:PORT | xargs kill -9` then restart. Add a quick "ping the server with curl" healthcheck after large file batches. <!-- Source: post-mortem, baby-name-picker #36, 2026-05-18 -->
- **Wall-clock vs active-time gap on design-iteration PRs.** Design-led PRs (rebrand, landing pages, icons) can have wall-clock 100x active-implementation time due to user-driven iteration. Don't infer "stuck" or "high friction" from wall-clock alone; track an explicit `designIterationRounds` metric separately. <!-- Source: post-mortem, baby-name-picker #36, 2026-05-18 -->
- **Install `idb` (or Maestro) for reliable Expo Router deep-link / detail-route on-device verification.** baby-name-picker's iOS simulator repeatedly wedges onto Expo Router's fallback screen when deep-linking to `/name/[id]`, so on-device visual checks of routed screens keep degrading to "unit tests + critic" (2nd+ occurrence: the #88 cold-start race was found *because* this path is fragile; #113's Layout-B visual check was recorded `[⚠️]` for the same reason). There is no scripted tap/deep-link tooling installed to drive the simulator to a specific route. Until `idb`/Maestro is installed, routed-screen UI changes have no reliable visual gate. **3rd recurrence (baby-name-picker #121, 2026-05-29): a `general-purpose` background agent was dispatched to `expo run:ios` and screenshot the `/name/[id]` action bar; it STALLED and was watchdog-killed after 600s, and the screenshot the orchestrator salvaged showed the "Welcome to Expo" fallback (a stray Metro squatting :8081 from another worktree, per the project's own run notes) — NOT the app. Two compounding failure modes beyond the route-wedge: (a) delegating a multi-minute native iOS build to a watchdog-limited background agent is itself unreliable — the build out-runs the no-progress timer; (b) `npx expo` is mangled to `npm expo` by this user's RTK shell hook, so agents must use `./node_modules/.bin/expo`. Net: the routed-screen visual gate degraded to "unit tests + critic + manual eyeball" for the THIRD time, and the user shipped #121 on tests+critic alone, verifying visually by hand post-merge. Until scripted simulator driving (`idb`/Maestro) AND a foreground/longer-budget build path exist, low-risk presentational route-screen changes should treat the sim screenshot as best-effort, not a blocking gate — do not spend a background-agent + 10min watchdog cycle on it.** <!-- Source: post-mortem, baby-name-picker #113 (recurs from #88), 2026-05-29; 3rd recurrence #121, 2026-05-29 -->

- **Audit structured data on its structured representation, not a flattened projection.** A flattened/denormalized view of multi-valued data hides both directions of error: it makes legitimate multi-value entries look like conflations (false positives) and hides per-element mistakes (false negatives). Evidence: a baby-name audit on the joined `meaning` string produced 7 false positives, and a later pass on the per-language `meanings_json` found 18 errors the flat view missed (swapped pairs, wrong-language glosses). Always audit the canonical structured field. **Reinforced by the #87 regression (fixed across #89/#90): auditing on the flattened view caused #87 to (a) STRIP legitimate real origins — e.g. it dropped Cyrus's well-attested Greek "lord" (Kyrios), Uma's Hebrew, and collapsed Milan/Rhea/Xara to single origins — and (b) INJECT homophone-contaminated glosses by conflating distinct names that look/sound alike: it stamped the Sanskrit "blue, dark" gloss of the distinct name *Neel* onto *Neil* (Irish/Gaelic), and stamped an identical spurious `Arabic: "provisions, supplies"` gloss onto BOTH spelling-variants *Mira* and *Meera* — the same wrong value appearing on two variants was the clearest batch-error signature.** The lesson holds in both directions: a flattened projection both hides real multi-origin structure (so the audit "fixes" it away) and lets homophone/spelling-variant collisions slip in unnoticed. Audit per-language `meanings_json`/`origins_json`, and treat an identical gloss landing on two homophones/spelling-variants as a red flag for cross-name contamination. <!-- Source: post-mortem, baby-name-picker #43, 2026-05-27; reinforced baby-name-picker #87/#89/#90, 2026-05-29 -->
- **Verify the artifact that ships, not an intermediate build output.** A fix can pass all tests against a build output yet never reach users if the shipped artifact is generated/committed separately and has drifted. Trace what the app actually loads at runtime and validate that. Evidence: corrections were verified against `data/seed.db` while the app shipped a hand-edited `assets/seed.db` that had diverged (1249 vs 997 names). <!-- Source: post-mortem, baby-name-picker #41, 2026-05-27 -->
- **Stacked PR + squash-merge: rebase the child with `git rebase --onto <new-main> <old-parent-tip> <child-branch>`.** After the parent PR squash-merges (new SHA on main), this replays only the child's own commits and drops the now-redundant parent commit cleanly. Reconfirmed on plush-press #3 (stacked on #2): parent squash-merged minutes before the child, `rebase --onto` resolved the conflict cleanly pre-merge. **3rd plush-press occurrence, with a new unplanned-stack variant: plush-press #8 continued revising on the SAME branch (`docs/product-spec`) whose PR #6 the user squash-merged from the GitHub UI mid-revision — discovered only at push time, fixed with the same `rebase --onto`. In a solo workflow where the user can merge any open PR at any moment, every just-PR'd branch is implicitly a stack parent: before each subsequent push on a branch with an open-or-recently-open PR, re-fetch and check `git log HEAD..origin/main`; better, start follow-on revisions on a fresh branch off the PR head so a squash-merge can't strand local history.** <!-- Source: post-mortem, baby-name-picker #43, 2026-05-27; reconfirmed plush-press #3, 2026-06-09; unplanned-stack variant plush-press #8, 2026-06-09 -->
- **When you fix a data regression, add a guard test that asserts BOTH the corrected value AND the specific bad value's ABSENCE.** A guard that only pins the right answer can still pass while a different-but-also-wrong value sneaks in; pinning the exact bad string as forbidden makes the specific regression class un-reintroducible. This is what made test-coverage-as-prevention work and scale on baby-name-picker: the seed-corrections suite (built in #43/#55) is the ONLY reason the first 5 #87 regressions were caught at all (they turned the suite red → fixed in #89). #90 then deliberately EXTENDED the same suite to the 6 newly-found regressions with two paired assertions: `RESTORATIONS` (the exact restored `origins_json`/`meanings_json`/`meaning`/`origin` for all 6) AND `RESTORATION_REMOVED_GLOSSES` (the #87-injected contaminants must stay absent — Mira/Meera Arabic "provisions, supplies", Kai Chinese/Scandinavian, Neil Sanskrit "blue", Soren duplicate Latin — plus an assertion that Cyrus *keeps* Greek "lord"). The forbidden-value half is what guarantees a future audit batch can't silently re-inject the same homophone contamination. Generalizable: a regression-guard test should be a two-sided fence (correct value present + known-bad value absent), and the durable response to "a batch operation regressed data with no coverage" is to grow the verified-corrections suite to cover the newly-found cases, not just hand-fix them. <!-- Source: post-mortem, baby-name-picker #89/#90, 2026-05-29 -->
- **Verify subagent-reported anomalies independently before acting; for build artifacts, compare parsed content, not raw bytes.** During #90 an implementer reported a 258-row binary churn in the regenerated `seed.db` and suspected build non-determinism — which, if true, would have blocked the PR or triggered a needless pipeline investigation. The fresh-context critic independently re-derived the diff and proved it was a clean **6 rows** (exactly the intended edits), with the build pipeline confirmed deterministic (a rebuild produced an md5-identical *parsed* dump). The miscount came from diffing the raw SQLite binary, where page reordering / key-order / internal layout changes inflate the apparent diff far beyond the logical change. Two reusable rules: (1) **an orchestrator should not act on a subagent's reported anomaly (regression, churn, non-determinism, flake) until a second independent pass reproduces it** — author-side measurement error is common and cheap to debunk; (2) **to diff generated binary artifacts (SQLite DBs, sqlite dumps, compiled bundles, images), compare a canonical parsed/normalized representation (row-by-row JSON cell dump, normalized export), never raw bytes** — byte diffs conflate logical content change with non-semantic layout churn and produce false anomaly reports. <!-- Source: post-mortem, baby-name-picker #90, 2026-05-29 -->
- **Catalog COMPLETENESS audits (missing values on existing rows) use the same surface→verify gate as additions — and the homograph hit-rate is concentrated in SHORT names, so slice there first.** The generate→screen→salvage pipeline (#141/#149) adds NEW rows; baby-name-picker #174/#176 proved the same discipline applies to ENRICHING existing rows with missing data. The class: single-origin names that are genuine cross-cultural homographs missing a second origin (Sachi = Japanese AND Sanskrit/Śachī). Method: audit the candidate pool (634 single-origin names) → conservative surface pass flags homograph candidates → **independent adversarial WEB-SEARCH verification** of each flagged origin+meaning → enrich only the confirmed (`origins_json` + per-origin `meanings_json`, primaries preserved, count unchanged). Measured: the short slice (≤2 syllables, 409 names) had a **~3.7%** hit rate; the long slice (225 names) only **~0.9%** — cross-cultural homographs cluster overwhelmingly in short, vowel-rich names, so target the short single-origin pool first for the best yield-per-audit. The verification gate is the load-bearing part: it rejected ~12 of ~28 surfaced candidates (43%) as stretches — LLM surface passes confidently over-claim origins, exactly the hallucination risk; never enrich on the surface pass alone. <!-- Source: post-mortem, baby-name-picker #174/#176, 2026-06-02 -->
- **A data-enrichment critic must enforce REJECTION PRECEDENTS, not just per-item accuracy — "is this addition consistent with what we already rejected?" is a distinct check.** In #176 the surface pass proposed Otto+Finnish; it's individually defensible (Otto IS a popular Finnish name). But the same batch had already rejected Roman+Slavic on the rule "same etymological root merely adopted into a host language, identical meaning ≠ a distinct cultural origin." The critic caught that Otto+Finnish (Germanic *audaz, identical "wealth" meaning, just Finnish usage) is the SAME case and must be cut for consistency — otherwise the catalog applies its own inclusion bar unevenly. Reusable rule: when a review establishes a rejection criterion mid-batch, every surviving item must be re-screened against that criterion, not just the ones flagged on first pass. For cross-cultural origin specifically, the bar is "genuinely DISTINCT etymology/meaning in the other culture," not "the name is also used there." <!-- Source: post-mortem, baby-name-picker #176, 2026-06-02 -->
- **Before implementing data enrichments, RECONCILE the proposed additions against the AUTHORITATIVE current DB state — not the surface/verify agent's assumed state — to catch same-root duplicates the upstream agents couldn't see.** In baby-name-picker #178 (the two-origin→third-origin completeness pass, the repeatable sibling of #176), the surface and verification agents were given each name's "current origins" as context, but those strings were lossy/approximate for a few names. The orchestrator re-queried the real seed.db for all 18 verified candidates before building and caught that **Baran** already carried Turkish+Persian, making the proposed "+Kurdish (rain)" a same-Iranian-root restatement of the existing Persian "rain" — exactly the Otto+Finnish/Roman+Slavic rejection class, but invisible to a verifier that only saw "is Baran a Kurdish name?" (it is) without seeing the already-present Persian. Dropping it pre-build (18→17) kept the distinct-etymology bar consistent. Reusable rule: a verify agent answers "is claim X true?"; only a reconciliation against ground-truth current state answers "is claim X NON-REDUNDANT given what we already have?" — both gates are needed for enrichment, and the redundancy check belongs at the orchestrator (which holds the authoritative DB), not the per-item agent. This makes the surface→verify→**reconcile**→implement→critic pipeline the standard shape for catalog completeness work. (Method now proven across three pools: single-origin short ~3.7%, single-origin long ~0.9% [#176], two-origin third-origin ~4% surface→17 shipped [#178]; both PRs 0% post-merge-fix.) <!-- Source: post-mortem, baby-name-picker #178, 2026-06-02 -->
- **When a registry keys on content (front matter) but files live under a slug-named dir, the update/write path must resolve the TRUE on-disk path from the registry — and a test must pin the dir≠filename case explicitly.** plush-press #34 mirrored the scenes layer for characters: identity is anchored in front matter, not the filename, so a real cast member can have `character bible/cat/berlioz.md` where the dir slug (`cat`) ≠ the filename stem (`berlioz`). The list/read path keyed on front matter and worked; the UPDATE path naively reconstructed the target as `<slug>/<slug>.md` and 404'd for exactly that member. Fix shape: resolve the write target by asking the registry for the entry's real path (the same lookup the read path already trusts), never by re-deriving `<slug>/<slug>`; and add a regression fixture where dir≠filename so the asymmetry is pinned. Reusable rule: when read keys on one thing (content/front matter) and write addresses by another (slug/dir name), they're two independent path-resolution code paths — the write path needs its own dir≠filename test, because a fixture set that only covers the symmetric case gives false green. Cite this entry at occurrence #1 in any sibling registry (scenes, books) BEFORE writing the path logic, not after.** <!-- Source: post-mortem, plush-press #34, 2026-06-16; THIRD-occurrence strengthened plush-press #35, 2026-06-16 -->
