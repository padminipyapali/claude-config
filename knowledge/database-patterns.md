# Database / PostgreSQL Patterns

Cross-project learnings for SQL schema design, indexing, and the node-postgres driver.

## Schema Design

- **Bidirectional invariant enforcement.** If a child only makes sense for a specific parent type: (1) trigger on CHILD INSERT/UPDATE verifies parent type, (2) trigger on PARENT UPDATE blocks type change while child exists. Missing either creates orphaned rows.
- **CHECK constraint for type-specific nullable columns.** When a nullable column is only valid for a specific row type (e.g., `caption` only for MEDIA entries), add `CHECK (col IS NULL OR type = 'TARGET_TYPE')`. API validation alone is bypassed by direct SQL, backfills, and migrations. The CHECK prevents inconsistent rows at the DB level. <!-- Source: PR review (CodeRabbit), second-brain #349, 2026-03-04 -->
- **Canonicalized bidirectional links.** For bidirectional links between entities, store with `CHECK (source_id < target_id)` constraint. This prevents duplicate pairs (A→B and B→A) without application-level dedup. The service always sorts the two IDs before inserting. <!-- Source: my_mind_evolved-slip-box DECISIONS -->
- **Metadata JSONB for type-specific context.** When storing type-specific data (response metadata, bot context, channel-specific fields), use a JSONB column rather than type-specific columns. Avoids schema bloat and is extensible to future types. Trade-off: weaker DB-level type safety, but the TypeScript layer enforces shape. <!-- Source: second-brain DECISIONS -->
- **COALESCE in UPDATE prevents clearing nullable fields.** `SET col = COALESCE(@param, col)` treats both "not provided" and "explicitly null" identically — keeping the old value. To support clearing, use a companion boolean flag: `SET col = CASE WHEN @setCol = 1 THEN @col ELSE col END`. The caller passes `setCol: 'col' in input ? 1 : 0`. This distinguishes "omitted" (keep old) from "set to null" (clear). <!-- Source: PR review, command-center #74, 2026-03-02 -->
- **Migration catch blocks must be targeted.** `try { ALTER TABLE ADD COLUMN ... } catch { /* ignore */ }` swallows ALL errors, not just "column already exists". Check the error message: `if (!/duplicate column name/i.test(message)) throw error`. Blanket catches mask disk errors, permission failures, and syntax errors. <!-- Source: PR review, command-center #74, 2026-03-02 -->
- **Backfill data outside the "seed if empty" path.** When adding default values for a new column, don't put the backfill inside the empty-check branch — existing databases skip it entirely. Run backfill unconditionally with `WHERE new_col IS NULL` to avoid overwriting user-modified values. <!-- Source: PR review, command-center #74, 2026-03-02 -->
- **Dedupe-then-repoint, never repoint-then-dedupe.** When merging duplicate rows that have a unique constraint on `(parent_id, user_key)` (votes, favorites, reactions, etc.), DELETE the losing rows within each `(canonical_parent, user_key)` partition BEFORE running the UPDATE that repoints child FKs onto the canonical parent. The naive order — UPDATE first, then dedupe — collides with the existing unique constraint when both the canonical row and a duplicate already had a record from the same user. Migration must be transactional and idempotent (use `IF NOT EXISTS` on partial unique indexes), and tiebreakers should use `ORDER BY updated_at DESC NULLS FIRST, created_at DESC NULLS FIRST, id DESC` so missing-timestamp rows don't accidentally win. <!-- Source: post-mortem, remodel-hq #23, 2026-05-04 -->
- **Destructive merge-collapse where the SURVIVOR owns the contested unique key: rename the winner LAST.** Distinct from the dedupe-then-repoint bullet above (children point at a stable canonical *parent*) — here the `UNIQUE(name, user_id)` value lives on the surviving row's own `name`, and several rows collapse onto one canonical name. Per `(canonicalize(name), user_id)` group: pick a deterministic winner (oldest `created_at`, tie-break lowest `id` — `created_at` from a single `now()` statement CAN tie, so the id tie-break is load-bearing for idempotency), then for each loser re-point its join rows onto the winner with `INSERT … SELECT … ON CONFLICT (entry_id, tag_id) DO NOTHING` (preserves an entry that already held BOTH winner and loser — no link lost, no dup row), `DELETE` the loser's join rows, `DELETE` the loser; only AFTER every loser is gone, `UPDATE … SET name = canonical WHERE id = winner AND name <> canonical` — renaming last guarantees the unique target is free so the rename can't violate the constraint, and the `name <>` guard makes it a no-op on re-runs. Lock all touched rows `FOR UPDATE` up front; run the whole thing in ONE transaction; ship it DRY-RUN-BY-DEFAULT (mutation behind an explicit `--apply` flag, and the dry-run path returns before `pool.connect()` so it physically cannot mutate). When the normalizer has no faithful SQL equivalent (e.g. NFKC Unicode folding), run the backfill through the REAL TS normalizer as a Node script — make any companion `.sql` documentation + an approximate read-only impact query only, never the executor. Skip+report rows whose canonical form is `""` (never rewrite to `''` — UNIQUE would fold unrelated junk together). See also [[BUG-037]]. <!-- Source: adversarial review, second-brain #748, 2026-06-26 -->

## Pagination

- **Composite cursor for timestamp-based pagination.** When paginating with `WHERE created_at > $1`, rows sharing the same timestamp get skipped — only the first row at that timestamp is returned, and all subsequent rows with the same value are lost. Use a composite cursor with a tiebreaker column (usually the PK): `WHERE (created_at, id) > ($1, $2) ORDER BY created_at, id`. This applies to any timestamp-based cursor pagination — `created_at`, `updated_at`, `completed_at`, etc. Batch inserts, same-second operations, and high-throughput systems routinely produce duplicate timestamps. <!-- Source: PR review, second-brain #246, 2026-02-25 -->

## Query Patterns

- **Scope all DB queries AND mutations by user_id.** Channel-local IDs (e.g., Telegram message_id) are NOT globally unique. Without user scoping, user A's data can match user B's query. This applies to UPDATE/DELETE too — `WHERE id = $1` without `AND user_id = $2` allows IDOR. Even if the route handler already verified ownership via a prior SELECT, add `user_id` to the mutation query as defense-in-depth — the SELECT and mutation can race with a concurrent delete. <!-- Source: PR review (CodeRabbit), second-brain #349, 2026-03-04 -->
- **IDs that round-trip through the client must be re-scoped to the authenticated user on the way back in.** When a DB row's primary key is embedded in client-controlled state (Telegram `callback_data`, a hidden form field, a URL param, a webhook echo), the value returning from the client is attacker-controllable — a different user can substitute another user's UUID. The handler MUST re-derive the authenticated user (e.g., from the trusted chat/session, NOT from the echoed payload) and look the row up by `WHERE id = $1 AND user_id = $2`, mirroring the sibling query's scoping. A wrong-user lookup returns null → degrade to the benign "expired/not found" path with no side effect, and assert exactly that in a test (`runCalendarConfirm` for a different user → no calendar write). <!-- Source: PR review, second-brain #668, 2026-06-20 -->
- **User scoping on correlated subqueries.** Always include `AND c.user_id = e.user_id` even if the data model guarantees it — defense in depth.
- **FTS + vector search are complementary, not alternatives.** FTS excels at exact/stemmed word matching but fails on conceptual similarity ("colors" won't find "yellow", "blue"). Use FTS as primary with vector similarity fallback when FTS returns 0 results. This avoids the cost of embedding every query while catching semantic matches.
- **Conditional SELECT for type-specific columns in cross-type queries.** When a column is only meaningful for one entry type (e.g., `extracted_text` for MEDIA), use `CASE WHEN type = 'MEDIA' THEN extracted_text ELSE NULL END` in cross-type result sets (search, related entries). This avoids transferring large unused text for non-matching types. Single-entry display queries can still select unconditionally. <!-- Source: PR review, second-brain #162, 2026-02-19 -->
- **Client-called RPC vs triggers for expensive aggregation.** Use DB triggers for lightweight bookkeeping (updating `updated_at`, incrementing counters), but use client-called RPCs for expensive aggregations (e.g., recomputing net worth across all accounts). Triggers fire on every row change and can cascade into costly recalculations on batch updates. An explicit RPC (`SELECT recompute_net_worth(household_id)`) lets the client control when the cost is paid — call once after a batch of balance updates, not per-row. <!-- Source: folio D002, 2026-02-23 -->
- **`COUNT(*) OVER()` returns 0 when `LIMIT` yields no rows.** The window function `COUNT(*) OVER()` counts only the rows in the result set, not the total matching rows before LIMIT is applied. When `LIMIT 0` (or any limit smaller than the matching set that results in 0 rows), total becomes 0 even when matches exist. Guard with a separate count-only query for `limit <= 0`, or use a CTE that computes the count before limiting. <!-- Source: PR review, second-brain #276, 2026-02-26 -->
- **FTS: use OR semantics for personal knowledge retrieval.** `plainto_tsquery` (AND) fails when users search with metadata terms — proper nouns, category labels, or concept names that don't appear verbatim in the stored text (e.g., "Bene Gesserit fear mantra" for an entry containing only the Litany text). Use `websearch_to_tsquery` with OR-joined terms so entries matching ANY term surface, ranked by `ts_rank_cd`. AND semantics is only appropriate when false positives are dangerous (e.g., matching TODOs for completion).
- **A new user-writable signal must be wired into RETRIEVAL, not just storage + display.** A field that is stored and feed-filterable but absent from the search index/query is a retrieval silo: searching by it returns nothing for items that match ONLY on it. When you add a taggable/categorizable/labelable dimension, the "done" bar includes "is this searchable?" — add a dedicated lane (or column to the FTS expression) that reads the new table, user-scoped, parameterized. second-brain #740: tags lived in `entry_tags`/`tags` and filtered the feed, but the hybrid search read only content fields, so "remodel" missed `#remodel`-tagged entries with no body match — fixed by a third exact-match tag lane (`= ANY($2::text[])`, scoped on BOTH `entries.user_id` AND `tags.user_id`). <!-- Source: adversarial review, second-brain #740, 2026-06-25 -->
- **Adding a lane to an RRF/score-fusion merge: SEED the lane's rows into the score map BEFORE any boost loop.** RRF merges typically build a `Map<id, {row, score}>` from each source list, then run boost passes that iterate ONLY `scores.values()`. A new source whose rows are applied as a boost-only pass (not seeded as base entries) is invisible for any id the other lanes never retrieved — the boost loop never visits it. Seed every lane's rows into the map (summing scores when already present) before the boost passes, or lane-only hits silently never appear in results. This is the recall half of the fix; the boost is only the ranking half. <!-- Source: adversarial review, second-brain #740, 2026-06-25 -->
- **An exact-match lane must match BOTH the canonical and the as-stored literal form until write-time canonicalization lands.** When matching query terms against stored names by equality, and writes don't yet canonicalize (e.g. tags stored as `trim()+toLowerCase()` with no hyphenation), keying the lane only on the canonical form (`home-remodel`) misses the literal stored value (`home remodel`, `remodel_kitchen`). Emit both forms as candidates (per term AND the whole query, de-duped, empties dropped) so stored values are reachable in either format; collapse to canonical-only once a migration/write-path canonicalizes existing rows. <!-- Source: adversarial review, second-brain #740, 2026-06-25 -->
- **When a write path adopts a STRICTER normalizer as its dedup key, run the empty-result/empty-name guard AFTER canonicalization — and keep the as-stored literal read lane until a backfill converges old rows.** Swapping a loose key (`trim()+toLowerCase()`) for a stricter canonical form (strip `#`, fold whitespace/underscores to hyphens, trim hyphens) means inputs the old key kept non-empty (`"###"`, `"___"`, `"---"`, `"   "`) now collapse to `""`. If the empty-name guard still runs on the raw/loose value, those reach the DB and either mint a junk row or hit the wrong branch — order it `canonical = canonicalize(raw); if (!canonical) throw/return` so the guard sees the post-canonical value, no query issued. The write side converging on the canonical form does NOT retroactively fix existing rows, so any read/dedup/removal that must match stored values keeps the both-forms lane (see prior bullet) until a backfill rewrites old rows. <!-- Source: adversarial review, second-brain #746, 2026-06-25 -->

## Indexing

- **Use partial unique indexes for nullable columns.** `CREATE UNIQUE INDEX ... ON table(col) WHERE col IS NOT NULL` enforces uniqueness only when the column has a value, allowing multiple NULLs.
- **FTS indexes must cover ALL searchable text columns.** When adding full-text search, include every column users might search — title, body, tags, metadata. A missing column means silently incomplete results.
- **Index leading columns must match WHERE clause order.** A composite index `(A, B)` or composite PK only accelerates queries filtering on `A` or `(A, B)` — not `B` alone.
- **UNIQUE(A, B) already indexes A-only lookups — don't add a redundant single-column index.** A UNIQUE constraint on `(source_id, related_id)` creates a composite index with `source_id` as the leading column, which PostgreSQL can use for `WHERE source_id = $1` queries (including EXISTS subqueries). An additional `CREATE INDEX ON table(source_id)` adds write overhead with no read benefit. Only add a separate index if you need to query by the non-leading column alone (`related_id`). <!-- Source: PR review (CodeRabbit), second-brain #351, 2026-03-04 -->
- **Never use OR in WHERE clauses that defeat index usage.** `WHERE a = 1 OR b = 2` cannot use an index on `(a)` or `(b)` efficiently. Split into two queries and UNION, or use separate indexed lookups.

## Timestamp Management

- **Timestamp propagation: child changes should touch parent updated_at.** For recency-sorted feeds, when a child record changes (comment added, subtask completed), update the parent's `updated_at` via trigger or application code. Without this, the parent appears stale in lists sorted by last activity.

## Concurrency & Locking

- **Use advisory locks for rate-limit invariants, not bare COUNT+INSERT.** `INSERT ... WHERE (SELECT COUNT(*) ...) < N` is racy at READ COMMITTED isolation — concurrent transactions each see the same count and all insert. Wrap in a transaction with `SELECT pg_advisory_xact_lock(hashtext(user_id))` to serialize per-user. The lock is automatically released at COMMIT/ROLLBACK. This applies to any "insert if under limit" pattern: rate limiting, quota enforcement, max-children checks. <!-- Source: PR review, leaflet #21, 2026-03-10 -->

## Connection Management

- **Set `connectionTimeoutMillis` on every pg.Pool.** The default of `0` means connection attempts wait indefinitely. A single slow connection (transient network issue, cold start after idle) makes the entire service appear dead with no error logged. Use `connectionTimeoutMillis: 5_000` (5s) — normal connections establish in 50-200ms, so 5s has no impact on healthy operations but ensures hung attempts fail fast. <!-- Source: BUG-023, second-brain, 2026-02-15 -->

- **Register `pool.on("error", …)` on EVERY `pg.Pool` — including one-off scripts and backfills — and `end()` the pool when done.** A `pg.Pool` is an `EventEmitter`. When a pooled connection that is currently IDLE drops (Supabase/pgbouncer pooler idle timeout, a Postgres restart, a TCP reset), pg emits an `error` event on the pool asynchronously. With no listener, Node's default `EventEmitter` behavior promotes it to an UNCAUGHT exception and the process exits non-zero — even AFTER all your work has fully succeeded. In a nightly backup/export script this manifested as a FALSE failure: the export finished, wrote a truthful success marker, then ~14 min later an idle pooled connection hit `read ETIMEDOUT`, crashed the process, and the launchd wrapper fired a "backup FAILED" alert for a good backup (second-brain #857). Fix: attach `pool.on("error", (err) => logger.error(..., err))` BEFORE the first query to log-and-absorb idle-client errors (mirror the listener your long-running server already registers), and `pool.end()` in a `finally` as the last thing you do with the pool so no idle connection lingers to time out after the work is done. Corollary: a non-zero exit from a long-lived pg script is NOT proof the work failed — check the on-disk result/marker before treating the exit code as authoritative. <!-- Source: BUG-039 / adversarial review, second-brain #857, 2026-07-08 -->

- **pg emits `error` on the CHECKED-OUT client too, not just the idle pool — a `pool.on("error")` listener does NOT cover it.** The pool-level listener above only fires for connections sitting IDLE in the pool. A client you have `pool.connect()`-ed and are actively using has its OWN `EventEmitter`; if its socket drops mid-transaction (`Connection terminated unexpectedly`), pg emits `error` on that CLIENT, and with no `client.on("error", …)` it becomes an uncaught exception that crashes the process — potentially before your `catch`/failure-marker path can run, so a crashed job leaves no evidence it failed (second-brain #867: a backup crash left no `BACKUP_FAILED.txt`). Fix: attach a listener to the client for the checkout's lifetime and REMOVE it on `release()` so it doesn't accumulate across checkouts and so later idle errors fall back to the pool listener: `const onErr = (e) => logger.error(..., e); client.on("error", onErr); try { … } finally { client.removeListener("error", onErr); client.release(); }`. The in-flight query's own promise rejection still drives your normal rollback/failure path — the listener only absorbs the redundant EventEmitter crash. **Related lesson: code BEFORE the `try` block is outside your failure handling.** In the same incident, `pool.connect()` sat above the `try`, so a clean connect failure (network not up yet when launchd fired the job as the Mac woke) threw before the `catch` could write the failure marker. Move the acquire INSIDE `try` (and guard the now-possibly-undefined client in `catch`/`finally`) so an acquisition failure still runs your failure path. <!-- Source: adversarial review, second-brain #867, 2026-07-10 -->

- **pg.Pool `min` does NOT eagerly create connections.** The `min` option only prevents the pool from reaping idle connections below that count — it does NOT create connections at startup. Connections are always created lazily on demand. To warm the pool, run concurrent queries at startup: `await Promise.all(Array.from({ length: pool.options.min }, () => pool.query('SELECT 1')))`. A single `pool.query()` only opens one connection regardless of the `min` setting. Log warmup timing and `pool.totalCount` afterward for operational visibility. <!-- Source: PR review (CodeRabbit), second-brain #268, 2026-02-26 -->

- **The Supabase TRANSACTION pooler (pgbouncer, :6543) does NOT apply the role's default `search_path` — pin it with the libpq STARTUP param, not a per-transaction `SET`.** When `DATABASE_URL` points at Supabase's transaction-mode pooler, sessions come up with an EMPTY `search_path` (pgbouncer does not replay the role default per session). Every *unqualified* query — starting with the very first write — then fails with `42P01 relation "X" does not exist` even though the table exists in `public`. The symptom is deceptive: the DB has the tables and all the data (second-brain #853: 1077 entries + 4 users all intact in `public`); nothing was lost — it is purely a connection setting. **Fix:** set `options: "-c search_path=public"` on the pool config (`new Pool({ ..., options: "-c search_path=public" })`). This libpq option travels in the pgbouncer STARTUP packet and is applied per *physical* connection, so it survives transaction-mode pooling. A per-transaction `SET search_path = public` does NOT work — pgbouncer resets session state between transactions (checkouts), so the SET is gone by the next unqualified query. Extract the pool config into a pure `buildPoolConfig()` so the pin is unit-tested (both env flags, connectionString passthrough, TLS/keepAlive/timeouts/min preserved) in isolation from bootstrap side effects. Corollary: any script or service that builds its OWN `pg.Pool` (maintenance scripts, one-offs) needs the same pin — route them through the shared builder (second-brain follow-up #852). <!-- Source: post-mortem, second-brain #853, 2026-07-05 -->

- **Validate a POOLER / connection-setting fix against the REAL pooler with MULTIPLE concurrent connections — a single-connection test can pass while transaction pooling breaks it.** A per-physical-connection setting (session `search_path`, `SET` params, prepared-statement state, `application_name`) is only proven correct when you force >1 physical connection at once and assert the property on EVERY one. second-brain #853 validated the `search_path=public` pin by opening 8 concurrent checkouts through the live transaction pooler and confirming all 8 reported `search_path=public`, unqualified `SELECT count(*) FROM users` → 4 / `FROM entries` → 1077, and the previously-`42P01` `findOrCreateUser` succeeded with no dup — proving the startup param persists per physical connection through pgbouncer. A single sequential connection would have reused one warm physical connection and hidden a per-checkout reset. Pattern: `await Promise.all(Array.from({ length: 8 }, async () => { const c = await pool.connect(); try { assert((await c.query('SHOW search_path')).rows[0].search_path === 'public'); } finally { c.release(); } }))`. <!-- Source: post-mortem, second-brain #853, 2026-07-05 -->

## Triggers & State Machines

- **Auto-timestamp triggers must fire on INSERT OR UPDATE, not UPDATE only.** If a trigger auto-manages a timestamp (e.g., `completed_at = now()` when status = 'DONE'), make it fire `BEFORE INSERT OR UPDATE` — not just `BEFORE UPDATE`. UPDATE-only triggers silently skip direct INSERTs with terminal status (test data seeding, manual migrations, data repairs). The function body handles INSERT safely when using `OLD IS NULL OR OLD.status IS DISTINCT FROM 'DONE'` — `OLD IS NULL` is true for INSERTs, so `IS DISTINCT FROM` already works. <!-- Source: PR review, second-brain #206, 2026-02-22 -->

- **Enumerate ALL transition paths when expanding a state machine.** When adding a new status to a DB-managed state machine with triggers, enumerate every possible transition (N states = N*(N-1) directional transitions). It's easy to handle forward paths (OPEN→IN_PROGRESS→DONE) and forget reversal paths (DONE→IN_PROGRESS). Missing a transition branch leaves derived timestamps in an inconsistent state (e.g., `completed_at` stays set when moving a DONE item back to IN_PROGRESS). <!-- Source: adversarial review, second-brain #156, 2026-02-19 -->

## PostgreSQL-Specific

- **`AT TIME ZONE`: always cast to `::timestamp` before applying.** `date` implicitly casts to `timestamptz` which reverses the timezone conversion. Use `my_date::timestamp AT TIME ZONE 'America/New_York'` to get correct results. **Corollary: never use `col::date` for user-facing date comparisons** — `created_at::date` evaluates in the DB server's timezone, not the user's. Near midnight, TODOs/entries silently appear under the wrong day. Use `col >= $date::timestamp AT TIME ZONE $tz AND col < ($date::timestamp + interval '1 day') AT TIME ZONE $tz` instead. Similarly, **format dates in SQL with `to_char(col AT TIME ZONE $tz, 'YYYY-MM-DD')`** rather than returning raw timestamps and calling `.toISOString().slice(0, 10)` in application code — the latter normalizes to UTC, shifting dates for non-UTC users. <!-- Strengthened: PR review, second-brain #359, 2026-03-04 -->
- **(node-postgres) pg driver return types differ from expectations.** `DATE` columns return JS `Date`, `TIMESTAMPTZ` returns `Date`, `JSONB` returns parsed object. Mock-based tests can't catch these type mismatches — verify pg's actual return type when adding new columns.

## SQLite-Specific

- **Use PRAGMA table_info for idempotent migrations, not blanket try/catch.** SQLite's `ALTER TABLE ADD COLUMN` throws if the column exists, but catching all errors hides real failures (disk full, permissions, corrupt DB). Instead: `const cols = db.pragma("table_info(table_name)"); if (!cols.some(c => c.name === "col")) { db.exec("ALTER TABLE ..."); }`. This is precise and doesn't mask unexpected errors. <!-- Source: PR review, command-center #34, 2026-02-21 -->

## Supabase Auth Patterns

- **Always set `emailRedirectTo` in `signInWithOtp`.** Without it, Supabase falls back to the project's Site URL in the dashboard — typically `http://localhost:3000` from initial setup. This silently breaks magic links in production and on mobile. Use `emailRedirectTo: window.location.origin` for web apps. Also ensure the production URL is in the Supabase dashboard redirect allowlist (Authentication → URL Configuration → Redirect URLs). <!-- Source: BUG, second-brain #214, 2026-02-23 -->

## Supabase / RLS Patterns

- **RLS UPDATE policies need both USING and WITH CHECK.** `USING` controls which existing rows the user can modify, but without `WITH CHECK`, the UPDATE can write *any* new values — including changing `household_id` to move data to another tenant. Always add `WITH CHECK (is_household_member(household_id))` (or equivalent) mirroring the USING clause on UPDATE policies. INSERT policies already require WITH CHECK by syntax. <!-- Source: PR review, folio #1, 2026-02-23 -->
- **Every new table in the `public` schema needs `ENABLE ROW LEVEL SECURITY` in the SAME migration that creates it — and you must fix EVERY creation source, not just prod.** In Supabase, `public` is exposed through PostgREST, so a table without RLS is readable and writable with the browser anon key that ships in the frontend bundle. The gap appears silently: RLS is enabled per-table, so tables added later by hand-applied migrations inherit nothing from their siblings, and only the Security Advisor ("RLS Disabled in Public") ever mentions it. second-brain #950 found `data_sources` and `message_processing_log` exposed this way while all 25 sibling tables had RLS on; `message_processing_log` holds previews of the owner's inbound messages. Two things make this worth a checklist item: (1) **The fix is usually zero-policy.** RLS with NO policies is deny-all to `anon`/`authenticated`, which is exactly right when the server reaches the table over `DATABASE_URL` (verify with `SELECT rolbypassrls FROM pg_roles WHERE rolname = current_user` — and check `relforcerowsecurity` is false, since a table OWNER bypasses RLS only when FORCE is off) and the browser client uses Supabase for auth only. Confirm no client actually queries the table via PostgREST before assuming this: grep the web package for `.from(`/`.rpc(`. Several tables in the same DB already used this deny-all shape, so match the existing posture rather than inventing policies. (2) **The sibling sweep is over creation SOURCES, not over prod.** Patching the live DB fixes today; the error returns the moment anyone runs the *other* copies of the DDL. In the "setup card" pattern (see the manual-migration entry in this file), the same `CREATE TABLE` exists in up to four places — the numbered migration, a root `migrations/*.sql`, `schema.sql`, and an exported `*_SETUP_SQL` constant the admin UI hands the operator to paste into the SQL editor. #950's sweep found a table that did not exist in prod YET (`job_runs`), whose setup constant would have created a third exposed table on first use. Fix every copy and add a test asserting the constant contains the `ALTER TABLE … ENABLE ROW LEVEL SECURITY` line — a string constant that generates schema deserves the same completeness check as a migration. Diagnose from the DB, not the repo: `SELECT relname, relrowsecurity FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace WHERE n.nspname = 'public' AND c.relkind = 'r'` lists every gap at once, and `pg_policies` shows which siblings are deny-all vs. policied. <!-- Source: Supabase Security Advisor triage, second-brain #950, 2026-07-28 -->
- **Supabase upsert can't target partial unique indexes.** PostgREST maps `onConflict: 'col1,col2'` to `ON CONFLICT (col1, col2)` without a WHERE clause, so Postgres can't match a partial unique index (`WHERE source = 'manual'`). Fix: use a full (non-partial) unique index and include the discriminator column in `onConflict` (e.g., `onConflict: 'account_id,snapshot_date,source'`). This preserves per-source uniqueness without the partial index limitation. <!-- Source: PR review, folio #1, 2026-02-23 -->
- **Include mutable timestamps in upsert payloads.** On an upsert UPDATE, columns not in the payload keep their old values. If a trigger copies `recorded_at` to a parent table (`balance_updated_at`), the old timestamp propagates, making "last updated" stale after same-day corrections. Always include time-sensitive columns like `recorded_at: new Date().toISOString()` in the upsert payload. <!-- Source: PR review, folio #1, 2026-02-23 -->
- **Never overwrite created_at in ON CONFLICT DO UPDATE.** `created_at = now()` in a DO UPDATE SET clause destroys the original creation time. Immutable audit columns (`created_at`) should never appear in DO UPDATE SET. If you need an update timestamp, add a separate `updated_at` column. <!-- Source: PR review, folio #1, 2026-02-23 -->
- **Realtime subscription must cover all published tables.** When `ALTER PUBLICATION supabase_realtime ADD TABLE X` publishes a table, verify the client subscribes to it. Derived tables (e.g., `net_worth_snapshots` recomputed via RPC) need subscriptions too — cross-partner sync breaks silently if only the directly-written tables are subscribed. <!-- Source: PR review, folio #1, 2026-02-23 -->

## Counter Management

- **Async counter resets should use relative decrement, not unconditional zero.** When a fire-and-forget task processes N items and resets a counter (e.g., `turns_since_summary`), use `GREATEST(counter - $N, 0)` instead of `SET counter = 0`. Between the async task starting and completing, new increments may have arrived. Zeroing the counter loses those increments; relative decrement preserves them. This applies to any pattern where: (1) a counter tracks unprocessed items, (2) processing runs asynchronously, and (3) new items can arrive during processing. <!-- Source: PR review, second-brain #275, 2026-02-26 -->

## Mutation Return Values

- **DB mutations (UPDATE/DELETE) should return affected row count, not void.** When a service method runs `UPDATE ... WHERE id = $1 AND user_id = $2`, returning `void` gives the API layer no signal for 0-row results (row doesn't exist, wrong user, wrong type). Return `boolean` (`(result.rowCount ?? 0) > 0`) or the count itself. This lets routes return 404 on miss instead of silently succeeding. Applies to any mutation gated by ownership or type constraints. <!-- Source: PR review, second-brain #262, 2026-02-25 -->
- **A bare `UPDATE` on a CHILD table is a silent no-op when the child row was never created — and `pg` reports that as success.** An `UPDATE child SET col = $1 WHERE parent_id = $2` expresses "change this row if it exists," but the caller's intent is almost always the assertion "the parent NOW has this value." Those diverge whenever the child row can legitimately be absent — most often because a sibling write path was deliberately allowed to tolerate a partial write (second-brain's `createTodoEntry` downgrades a failed `todo_status` insert to a warning rather than rolling the entry back, committing a TODO with no status row). Every caller then sees success while nothing happened, and any read that `INNER JOIN`s the child table shows nothing — so a route can return 200 for an item that appears on no surface. Ask of every UPDATE: *can the target row legitimately be missing?* If yes, use an upsert or check `rowCount`. When converting to an upsert, source the row from the PARENT so the type/ownership guard stays in SQL (`INSERT INTO child (parent_id, col) SELECT p.id, $1 FROM parent p WHERE p.id = $2 AND p.type = '…' ON CONFLICT (parent_id) DO UPDATE SET col = EXCLUDED.col`; `ON CONFLICT` needs the child's PK/unique column as its target). Then enumerate what the new INSERT arm does to callers that were RELYING on the old no-op — second-brain #942 needed an `AND ($1 IS NOT NULL OR EXISTS (SELECT 1 FROM child …))` arm because a shared caller that CLEARS the value would otherwise have created a defaulted status row, materializing a previously-invisible todo and floating it to the top of recency-sorted feeds via the `updated_at` trigger. A fix for a silent no-op must not become a silent create. <!-- Source: adversarial review, second-brain #942, 2026-07-27 -->

## Data Integrity
- **When a feature is defined as a CONJUNCTION of stored conditions, every writer owes the reader ALL of them — otherwise a write "succeeds" into invisibility.** If the read is `WHERE tagged AND dated AND status <> 'DISMISSED'` and a write path establishes only some of those, the endpoint returns 200 for a row that shows up in no list, no card, and no export. The constraint is invisible at the write site: the writer's code contains no reference to the reader's filters, so nothing links them. Two rules: (1) before shipping any write path, run the feature's OWN read query against the row the write just produced and ask "would this come back?" — if a filter can exclude it, fail loudly (400 / per-item error) instead of returning a successful-looking no-op; soft-deleted / dismissed / archived / superseded states are the usual culprits. (2) If the definition needs two writes, make them ONE server-side endpoint rather than two client calls (two calls can half-fail), and order them so a mid-flight failure lands in the VISIBLE partial state — second-brain #942 writes the due date first and the tag second, so a failure leaves an untagged due-today todo (still listed) rather than a tagged-but-undated one (invisible everywhere). Also check date-conditional writers: stamping a "today" marker while sealing a PAST date produces a tag that can never satisfy the conjunction, and inert tags still pollute tag lists, tag search, and filters. <!-- Source: adversarial review, second-brain #942, 2026-07-27 — the class occurred on TWO routes in one PR -->


- **Validate FK references belong to the authenticated user inside transactions.** When a transaction inserts a row referencing another row via FK (e.g., `source_entry_id` pointing to the entry that spawned an idea), validate that the referenced row belongs to the same `user_id` with a `SELECT id FROM table WHERE id = $1 AND user_id = $2` inside the same transaction client. Without this, a user can reference another user's data by guessing UUIDs. Silently null-out invalid references (the creation should still succeed) unless referential integrity is critical to the feature. <!-- Source: PR review, second-brain #262, 2026-02-25 -->
- **Guard after create → reload.** After creating a resource and reloading from DB, check for null. Fire-and-forget patterns, replication lag, or race conditions can cause the reload to fail.
- **Dedup-check-then-insert must be in a transaction.** When checking for duplicates before inserting, both the SELECT and INSERT must be inside a `BEGIN`/`COMMIT` block. Without a transaction, a concurrent request can pass the dedup check after the first request's SELECT but before its INSERT, creating duplicates. Use `pool.connect()` + explicit transaction, not `pool.query()`. <!-- Source: PR review, second-brain #102, 2026-02-15 -->
- **A unique-constraint violation is NOT proof of a retry/duplicate — verify the existing row's content before deduping.** When code inserts a row keyed on an EXTERNAL sequence id (a Telegram `message_id`, a per-conversation counter, a provider webhook id) and treats the resulting 23505/unique violation as "already saw this, ignore it," it silently drops data the moment those ids get recycled. Per-conversation sequence ids are not globally unique for a user over time: deleting/recreating the chat resets the counter, so a fresh low id collides with an OLD row holding the same id but different content. At the SQLSTATE level a recycled-id collision is indistinguishable from a genuine webhook retry — only the stored content disambiguates. Fix: on the violation, fetch the existing row (scoped to the authenticated user), compare content — identical → it really is a duplicate (rethrow/ignore); different → degrade by re-inserting once with the non-unique external id NULLed (works when the unique index is partial, `WHERE external_id IS NOT NULL`) so the user's data survives. Gate the recovery on the SPECIFIC constraint name so unrelated unique indexes still propagate untouched, and split the raw insert into its own helper so recovery re-inserts exactly once (no recursion). **Merged as #861 (2026-07-09); note the diagnosis history: the collision was FIRST misread as a webhook retry and corrected only after querying prod and finding the "duplicate" row held different, months-old content — verify a 23505's meaning against the actual row, don't assume the benign case (see process-patterns.md "An error CODE is not a diagnosis").** <!-- Source: adversarial review, second-brain #856, 2026-07-08; merged/strengthened #861, 2026-07-09 -->
- **`SELECT ... FOR UPDATE` to serialize status-guarded mutations.** When a mutation checks `WHERE status = 'PENDING'` and then fires side-effects (API calls, notifications, state transitions), concurrent requests can both pass the status check before either commits, executing the side-effect twice. Fix: use `SELECT ... WHERE id = $1 AND status = 'PENDING' FOR UPDATE` inside a transaction. The `FOR UPDATE` lock serializes access — the second concurrent request blocks until the first commits (which changes the status), then the second SELECT returns zero rows and skips the side-effect. This is critical in systems with Telegram inline buttons (double-tap), webhook retries, or dashboard clicks that can fire concurrent requests. <!-- Source: PR review, second-brain #246, 2026-02-25 -->
- **Advisory locks for count-based limits in transactions.** A transaction alone doesn't prevent TOCTOU races on `SELECT COUNT(*) ... INSERT` patterns — concurrent transactions both observe the same count before either commits, exceeding the limit. Add `SELECT pg_advisory_xact_lock(hashtext($1))` with the scoping key (e.g., userId) after `BEGIN` to serialize the critical section. Unique partial indexes handle dedup but can't enforce count limits. <!-- Source: PR review, second-brain #208, 2026-02-22 -->
- **Source of truth directionality for type/CHECK pairs.** When a TypeScript union and a SQL CHECK constraint mirror each other, designate ONE as canonical (usually the TS type — it has compile-time checking) and have the other reference it. If both files say "I'm the source of truth," they'll diverge when one is updated without the other. When narrowing the constraint, always create a migration file — even without an auto-runner. If the project has existing migrations that use `ALTER TABLE ... DROP CONSTRAINT ... ADD CONSTRAINT` (check for precedent), follow that pattern. Documenting a permanent mismatch is a last resort, not the default. A wider CHECK is safe (never rejects valid values) but undocumented divergence confuses future maintainers. <!-- Source: PR review, second-brain #191, 2026-02-20; strengthened second-brain #297, 2026-03-01 -->
- **Content hash must include full provenance, not just content.** When content-addressing chunks for dedup/upsert (ON CONFLICT on content_hash), the hash must include source file, section/heading, and position — not just the chunk text. Identical text in different files collides cross-file; identical text in different sections of the same file collides intra-file. Pattern: `hash(sourceFile + "\n" + heading + "\n" + index + "\n" + content)`. This applies to any content-addressed storage: embeddings, document chunks, cache entries, asset dedup. <!-- Source: PR review, second-brain #237, 2026-02-24; strengthened round 2 -->
- **Delete-then-insert re-indexing must be transactional.** When replacing all records for a source (delete existing + insert new), wrap both in a single `BEGIN`/`COMMIT` transaction. Without a transaction, a DB write failure mid-loop leaves the source partially indexed (old data deleted, new data only partially inserted). Use `pool.connect()` + explicit `BEGIN`/`COMMIT`/`ROLLBACK` with `client.release()` in `finally`. This is distinct from the prepare-then-replace pattern (which guards against embedding/API failures) — both are needed for full safety. <!-- Source: PR review, second-brain #237, 2026-02-25 -->
- **Reverting an optimistic mutation must DELETE rows the mutation lazily CREATED — not restore a default.** When an action upserts/lazily-creates a row (e.g. a first-ever Elo `rating` row defaulting to 1500 on first comparison), the undo must distinguish "row didn't exist before" from "row had value X". Capture-before: snapshot the prior row OR `null` if absent. On revert, restore the captured value when it existed, but **`DELETE` the row when the pre-state was `null`** — restoring a "default" instead leaves a phantom row (a name now carrying a 1500 rating it never earned) that corrupts downstream logic. Also delete any log/event rows the action wrote (capture the inserted `lastInsertRowId` and delete that exact id), or the undone action still pollutes anything reading that log. <!-- Source: baby-name-picker selection-undo #N, 2026-05-28 -->
- **Export/backup tools: LOUDLY flag data that physically exists but is excluded by policy — never skip it silently.** A catalog-driven export that reconciles a live DB against a static include/exclude map has three cases for a live table: included (export it), unknown (include + warn), and excluded-by-policy. The dangerous case is the third: if a table is classified "excluded — dropped by migration X / feature removed" but a stale DB still has it populated (common when there's no migration runner and migrations are applied manually), routing it to an `excludedTables` map with a reassuring reason and no warning is **silent data loss** — the operator reads "dropped, feature removed" and never learns real rows were skipped. Fix: when an excluded-by-policy table is found *present* live, emit a loud `warn`, record it in a dedicated machine-readable field (`presentButExcluded`), and surface it in any human-facing summary/README — distinct from the benign "absent by design" case. Corollary: a "missing expected tables" alarm must list only *included* tables that are absent; folding in by-design-absent excluded tables makes the alarm cry wolf every run and trains the reader to ignore a genuine missing-table event. The governing principle for a personal-data backup: it's the user's data — include unless it's a genuine secret or pure system scaffolding, and if you must skip something that exists, say so where they'll see it. <!-- Source: critic review, second-brain data-export PR1, 2026-06-22 -->

- **When a feature ships ahead of a hand-applied migration, make its read path degrade to the PRIOR source (or null) when the new table is absent — never throw on a missing relation.** In a project where Supabase migrations are applied by hand (so a deploy can land code before its schema), a new DB-backed feature must not 500 the moment it runs against a database that lacks the table yet. second-brain #866 introduced a `data_sources` registry (migration `030`) but designed `DataSourceRegistry.getSpreadsheetId(kind)` to resolve enabled-row → env-var fallback → null with a never-throw contract: a missing table (migration not yet applied) or a transient DB error logs once and falls back to the env var, so the code is safe to deploy in EITHER order relative to the migration. This decouples deploy order from migration order and removes the entire class of post-merge 500s the manual-migration lag otherwise causes (a known failure mode — the previous source of truth, here env vars, becomes the graceful fallback layer). Pair with the standard "catch blocks only return defaults for EXPECTED errors" rule: `undefined_table` / relation-does-not-exist is an expected, migration-lag error to absorb; a connection failure or syntax error should still propagate. Also test the fallback arm explicitly (missing-table → env resolution), not just the happy path — the untested degradation branch was exactly what the fresh-context critic flagged as blocking. **STRENGTHENED — when the new table has no prior source to fall back to, degrade the READ path to a "run this SQL in Supabase" setup card that ships the exact setup SQL, and single-source that SQL so its three copies can't drift.** The second-brain admin series applied this shape twice: #901 (Jobs) and #902/#903 (message inspector) each create a hand-applied table with no legacy fallback, so the routes feature-detect the missing relation (`42P01`) and return `tableMissing: true` **with the exact setup SQL**; the panel renders a setup card instead of erroring, and everything that doesn't need the table (schedules, manual triggers) keeps working. Two refinements worth copying: (1) surface the setup SQL **in the UI**, not just a log line, so the owner can self-serve the migration; (2) **single-source the SQL as one exported constant** — #901 left it triplicated (schema.sql, migration file, `JOB_RUNS_SETUP_SQL`) and the review flagged the drift risk; #903 corrected the pattern by exporting one constant all consumers import. Split write vs read degradation by need: the 5a write path (#902) silently no-ops on `42P01` (a trace write must never break message handling), while the 5b read path (#903) surfaces the missing table so the route can show the setup card. <!-- Source: post-mortem, second-brain #866 (data-source registry PR-A), 2026-07-10; STRENGTHENED admin series #901/#902/#903, 2026-07-13 (setup-card + single-source-SQL + write-silent/read-surface split) -->
