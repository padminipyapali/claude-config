# Architecture Patterns

Cross-project learnings for service design, error handling, and system architecture.

## Service Layer Design

- **Optional services via env var presence.** When a feature depends on external credentials (bot token, API key, calendar service account), check env var presence at startup and skip initialization entirely when missing. Log the mode ("starting in dashboard-only mode") but don't fail. This enables deployment flexibility (bot-only, API-only, full-stack) without code changes or feature flags. <!-- Source: command-center D8, dashboard-only mode, 2026-02-15 -->
- **For single-user apps, service accounts > OAuth for external API access.** No consent screen, no token refresh, no callback URLs. The user shares their resource (calendar, drive) with the service account email. OAuth can be added later behind the same service interface.
- **Google service-account `calendarList` is EMPTY — resolve metadata via `calendars.get(id)`, not `calendarList.list`.** A service account reads shared calendars by id, but those calendars are NOT in its own subscription list, so `calendarList.list()` returns nothing for it (it works fine under OAuth2). To resolve calendar names under a service account, call `calendars.get({ calendarId })` per configured id (the `calendar.readonly` scope permits it). Colors live ONLY on `calendarList` (a per-user subscription property), so service accounts get names but NOT colors → fall back to a stable deterministic dot/color assignment when no color is present. Run the per-id gets via `Promise.allSettled` so one lost-permission id doesn't drop the others. Verification trap: a debug/verification script run under OAuth (e.g. your own `gcloud`/personal token) MASKS service-account-only failures — always verify integration behavior under the SAME auth model production uses. <!-- Source: adversarial review, second-brain #697, 2026-06-23 -->
- **For external-API services, your verification harness must use production's exact auth model.** A script that authenticates differently than production (OAuth vs service account, admin token vs scoped token) can pass while production silently fails, because permission/visibility surfaces differ per principal. <!-- Source: second-brain #697, 2026-06-23 -->
- **Google OAuth `calendar.events` scope reads/writes EVENTS but does NOT grant `calendarList.list` or `calendars.get` — it is NOT a superset of `calendar.readonly`.** Those calendar-metadata reads (names, colors) require the `calendar` or `calendar.readonly` scope; an events-only token 403s on them, leaving every event with an unresolved name (rendered as "Other"). A token's scope is fixed when minted, so re-mint with the full `calendar` scope to fix. The trap repeated from #697: a debug run under a DIFFERENT auth model (and mocked unit tests) both mask scope failures — verify OAuth-scoped integrations by hitting the REAL API with the REAL token under the SAME auth model production uses. (2nd escaped bug in this feature from not verifying under prod's real auth.) <!-- Source: adversarial review, second-brain #697 (OAuth scope), 2026-06-23 -->
- **Build hooks must not default to reading from user home directories.** Scripts triggered by `prebuild`/`predev` should never silently copy files from `$HOME` paths. If someone forks the repo and runs `npm run build`, it should not touch their personal files. Gate home-directory access behind an explicit env var (e.g., `INCLUDE_HOME_DOCS=true`). <!-- Source: PR review, command-center #41, 2026-02-27 -->
- **Build hooks should only depend on project-stack runtimes.** A Node.js project's `prebuild`/`predev` scripts should not require `python3`, `ruby`, or other runtimes not in the project's dependency tree. Use `node -e` for URL encoding, JSON manipulation, etc. instead of `python3 -c`. This avoids CI failures in Node-only environments. <!-- Source: post-mortem, command-center #41, 2026-02-27 -->

## Express / HTTP Server

- **Cap `express.json()` body size on public APIs.** The default limit is 100kb. If your endpoint only accepts a short string (e.g., 200-char topic), set `express.json({ limit: '8kb' })` to prevent request-amplification attacks that waste memory/CPU parsing large bodies before validation rejects them. <!-- Source: PR review (CodeRabbit), leaflet #8, 2026-03-09 -->
- **Don't leak upstream error.message to clients — apply to ALL routes.** When sanitizing error responses, apply the same pattern to every catch block, not just the primary route. It's common to fix the main endpoint but miss secondary routes (e.g., image proxy, webhook). Generic client message + detailed server-side log. Mechanical check: grep for `error.message` in res.json() calls across all route handlers. <!-- Source: PR review (CodeRabbit), leaflet #8, 2026-03-09 -->
- **Re-arm SSE timeouts on each chunk, not just the first.** When an SSE stream has a generation timeout (e.g., 15s), clearing it on the first received chunk leaves the client unprotected if the stream stalls mid-delivery. Re-arm the timeout on every `onPageGroup`/`onChunk` callback: `clearTimeout(timeout); timeout = setTimeout(onStall, TIMEOUT_MS);`. Only clear definitively in `onDone`/`onError`. Without re-arming, a partial stream (group 1 arrives, groups 2-3 never come) leaves the UI stuck on the streaming screen indefinitely. <!-- Source: PR review (CodeRabbit), leaflet #32, 2026-03-11 -->
- **SSE disconnect: listen on `res.on('close')`, not `req.on('close')`.** In SSE endpoints, `req.close` fires when the request body is fully consumed (immediately for GET/small POST), NOT when the client disconnects. `res.close` fires when the response connection terminates — the correct signal for SSE cleanup (aborting in-flight API calls, freeing resources). Using `req.close` leaves background work running after the client navigates away. <!-- Source: PR review, leaflet #30, 2026-03-11 -->

## Async Initialization

- **Bind HTTP listener before slow async init on container platforms.** Railway, Kubernetes, and ECS health check probes expect the port to accept connections within seconds. Call `app.listen()` right after creating the app (with health/readiness routes already registered), then initialize services (bot connections, external APIs) afterward. Express/Fastify/Koa all support adding routes dynamically after the server is listening. <!-- Source: command-center fix/railway-host-bind, 2026-02-15 -->

- **Close persistent resources (SQLite, DB pools) on ALL exit paths.** Container orchestrators send SIGTERM before SIGKILL. Add `process.on("SIGTERM", ...)` handlers that close DB connections, flush WAL journals, and exit cleanly. **Also close in `bootstrap().catch()` — if bootstrap fails after stores are initialized (e.g., during bot setup), the stores leak without explicit cleanup.** Use `try/catch` with empty catch for best-effort cleanup — the process is terminating regardless. Hoist the resource reference to module scope if it's created inside `bootstrap()`. Use optional chaining (`store?.close()`) so cleanup is safe even if the resource wasn't initialized yet. <!-- Strengthened: PR review, command-center #33, 2026-02-20 -->
- **SIGTERM handlers must await in-flight async work.** When buffered operations (debounce timers, batch queues) hold unprocessed data, the SIGTERM handler must flush them with `await Promise.allSettled(pendingPromises)` before exiting. Fire-and-forgetting the flush means data loss on deploys. Pattern: have buffered operations return Promises, collect them in a module-scoped array, and `await Promise.allSettled(...)` in the SIGTERM handler. <!-- Source: PR review (CodeRabbit), second-brain #407, 2026-03-08 -->

## Concurrency & Task Queues

- **Sequential task queue (concurrency 1) for rate-limited external APIs.** When tasks hit external APIs with strict rate limits (Claude API, GitHub API), use a queue with max concurrency 1 and auto-advance on completion. This prevents rate limit errors and ensures predictable execution order. A simple in-memory queue is sufficient for single-instance deployments; persist to DB only if tasks must survive restarts. <!-- Source: command-center D004, 2026-02-14 -->

## In-Memory State & Process Restarts

- **In-memory dedup markers don't survive restarts.** On deploy-on-push platforms (Railway, Vercel, Heroku), every deploy clears memory. Schedulers and notification systems using in-memory state (e.g., `lastSentDate`) will re-trigger on every restart. Either persist the marker to DB, or initialize defensively by checking whether the scheduled time has already passed.
- **Defensive initialization over persistence for simple cases.** If a scheduler's dedup marker is a date string, pre-set it in the constructor when the current time is past the trigger hour. Simpler than a schema change, though it can't distinguish "first startup of the day" from "restart after already sent" — acceptable when at-most-once is better than spam.
- **In-memory caches need TTL and size caps.** An unbounded `Map` used as a cache is a slow memory leak in long-running services. Even for single-user apps, cached entries become stale (e.g., revoked auth tokens, re-linked accounts). Use a TTL (e.g., 5 minutes) and a max-size cap (e.g., 1000 entries with oldest-first eviction). A simple `{ value, expiresAt }` wrapper around Map is sufficient -- no library needed. Check expiry on read, evict oldest on write when at capacity. **When enforcing a size cap, evict expired entries BEFORE checking capacity** — otherwise expired entries count toward the cap and block new writes until the periodic cleanup fires. Pattern: `this.evictExpired(); if (this.map.size >= this.maxSize) return null;`. <!-- Source: PR review, second-brain #234, 2026-02-25; strengthened: PR review (CodeRabbit), command-center #94, 2026-03-08 -->
- **Dedup guard before debounce timer, not after.** When using a debounce pattern with deduplication (e.g., webhook retry prevention), check the dedup set BEFORE resetting the timer. If the dedup check happens after the timer reset, retried duplicates keep pushing the flush timer forward indefinitely, delaying processing. Pattern: `if (alreadyProcessed(id)) return;` → then `clearTimeout` / `setTimeout`. <!-- Source: PR review (CodeRabbit), second-brain #407, 2026-03-08 -->

## Single-User / v0 Persistence

- **Atomic JSON-file state store as a v0 substitute for a database.** For single-user CLI tools and v0 prototypes, a JSON file with atomic writes is sufficient persistence — no database, no migration runner, no schema infrastructure. Three load-bearing details: (1) write to a temp file in the same directory then `fs.rename` (atomic on POSIX, prevents torn writes on crash); (2) use a stable partition key (e.g., ISO `weekKey` like `"2026-W17"`) so concurrent or repeat invocations idempotently target the same record; (3) place the file in a user-scoped directory (`~/.app-name/state.json`), not the repo. Defer the database migration until multi-user or multi-host is on the roadmap. <!-- Source: post-mortem, family-digest #12, 2026-04-22 -->
- **Display-only terminal states keep the canonical payload stable for downstream stages.** When a feature has user-facing terminal transitions (approve / cancel / archive) but a downstream stage will act on the same payload, model the transition as display-only: update a user-visible marker (Telegram message prefix, email subject tag, UI badge) without mutating the canonical body. The downstream stage then reads the unchanged authoritative content. Generalizable to any approve/edit/cancel flow that has a separate authoritative consumer (PR 2c approve → PR 2d send). <!-- Source: post-mortem, family-digest #12, 2026-04-22 -->

## Data Integrity

- **Pass all relevant fields at document/record creation time.** Don't assume data can be looked up later or leave fields empty for future population. The record should be complete when created — empty fields create permanent data inconsistencies that require manual data fixes.
- **Carry all fields through pipeline stages — audit at each transform.** When data passes through multiple stages (buffer → synthetic message → handler → service), audit each transform to verify all fields survive. Fields captured in early stages (e.g., per-item captions in a media buffer) are easily dropped when constructing intermediate representations (e.g., synthetic IncomingMessage). After adding a field to any stage, grep forward through all downstream consumers and intermediate types. <!-- Source: PR review (CodeRabbit), second-brain #407, 2026-03-08 -->
- **Consistent treatment of related domain types across ALL calculation paths.** When multiple types share the same semantics (e.g., sick/vacation/holiday hours all count as PTO), ensure ALL paths (canonical calculation, PDF export, UI summary) treat them identically. Independent calculation paths drift apart over time — adding a new type to one path but not others is a common source of bugs.
- **Consolidate entity creation into a single shared service method.** When multiple code paths create the same entity type (e.g., entries from Telegram, web, or promotion), use one shared creation function. Independent creation paths inevitably diverge — some will miss required fields (status initialization, embeddings, metadata). This complements the "complete at creation" rule by providing a structural enforcement mechanism. <!-- Source: BUG-W007, second-brain, 2026-02-14 -->
- **Prepare-then-replace for re-indexing operations.** When re-indexing a dataset (embeddings, search index, cache), prepare ALL replacement data before deleting existing records. If any preparation step fails (embedding API timeout, network error), skip the replacement entirely to preserve the existing index. Pattern: (1) prepare all new records into an array, (2) if any failure → skip and log, (3) delete existing records, (4) insert all prepared records. The anti-pattern is delete-then-prepare, which leaves the index empty on partial failure. <!-- Source: PR review, second-brain #237, 2026-02-24 -->

- **When client and server generate independent IDs, capture the server ID before downstream server operations.** If `saveEntityToServer()` is fire-and-forget and the server generates its own UUID (e.g., `gen_random_uuid()`), any subsequent server call using the client-generated ID (e.g., saving a child record with a foreign key) will fail the ownership check. Either: (1) await the server save and capture the returned ID, or (2) store the server ID in a ref/variable via `.then()` and guard downstream calls on its availability. The anti-pattern is fire-and-forget parent creation + immediate child creation using the local ID. <!-- Source: PR review (CodeRabbit), leaflet #40, 2026-03-14 -->

- **Collect errors in bulk update loops instead of silently continuing or failing fast.** When a route applies N updates in a loop (e.g., sync results, batch operations), wrap each iteration in try/catch, collect failures into an `errors[]` array, and return HTTP 207 (Multi-Status) with the partial result + errors. Silent continuation returns false success; fail-fast on the first error loses already-applied updates. Pattern: `const errors: string[] = []; for (const item of updates) { try { apply(item); } catch (e) { errors.push(...); } } if (errors.length) res.status(207).json({ ...result, errors });`. <!-- Source: PR review, command-center #67, 2026-03-02 -->

## Auth & Security Boundaries

- **Scope auth fallbacks to the specific routes that need them.** When adding an alternative auth mechanism (query param token, cookie, API key header), restrict it to the exact route that requires it — never apply it globally in middleware. The temptation is to add the fallback once in shared middleware for simplicity, but this broadens the attack surface to every route. Use route path matching (`req.path`) and method checks (`req.method`) in the middleware to gate the fallback. <!-- Source: PR review, second-brain #152, 2026-02-17 -->
- **Express `router.use()` middleware runs for ALL requests matching the mount path, not just matching terminal routes.** When multiple routers are mounted at the same path (e.g., `app.use("/api", routerA)` and `app.use("/api", routerB)`), requests traverse middleware from all routers in mount order — even if only one router has a matching route. Auth middleware on routerA will execute for requests that only routerB handles. To scope middleware to specific routes, either mount routers at distinct sub-paths or attach middleware directly to route handlers (`router.get("/x", auth, handler)`). <!-- Source: PR review, second-brain #251, 2026-02-25 -->
- **Validate JWT issuer for defense-in-depth.** When verifying JWTs locally (e.g., Supabase JWT via `jose`), validate both `audience` and `issuer` claims. The shared HMAC secret already scopes trust, but issuer validation rejects tokens minted by other services that happen to share the same signing key. Make issuer optional (only checked when the issuer URL is configured) so environments missing the config don't break. <!-- Source: PR review, second-brain #234, 2026-02-25 -->

## Error Handling Strategy

- **Fire-and-forget needs visibility.** Log at the decision point ("split returned N items"), not just the error path. Silent success is as bad as silent failure for debugging.
- **Fire-and-forget side effects AFTER the primary operation succeeds.** When a fire-and-forget call (e.g., `markAsInitiated().catch(...)`) is a side effect of a primary async operation (e.g., `await startResearch()`), place it AFTER the primary succeeds — not before. If the primary fails, the side effect leaves the system in an inconsistent state (entry marked but no task running, item flagged but no record created). Pattern: `await primary(); sideEffect().catch(logErr);` — never the reverse. <!-- Source: PR review, second-brain #211, 2026-02-23 -->
- **Guard user-facing notifications on DB rowCount.** When a DB UPDATE with a WHERE guard (e.g., `WHERE status NOT IN ('DONE', 'FAILED')`) precedes a user notification, check `result.rowCount > 0` before notifying. If the UPDATE matched 0 rows (task already completed or cancelled), the notification would mislead the user. The error log can fire unconditionally for debugging, but user-facing messages must only fire when state actually changed. <!-- Source: PR review, second-brain #211, 2026-02-23 -->
- **Wrap post-stream persistence in its own try/catch.** When DB writes happen after SSE data is already sent, catch failures and emit a warning event.
- **Split try/catch for non-transactional sequential DB operations.** When two DB writes aren't wrapped in a transaction, use separate try/catch blocks so users get accurate feedback about what succeeded. If op A succeeds but op B fails, returning a generic "failed" error is misleading — the first write already committed. <!-- Source: PR review, my_mind_evolved #76, 2026-02-14 -->
- **Surface secondary operation failures as warnings, don't silently swallow.** When a multi-step creation has a primary record (entry) and a secondary record (status/metadata), don't `catch` the secondary failure and ignore it. Return a `{ result, warning? }` shape so the caller/UI can inform the user ("TODO created but status record failed"). Silent swallowing creates invisible data inconsistencies. <!-- Source: PR review, second-brain #102, 2026-02-15 -->
- **A generic user-facing failure reply ("Something went wrong") that HIDES the underlying provider error makes production bugs undiagnosable — surface the real status/reason (safely, no secrets/PII), don't swallow it into a catch-all.** second-brain #837 (the multi-delete hardening half): "delete all shelo events" failed with a blanket "Something went wrong" that swallowed the exact Google error, so the real cause (stale recurring-instance ids) was invisible from the reply and the bug could only be diagnosed by re-running with a probe. Both live calendar-write bugs in this session were opaque for exactly this reason — a top-level generic catch-all reported failure without WHY. The fix added `describeWriteError()`, which walks the error's `cause` chain (Gaxios wraps status at `err.response.status`, not `err.code`, and it survives a `new Error(..., { cause })` wrap — see the Gaxios entry above) and surfaces the real status + reason (e.g. "403 forbidden", "410 gone") in the user reply, bounded to avoid a cyclic-cause loop. Reusable rule: a user-facing error reply for an operation that calls an external service (Google/Stripe/Twilio/an LLM) must carry the provider's real failure reason, not a generic string — the generic message is undiagnosable in production, and the underlying status is exactly what tells the user (and you) whether it's a permission problem, a stale id, a rate limit, or a genuine outage. Guardrails: (1) walk the `cause` chain and check the provider's real status field (`response.status` for Gaxios), bounding the walk; (2) surface the status + short reason, NOT the raw error object (which can carry tokens/PII/stack) — map to a safe human sentence; (3) the swallow-and-generic-reply anti-pattern is the same failure as swallowing a secondary op (above), one level up: it's the PRIMARY op's failure being hidden from the user. **RECURS at the AUTH-EXPIRY axis, second-brain #850 (2026-07-04): the live bot answered "what do I have next Monday" with the generic `Something went wrong fetching your calendar` — indistinguishable from a transient blip — when the actual cause was the bot's Google OAuth REFRESH TOKEN being expired/revoked (`getEventsForRange` threw `All N calendar fetch(es) failed`, each per-calendar `reason` a GaxiosError carrying `invalid_grant` / "Token has been expired or revoked", so all 12 calendars failed at once). This is the SAME undiagnosable-generic-reply anti-pattern as #837, one class further: not "which provider status" but "this whole integration's credential is dead and no retry will fix it." The fix generalizes the #837 shape to a CLASS-SPECIFIC actionable reply: `isAuthExpiry(err)` walks the cause chain (including the ARRAY cause `{calendarId, reason}[]` and each reason's nested GaxiosError, bounded 6 deep, cycle-safe) and matches ONLY the `invalid_grant` signature — checking the structured `response.data.error === "invalid_grant"` field FIRST, then the message text — deliberately NOT a bare 400/`invalid_request`/500 so a transient can never masquerade as auth-expiry; on a match, every calendar-fetch surface returns a distinct `CALENDAR_AUTH_EXPIRED_REPLY` ("the Google connection has expired and needs to be reauthorized") instead of the generic string. The distinction from #837's `describeWriteError`: a transient blip and a dead credential need DIFFERENT user actions (wait-and-retry vs. reconnect), so a failure class the user must ACT ON differently deserves its own detected-and-named branch, not a status dump. Reusable rule: beyond surfacing the provider status, when a failure class implies a distinct USER remedy (reauthorize, top up quota, fix a config) — especially a terminal one no retry resolves (expired/revoked credential, exhausted quota, disabled account) — DETECT that specific class narrowly (match the authoritative structured field, not a broad status, so you never over-fire on a transient) and return a message that names the remedy, turning a silent recurring outage into a self-diagnosing one. Same cause-chain-walk mechanics as #837 (bounded, cycle-safe, checks the provider's real structured field). <!-- Source: post-mortem, second-brain #837, 2026-07-01; recurs at auth-expiry axis second-brain #850, 2026-07-04 -->
- **Distinguish a per-target "already gone" (404/410) from a batch FAILURE in a multi-delete: an idempotent delete's success state IS "no longer exists," so a 404/410 on one target should count toward deleted, not fail the whole batch — but keep single-delete conservative.** second-brain #837: "delete all shelo events" hit 12 recurring instances, some of whose ids were STALE (gone between the proposal and the confirm-tap); the original batch treated each 404/410 as a target failure and reported the whole delete as failed. Because delete is idempotent — the goal state of "delete X" is "X does not exist" — a per-target 404 (not found) or 410 (Gone; Google returns it for already-cancelled instances) means that instance is ALREADY in the desired state, so it counts as deleted, making stale ids structurally impossible to fail a batch on. The scoping guardrail that keeps this from masking real problems: the 404-as-success is MULTI-DELETE-BATCH-ONLY and is a non-destructive REPORTING edge (it changes what you tell the user, not what you delete); the SINGLE-delete path stays conservative ("no longer exists, try again") because there a 404 more likely means the user's mental model is stale and a silent success would be confusing. The fully-correct fix (re-resolve each recurring-instance id at commit time so the id is never stale in the first place) is a separate, heavier change tracked as a follow-up — the batch tolerance is the safe, shippable interim. Reusable rule: for an idempotent destructive op run over a batch, a per-item "target already in goal state" (404/410 on delete, 409/"already exists" on an idempotent create) is a SUCCESS for that item, not a batch failure — but gate this to the batch path and keep the single-item path conservative, and only apply it to the REPORTING outcome, never to skip a genuine mutation. <!-- Source: post-mortem, second-brain #837, 2026-07-01 -->
- **A self-attendee RSVP (decline/accept/tentative) is a DISTINCT operation from delete — an attendee declining an invite must NOT fall into the organizer's delete branch, and the RSVP write must PRESERVE every other attendee's responseStatus.** second-brain #837 (the decline/RSVP half of #834): the calendar-write path had create/update/delete but no RSVP, so "decline date night 7/16" was mis-routed to a DELETE and failed — because the user is an ATTENDEE, not the organizer, and can't delete someone else's event. The fix branches on identity: organizer → cancel/delete (declining your own event deletes it); attendee → `respondToEvent`, which reads the event, finds the SELF attendee (Google's `attendee.self === true` flag — no stored account email needed), sets only that entry's `responseStatus`, and patches the event back via `events.patch`, leaving every co-attendee's RSVP untouched. Two data-safety invariants a test must lock down: (1) the patched attendee array preserves all OTHER attendees' responseStatus exactly (assert the full 3-attendee array, not just the self entry — a naive rebuild that re-emits `{email, responseStatus}` for everyone would clobber co-attendees' RSVPs to the default); (2) an attendee-decline can NEVER reach the delete branch (the organizer/attendee discriminator is what routes it, and it must be tested on both roles). General shape: when a "respond to a shared resource" op (RSVP, approve, acknowledge, react) mutates one participant's slice of a multi-participant record, patch only that slice and prove the others survive byte-identical — and make sure the op is routed distinctly from the destructive op it superficially resembles (decline≠delete). <!-- Source: post-mortem, second-brain #837, 2026-07-01 -->
- **googleapis/Gaxios errors carry HTTP status at `err.response.status`, not `err.code` — and survive a `cause` wrap.** When a service wraps a provider error as `new Error("...", { cause: gaxiosErr })`, a downstream consumer trying to classify a 404 must walk the `cause` chain AND check `response.status` (the GaxiosError shape), not only `code`/`status` on the top error. Match all three (`code === 404 || code === "404" || status === 404 || response?.status === 404`) and bound the walk (e.g. 5 hops) to avoid a cyclic-cause loop. Prove the real provider shape with a fixture test, not just a synthetic `{ code: 404 }`. <!-- Source: adversarial review, second-brain calendar-write PR3, 2026-06-20 -->
- **Write/delete operations on multi-calendar setups must target the event's own `sourceCalendarId`, not a default write calendar — and a 404 from the wrong calendar masquerades as "already deleted."** When events can live on multiple calendars (e.g. a primary + a dedicated nanny/shared calendar) but the write service hardcodes a single `writeCalendarId`, a `delete`/`update` against the wrong calendar returns a Google 404 that is indistinguishable, at the call site, from the event genuinely being gone — so the user sees "that event no longer exists" for an event that plainly exists. The fix is to thread the event's calendar provenance (`sourceCalendarId`, already known at resolution time) end-to-end to the write call (`deleteEvent(id, calendarId ?? writeCalendarId)`), never re-deriving it. Checks: (1) any time you resolve/ground an event and later mutate it, verify the resolved calendar id survives every hop (intent → persisted metadata → parse-back → commit) and isn't dropped by a destructure/whitelist; `?? defaultCalendarId` keeps back-compat when absent. (2) A 404/"gone" mapping on a write is only trustworthy if the write hit the SAME calendar the event was read from — otherwise classify wrong-calendar/permission errors separately. (3) Routing to the right calendar is necessary but not sufficient: if the OAuth credential has only READ access to that calendar, Google still returns 403/404 — distinguish 403 (permission) from 404 (truly gone) before telling the user it was deleted. Recurring-instance deletes are unaffected when the candidate fetch uses `singleEvents: true` (instance ids `<master>_<instanceStart>` thread untouched and delete only that instance). <!-- Source: post-mortem, second-brain #744 (calendar cancel/update target), 2026-06-25 -->

## Result Types & Dependency Injection

- **Discriminated unions for expected failures.** For expected failures (bad auth, invalid payload, not found), return `{ ok: true, payload }` or `{ ok: false, status, error }` rather than throwing. This makes expected failures explicit in the type system. Pattern-match on `result.ok` — no catch blocks for control flow. Reserve exceptions for truly unexpected errors. <!-- Source: second-brain DECISIONS -->
- **Context injection: config via constructor, not `process.env`.** Services receive configuration (HMAC secret, API key, DB pool) through their constructor, not by reading `process.env` directly. Keeps wiring concerns in the composition root (`server.ts`). Makes services trivially testable without env var manipulation. Corollary: when a value is injected via `deps` (e.g., `deps.userTimezone`), don't also read the raw env var at the usage site as a fallback (`deps.x || process.env.X || default`). The injected value already resolves from the env var — the extra fallback is redundant and creates a hidden dependency that can diverge. <!-- Source: second-brain DECISIONS; strengthened: PR review, second-brain #199, 2026-02-21 -->

## Pipeline Design

- **Dedup after normalization must check both raw and cleaned text.** When a pipeline normalizes content before storage (LLM cleanup, trimming, prefix stripping), dedup checks must run on BOTH the original input AND the normalized output. Two different raw inputs can normalize to the same cleaned text, creating duplicates if only the raw text is checked. <!-- Source: PR review, second-brain #109, 2026-02-15 -->
- **When a shared dedup collapses duplicates by a key (summary+start+allDay), adding a semantically-important TAG to some copies means the collapse can silently drop the tagged copy — make the tag WIN the collision, bounded to tie-breaking only.** second-brain #855: `getEventsForRange` runs a shared `dedupeAndSort` that collapses events matching on (summary, start, allDay) with **first-calendar-wins**. When the OOO feature tagged trips fetched from the OOO calendar, any trip ALSO present on the primary calendar with the same title ("Burning Man Week", "Padmini @ Hoffman") had its OOO-tagged copy DROPPED by the existing first-wins rule — so the new tag never reached the consumers and the feature was inert for the common duplicated-trip case (see process-patterns.md "gates-green but inert"). The fix ("Option B" OOO-aware dedup) made the tagged copy WIN on a collision, but deliberately BOUNDED: it never changes the event COUNT (still one survivor per key — it only changes WHICH duplicate survives), is byte-identical when the feature is unconfigured, and an opaque/real busy Home commitment keeps precedence so no genuine hold is silently un-blocked. Reusable rule: whenever you add a field/tag that MATTERS to some copies of records that flow through a pre-existing dedup keyed on OTHER fields, that dedup will collapse a tagged and untagged copy to whichever arrives first and can silently discard the one carrying the meaning. Change the tie-break to prefer the semantically-richer copy — but keep the change a pure tie-break (same output cardinality, no-op when the tag is absent, and preserve any higher-precedence signal) so you don't perturb the count or reorder unrelated records. Prove it with a 4-case test: collision→tag wins, back-compat unconfigured is byte-identical, non-colliding records untouched, and the higher-precedence edge (opaque-Home) still wins. <!-- Source: post-mortem, second-brain #855 (OOO-aware dedup, Option B), 2026-07-07 -->

- **Internally-tracked data deliberately stripped at an API boundary — plumb it through the public type when a feature later needs it, don't re-derive.** When an internal record carries a field used only inside a service (e.g. a `SourcedCalendarEvent` tracking `sourceCalendarId` purely to dedupe across calendars) and the public/return type intentionally drops it at the boundary, a later feature that needs that field should widen the public type and stop stripping it — NOT re-fetch or re-derive it downstream. Re-derivation means a second source of truth that can diverge from the original; widening the existing internal value into the public shape (and deleting the strip step) keeps one source. Check: when adding a downstream consumer that needs provenance/origin already known internally, grep the producer for a `...rest`/`omit`/destructure-drop that discards it before re-implementing the lookup. <!-- Source: adversarial review, second-brain #694 (calendar sourceCalendarId), 2026-06-23 -->
- **Extract repeated logic from switch/if-else branches into helper functions.** When 2+ branches in a switch statement contain the same code block (e.g., creating an ACTION entry with the same field mapping), extract immediately into a helper. Copy-paste across branches is the intra-function equivalent of copy-paste across files — the branches WILL diverge as individual cases get bug fixes. Mechanical check: after writing a switch, compare each branch's body. If any two share > 3 lines of identical logic, extract. <!-- Source: PR review, second-brain #187, 2026-02-20 -->
- **Utilities copied between files in the same directory WILL diverge.** When a helper (e.g., `getDayLabel`, `formatRelativeDate`) is duplicated rather than extracted, the two copies accumulate independent fixes and edge-case handling. Extract immediately on first duplication into a shared module. If you discover two copies differ (e.g., `"3 Days Ago"` vs `"Mon, Feb 17"`), treat it as a bug — audit which behavior is correct, unify, and delete the copy. <!-- Source: PR review, command-center #23, 2026-02-19 -->
- **Fallback/legacy paths must match primary path semantics exactly.** When a primary code path distinguishes sentinel values (e.g., `null` vs `undefined` for "no date" vs "run extraction"), the fallback path must preserve the same distinction — don't use falsy coercion (`if (!x)`) that collapses them. Similarly, when the primary path passes explicit parameters to a shared function (e.g., `{ channel: "IN_APP" }`), the fallback must pass them too — don't rely on defaults in one path but not the other. Divergence between primary and fallback paths is the #1 source of subtle bugs when consolidating code paths behind a service. <!-- Source: PR review, second-brain #197, 2026-02-20 -->
- **When capping API results, always surface truncation to the caller.** If a service limits results to N items (e.g., 100 per repo), the response must include a flag or count indicating truncation: `{ items, truncated: items.length === MAX }`. Without it, UIs silently show incomplete data with no way to warn users. When adding truncation detection to a new service, grep for sibling services — the pattern should be consistent across the codebase. <!-- Source: PR review, command-center #23, 2026-02-19 -->
- **A two-step resolve→confirm flow MUST persist the resolved set in the pending record; a clarify/question that persists nothing forces the confirmation to re-resolve and fail.** second-brain #768: deleting 12 recurring calendar events looped forever because the first step disambiguated the set, then asked the user to confirm via a `clarify` that persisted NOTHING (`entryId: null`). The user's "yes" had no resolved set to read, so it was re-classified fresh and re-resolved against the whole calendar — the exact ambiguous lookup the first step had already narrowed — and failed ("Which event did you mean? … hundreds of events"). Re-resolution can never reproduce the original narrow result, so the flow loops. The fix: a confident multi-match persists a pending carrying the FULL resolved set (`{googleEventId, sourceCalendarId}[]` + count), and the confirm step READS that set and executes it (loops the delete per target on its own calendar via `Promise.allSettled`) — it NEVER re-resolves. Generalize beyond calendar: the confirm step's job is to *execute the already-resolved selection*, not to re-answer the question. Same class as the schedule-todos pending, which persists the analysis map so each refine round diffs the latest rather than re-analyzing from scratch (see llm-integration.md EDIT-VOCABULARY rule). Checklist: any "resolve a set, then ask the user to confirm" path — assert the resolved set is in the persisted pending and that the confirm handler reads it (grep the confirm/intercept path for a re-resolution call; if it re-queries, that's the bug). Persist defensively (the stored targets are untrusted on read-back) and make the execute step idempotent (a `confirmedAt`/CAS guard) for at-most-once. <!-- Source: post-mortem, second-brain #768 (calendar multi-delete: persist the resolved set, confirm reads it, never re-resolve), 2026-06-27 -->
- **When a feature is "detect condition X, then act" but X is unreliably detectable, evaluate acting UNCONDITIONALLY with a conservative/idempotent action that no-ops on the negative case.** Such an action can *dominate* an unreliable detector: it never false-negatives (every case is handled) and has no effective false-positive (the negative case is left ~unchanged), so it reaches the goal the flaky classifier couldn't — and you delete the detector entirely. Two guardrails: (1) the action must be a genuine no-op on already-satisfied input (meaning-preserving / idempotent), and preserve the original where the action mutates user-visible data (write the transformed copy to a *separate* field, keep the source immutable, make it reversible); (2) any cost-side heuristic gate must be framed as "is it worth spending the expensive step?" — NOT as the detector. Mislabeling the gate a detector re-imports the exact correctness problem you removed. Validate detectability with a cheap feasibility probe BEFORE committing to the detect-then-act shape. <!-- Source: post-mortem, second-brain #762 (Wispr dictation: "always-clean, preserve original" replaced "detect dictation, then clean"; gate is a cost lever, not a detector), 2026-06-26 -->

## Sub-Agent Delegation

- **Always include adversarial review instructions for delegated agents.** Agents follow feature correctness but skip security/robustness review unless explicitly prompted.
- **Parallel agents must use separate branches/worktrees.** Shared checkouts cause "file modified since read" errors.
- **Separate fixer and reviewer agents.** The agent that wrote a `catch-all return []` won't question its own code. Use two-agent pipeline: fixer commits, then reviewer reviews.
- **When concurrent agents may be active in a repo, use a Task agent with `bypassPermissions` to apply all edits atomically.** Concurrent agents running builds, linters, or formatters can revert uncommitted file edits between individual Edit tool calls. Delegating all changes to a single Task agent that applies edits + builds + tests in one burst prevents interference. This is a workaround — the real fix is to always run the CLAUDE.md repo conflict detection protocol before starting work. <!-- Source: second-brain feat/calendar-command, 2026-02-16 -->

## Planning Discipline

- **State reset effects must re-populate for ALL paths.** When `useEffect` clears state on dependency change, every path that sets the dependency must ensure re-population.
- **Cross-channel regression testing.** When modifying shared data formats consumed by multiple output channels (web, Telegram, email), verify ALL channels still work. Same data, different display constraints — web can render rich HTML while Telegram has a 4096-char text limit. Add this to the PR checklist for multi-channel apps. <!-- Source: BUG-022, second-brain #101, 2026-02-15 -->

## Scheduling & At-Most-Once Delivery

- **State update BEFORE side effect for at-most-once delivery.** In schedulers that deliver notifications, update persistent state (e.g., `lastSentDate`) BEFORE the side effect (sending the message). If the server crashes after marking but before delivery, the user misses one notification rather than getting duplicates on every restart. At-most-once > at-least-once-with-spam for non-critical notifications. <!-- Source: BUG-T017, second-brain -->

## Shell & Data Pipeline Pitfalls

- **Off-by-one field indexes when prepending columns in awk pipelines.** When an awk script prepends a new field (e.g., `print session "|" $0`), all downstream awk commands that reference the original fields must shift their indexes by +1. If the original line had `timestamp|type|repo` as `$1|$2|$3`, after prepending session it becomes `session|timestamp|type|repo` = `$1|$2|$3|$4`. Missing this shift causes type-checking conditions (like `$2 == "commit"`) to compare against the wrong field (timestamp instead of type), silently producing zero matches and empty output. **Mitigation:** Comment the field layout at the top of each pipeline stage (`# Format: session|timestamp|type|repo|hash|subject`), and grep-verify one record before building the full pipeline. <!-- Source: sessions off-by-one bug, 2026-02-19 -->
- **`<<<` (here-string) appends a trailing newline.** In bash, `func <<< "$var"` feeds `$var` plus `\n` to stdin. If the function encodes stdin verbatim (e.g., `json.dumps(sys.stdin.read())`), the output includes the newline as data. Use `printf '%s' "$var" | func` instead to avoid the invisible trailing newline. This is especially insidious with JSON encoding — `json.dumps("hello\n")` produces `"hello\n"` which looks correct until it breaks downstream parsing. <!-- Source: sessions json_str bug, 2026-02-19 -->

## Pattern Consistency

- **When following an existing pattern, implement it fully or don't start.** If a codebase has cursor-based pagination implemented for list types A and B (with `loadMore` functions, cursor state, and UI triggers), adding list type C must include the same pagination support. Capturing the cursor from the API response without wiring the "load more" behavior creates dead state and gives the false impression that pagination is supported. Either implement the full pattern (state + load function + UI trigger) or explicitly skip cursor capture with a comment explaining why. <!-- Source: PR review, second-brain #164, 2026-02-19 -->

## Debugging Process

- **For race conditions: list observable states.** Write out the state tuple at each step and check which intermediate states trigger effects.
- **When NEW code "misbehaves," suspect the SHARED SUBSTRATE it sits on, not just the new code — a new feature is frequently the first caller that EXERCISES a pre-existing latent bug in a shared dependency, so the bug predates your diff even though your diff is where it first became visible.** second-brain #846 (slot-check): the new per-slot free/busy verdict over-blocked a slot whose only overlap was a "Tahoe" all-day event the user had marked Free (Google `transparency`). The instinct is to debug the new `checkSlots` math — but the actual cause was that NO free/busy path in the codebase respected the `transparency` flag: transparent ("Free") events were being counted as busy by the SHARED interval engine (`busyIntervalsForDay`), which the pre-existing "am I free" availability path ALSO used. The over-block was a latent bug in the shared substrate that had shipped in availability long before slot-check existed; slot-check was just the first path someone validated against a real calendar that happened to contain a Free-marked all-day trip, so it surfaced there first. The fix therefore belonged in the shared engine (thread `transparency` through `CalendarEvent → CalendarQueryEvent → AvailabilityEvent`, skip transparent timed events in `busyIntervalsForDay`), which fixed BOTH the new slot-check AND the pre-existing availability over-block in one change. Reusable rule: when new code produces a wrong result that flows through a shared primitive (an interval engine, a normalizer, a query builder, a serializer), before adding a guard IN the new code, check whether the SHARED primitive has the defect and whether OTHER existing callers are silently wrong the same way — fixing the substrate fixes every caller at once and stops you from patching a symptom in one call site while the root cause keeps mis-serving the others. Pairs with the validate-first-against-real-data rule (the real-calendar probe is what exposes a shared-substrate bug that opaque-only unit fixtures never trigger) and the sibling-sweep-a-semantic-concept rule (once you find the substrate bug, sweep every consumer of that primitive). <!-- Source: post-mortem, second-brain #846, 2026-07-02 -->

## Deployment & Vendor Config

- **Prefer committed dispatchers over vendor dashboard `startCommand` overrides.** When multiple services share a Docker image and run different entry points (e.g., a long-running webhook vs. a cron-fired send job), put role selection in a committed wrapper script that reads an env var, not in a per-service dashboard textbox. Dashboard overrides can silently drop on redeploy and the failure mode is invisible until the cron fires and runs the wrong program. The committed wrapper is diff-reviewable and version-controlled. <!-- Source: post-mortem, family-digest #33, 2026-05-11 -->
- **One-way cron failures need an external success monitor.** A cron that quietly runs the wrong binary (or hits a recoverable error and exits clean) won't alert anyone. For weekly/non-critical crons, add a separate "did the expected log line appear / email arrive" check on a different schedule. Otherwise outages can run for multiple cycles before anyone notices. <!-- Source: post-mortem, family-digest #33, 2026-05-11 -->
- **A Google OAuth app left in "Testing" publishing status FORCE-EXPIRES its refresh tokens every 7 days — a recurring weekly total outage for any long-running service that uses it; the durable fix is publishing the consent screen to "In production."** second-brain #850 (OPERATIONAL root cause, not a code bug): the bot's Google Calendar integration went fully dark once a week — every calendar fetch failing at once with `invalid_grant` / "Token has been expired or revoked" — because the OAuth consent screen was still in "Testing" mode. Google intentionally expires refresh tokens issued by a Testing-status app after 7 days (also caps ~100 test users), so a server that stores one refresh token and relies on it indefinitely will lose calendar/Drive/Gmail access on a 7-day clock, re-minting only papering over it until the next cycle. Two-part remedy: (1) IMMEDIATE — re-authorize (run the OAuth setup script → paste the new refresh token into the host's env, here Railway → redeploy); (2) DURABLE — publish the consent screen from "Testing" to "In production" in the Google Cloud console so tokens stop expiring on the Testing clock (an internal/personal app can also use "Internal" if under a Workspace org). Diagnostic tell: a whole Google integration that works, then dies ~weekly with `invalid_grant` on EVERY call at once (not a per-call 403/404), points at token expiry, not code — verify by reproducing with the SERVICE's actual stored token, and check the app's publishing status BEFORE assuming a code regression. Pairs with the "detect the auth-expiry class and reply with the remedy" rule in Error Handling Strategy (the code-side surfacing) and the Testing-mode note in google-oauth ops. <!-- Source: post-mortem, second-brain #850, 2026-07-04 -->

## Selection & Sampling Logic

- **Random-reject sampling loops must never be the correctness boundary for "exhausted."** A bounded "pick random, reject if invalid, retry N times, else give up" loop can declare a pool exhausted while valid items still exist — the miss probability is `(1 - hits/total)^N`, which is high precisely when few valid options remain among many candidates (e.g. ~57% false-negative for 1 valid pair among C(10,2)=45 with N=25). This is most dangerous near genuine exhaustion, which is exactly when a wrong "nothing left" answer is user-visible. **Fix:** keep the random probe as a cheap fast-path, but before declaring exhaustion do a *deterministic exhaustive scan* of the candidate set (it's small by definition near exhaustion) and only fail if that finds nothing. **Test the miss path explicitly** — force the random probe to always return an invalid pick so the deterministic fallback is what succeeds; a test that only checks the happy path would pass even if the retry budget were 2. When a JS-side scan duplicates a SQL `WHERE` rule (e.g. gender compatibility), extract a shared predicate so the two can't drift. <!-- Source: baby-name-picker matchmaker coverage-first redesign, 2026-05-27 -->

## External Lookups & Derived Values

- **Plausibility-bound any number derived from an external lookup before display, and gate the lookup on whether its input is actually valid for it.** A drive-time feature passed the raw calendar `event.location` straight into a geocoder (Nominatim `limit=1`, no confidence threshold) + router (OSRM); a Zoom/Meet URL or a bare room name fuzzily geocoded to an arbitrary far-off point and OSRM returned a ~42h drive rendered as `(2552 min drive)`, while `Math.round(seconds/60)` with no floor rendered a sub-minute hop as `(0 min drive)`. Two coupled fixes: (1) **GATE** — detect inputs that aren't a routable physical address (meeting links, room names) and skip the lookup entirely (reuse the app's existing meeting-link detector rather than a new heuristic); (2) **BOUND** — clamp the derived number to a plausible range INSIDE the service (suppress `< 1` and `> a sane cap`, return `null` + `console.warn` on the cap) so every current and future caller inherits the guard instead of each call site re-checking. A best-effort external estimate must never render a confidently-wrong value — a low-confidence geocode/route is worse than no annotation. Sibling-sweep all call sites AND all render sites of the raw input (the same URL was also shown verbatim in several other places). <!-- Source: second-brain #773 (drive-time geocodes meeting URLs → bogus durations), 2026-06-27 -->

## Save-before-offer beats short-circuit-and-restore for confirm flows

**Pattern (second-brain #961 PR-B, 2026-08-14).** When a detected message triggers a "do you want X?" confirmation with inline buttons, there are two ways to keep the user's text safe:

1. **Short-circuit and restore** (the earlier source-connect flow): skip the normal save, stash the original text in the pending record, and re-save it if the user cancels. This has a hole — *if the user never taps anything, the message is never saved at all* — which is usually patched with an expiry sweep job.
2. **Save first, then offer**: persist the message exactly as it would have been persisted without the feature, THEN send the offer. On accept, delete the auto-saved copy.

Prefer (2). There is no window in which the text exists nowhere, an ignored offer costs nothing, and **the sweep job disappears entirely** — the sweep in (1) is pure accidental complexity created by the short-circuit.

The cost is the mirror image and worth naming: on accept you must clean up the auto-saved copy, or the feature leaves a duplicate behind. Make that cleanup best-effort and *report it honestly* — if the delete fails, say "the original note is still in your feed" rather than claiming a tidiness you didn't achieve. A failed cleanup is untidy; a failed save is data loss. Never trade the second for the first.

**Corollary — don't stamp an idempotency marker on a condition that will resolve itself.** These flows stamp `confirmedAt` so a repeat tap is a no-op. But if the failure was "the table doesn't exist yet" (hand-applied migration pending), stamping makes the offer permanently terminal: the user can never tap Save again once the migration lands. Stamp on *decisions*, not on *transient infrastructure states*. Same rule for a thrown DB error.
