# Testing Patterns

Cross-project learnings for testing strategy, mocking, and assertions.

## Test Strategy

- **"Include tests" means flow-level tests.** Pure-function tests on extracted helpers cannot catch missing code paths.
- **Byte-identity anchoring for engines that wrap proven artifacts.** When building an engine whose job is to reproduce already-proven outputs (a template renderer over proven prompts, a build script over a frozen dataset), the highest-value tests are golden-master replays (template + original slot values → byte-identical proven output) plus parse/serialize round-trips on the real repo files. This doubles as a data audit: plush-press #15's strict parser surfaced two latent data bugs in existing files (`../`-prefixed attachment paths; invalid YAML in `story-page.md`) that no unit test would have found. <!-- Source: post-mortem, plush-press #15, 2026-06-10 -->

## Test Design

- **MUTATION-VERIFY any test written to pin a specific line: break the line, watch the test go RED, restore it. A green run only proves the test PASSES, never that it TESTS anything.** plush-press #312 deleted a Variations suite that held the only SceneCanvas-level assertion pinning `busy = renderBusy || tuneBusy || savingBackdrop` (`SceneCanvas.tsx:643`) and replaced it with a focused test in the render-flow suite. The implementer didn't stop at a green run: it **dropped `tuneBusy` from the composition, confirmed the new test FAILED, then restored it** — proving the test actually pins the seam rather than passing vacuously. This matters most in exactly the situation that produced it: a replacement test written to close a coverage gap left by a deletion, where a vacuous pass restores the *appearance* of coverage while the gap stays open — strictly worse than no test, because it stops anyone from looking again. Cheap protocol (seconds, no tooling): invert/delete the condition under test → run the single test → require RED → `git checkout` the file. Do it whenever a test's whole purpose is to guard ONE expression, and assert **both edges** of a boolean gate (the block raising AND lifting), since a test that only asserts the busy state passes against a permanently-stuck-busy component. <!-- Source: post-mortem, plush-press #312, 2026-07-16 -->
- **MUTATION-VERIFY says watch the test fail; these are the three ways a revert can pass ANYWAY. All three shipped in ONE PR with all four gates green, and none was catchable by reading the test.** plush-press #439 (a save-time garbage collector deleting paid, irreproducible renders — `docs/BUGS.md` BUG-022) drafted three tests that passed for the wrong reason; each was caught only by running the revert. **(1) Revert the SPECIFIC behaviour, not the whole feature — a whole-feature revert can SATISFY an assertion by deleting the machinery the assertion is about.** This is the subtle one and the one most likely to be new. A test asserted "no *Show all* toggle appears when nothing is hidden"; the obvious revert (remove the display cap entirely) also removes the toggle, so the assertion came out true for a reason unrelated to what it guards, and the test passed against code with the cap gone. The correct perturbation moves ONE knob and leaves the machinery standing — change the cap from 5 to 4 so a 5-item list now hides one, the toggle must appear, and the test fails as designed. Generalize: whenever the thing you assert the ABSENCE of is *rendered by* the feature you are reverting, a feature-level revert is guaranteed to pass and proves nothing; perturb a parameter instead of deleting the code path. Same trap for "renders no error banner", "emits no warning", "shows no badge". **(2) Make sure the fixture actually REACHES the condition — an off-by-one in the setup silently vacates the test.** A regression test for an 8-entry cap performed 9 operations from an empty start, which *builds* the list to 8 but never trims it (the cap first bites on the 10th), so it passed with the entire bug restored. If a test targets a threshold, START AT the threshold rather than somewhere that merely approaches it — and prefer the state the real production data is actually in (here: the operator's live pages sat at exactly 8, one operation from loss). **(3) Prove the failure mode is REACHABLE before asserting it does not happen.** A test asserted that a `p10-*` file is not misattributed to page `p1`, but the `-` separator already made that impossible, so the naive implementation passed; the real ambiguity was ids that legally contain dashes (`p1` vs `p1-alt`). An assertion about a bug that cannot occur is decoration. **Report per test whether you watched it fail** — a test table with a revert column makes a vacuous test visible to a reviewer, while "all tests pass" actively hides it. **Why this outranks ordinary test hygiene: a vacuous test around a DESTRUCTIVE operation never fails loudly later — it sits green while data disappears.** A vacuous test elsewhere eventually surfaces as a bug report; a vacuous test guarding a delete path surfaces as work the user cannot get back. <!-- Source: post-mortem, plush-press #439 (BUG-022), 2026-08-01; extends the MUTATION-VERIFY rule above (plush-press #312) -->
- **When a CONTRACT change flips an existing assertion, sweep EVERY test twin that encodes that contract — the commit/unit-level test AND the interceptor/integration-level test live in different files, and updating only the one in your diff leaves the other RED. And the merge gate must be the FULL suite: a filtered/path-scoped run that reports 0-failed will never see the untouched twin.** second-brain #837 (multi-delete hardening): the fix changed a contract — a per-target 404 inside a multi-DELETE batch flips from fail-the-batch to already-gone SUCCESS (a stale/already-cancelled recurring-instance id is a no-op success, not a batch failure). The implementer updated the commit-level test (`calendar-write-commit.test.ts`) to the new contract but left the interceptor-level SIBLING test still asserting the OLD fail-the-batch behavior, and their own gate ran a FILTERED subset that reported 0 failures. The independent fresh-context critic's FULL `npm test` run caught the 1 real failure; round 2 updated the stale twin. Reusable rule: (1) whenever you change what an existing behavior asserts (an error becomes a success, a throw becomes a fallthrough, a status code changes meaning), grep for every test that encodes that behavior across ALL test levels — unit/commit-level, interceptor/integration-level, and any golden-master — and update each; a contract lives in more than one test file. (2) Never trust a path-filtered test run (`vitest run <changed files>`) as the merge gate — run the full workspace suite, because the twin you forgot is by definition outside the files you changed. This is the test-twin axis of the sibling-sweep family. <!-- Source: post-mortem, second-brain #837, 2026-07-01 -->
- **JSDoc on test helper factories.** `create*` test helpers should document default values and override behavior.
- **Guard browser-only APIs (`ResizeObserver`, `IntersectionObserver`, `matchMedia`) with `typeof X === "undefined"` for jsdom.** jsdom does not implement these. An unguarded `new ResizeObserver(...)` inside a layout/effect throws on EVERY render under the test environment, turning the whole test file red and masking other failures behind a single cryptic error. Add `if (!el || typeof ResizeObserver === "undefined") return;` before constructing — the early return also makes the cleanup function (`observer.disconnect()`) unreachable, which is correct. Sibling-sweep every `new (ResizeObserver|IntersectionObserver)` in the component dir when adding one guard. <!-- Source: adversarial review, second-brain #676, 2026-06-21 -->
- **Tests use `vi.waitFor()` for async side effects.** When testing fire-and-forget patterns (`.catch()` call sites), the fire-and-forget promise resolves asynchronously even when mocks are synchronous. Assertions on those calls need a microtask flush before checking: `await new Promise(r => setTimeout(r, 0))`. Without the flush, the assertion runs before the mock is called, producing false negatives. `vi.waitFor()` is also acceptable but less explicit about the cause. This applies to any code that calls an async function without `await` (fire-and-forget) — the test must yield to the event loop before asserting on the mock. <!-- Strengthened: PR review, second-brain #246, 2026-02-25 -->
- **Restore mutated `process.env` in afterEach.** Tests that `delete` or override env vars can leak state into other test files. Capture the original value in `beforeEach`, restore it in `afterEach`. <!-- Source: PR review, second-brain #148, 2026-02-17 -->
- **`vi.mock()` specifier must exactly match the production import path.** In Vitest ESM, `vi.mock('./auth')` does NOT intercept `import ... from './auth.js'` — the mock registry matches by resolved module ID, and different specifiers can resolve to different IDs. Use the exact same string as the production import (including `.js` extension). Same applies to `vi.importActual()` and dynamic `import()` in tests. Mechanical check: diff each `vi.mock()` argument against the corresponding production `import` statement. <!-- Source: PR review, leaflet #21, 2026-03-10 -->
- **Untranspiled-ESM native modules break node-only Jest suites — map them to a hand stub via `moduleNameMapper`.** Expo/React-Native packages like `expo-haptics` ship untranspiled ESM, so the moment a production module that imports one gets pulled into a node-environment Jest suite, unrelated suites fail to parse it. When the dependency is a fire-and-forget side-effect with no return-value contract (haptics, analytics pings), the cheapest fix is a no-op stub file (`src/utils/testStubs/<pkg>Stub.ts`) wired through `jest.config.ts` `moduleNameMapper: { '^expo-haptics$': '<rootDir>/src/utils/testStubs/expoHapticsStub.ts' }` — faster than expanding `transformIgnorePatterns` to transpile the real ESM. Two guards: (1) the stub must mirror the FULL API surface the wrappers touch (e.g. `selectionAsync`, `notificationAsync` + `NotificationFeedbackType`, `impactAsync` + `ImpactFeedbackStyle`), or call sites throw on missing members; (2) keep the real behavior independently asserted in the dedicated wrapper test, which should use `jest.mock('<pkg>', factory)` — that takes precedence over `moduleNameMapper` within the file, so the mapper stub does NOT shadow it and the actual `impactAsync("Light")`/`notificationAsync("Success")` assertions still run. Verify empirically that the wrapper test still asserts the real calls after adding the mapper. <!-- Source: post-mortem, baby-name-picker #115, 2026-05-29 -->
- **A TypeScript Jest config (`jest.config.ts`) requires `ts-node` as an EXPLICIT devDependency for clean installs.** Jest parses `*.config.ts` via `ts-node`, which it treats as an optional peer — so a local `node_modules` that happened to pull `ts-node` in transitively will run tests fine, while a clean `npm ci` (CI) fails with `'ts-node' is required for the TypeScript configuration files`. Declare `ts-node` in `devDependencies` explicitly; never rely on transitive presence. General rule: before declaring a build/test command CI-ready, verify against a pristine tree (`rm -rf node_modules && npm ci`), not an accreted local one — "verified locally" ≠ "verified on a clean install." <!-- Source: post-mortem, baby-name-picker #150, 2026-06-02 -->
- **CI-parity for tests that shell out to a runtime the runner must supply (generalized beyond `ts-node` to ANY subprocess interpreter).** A jest/vitest test that invokes `python3`, `ruby`, `go`, etc. via `child_process` passes locally because the dev machine has the interpreter, but will fail on a CI runner that lacks it. The pre-push checklist for such a test: (1) is the interpreter guaranteed on the chosen runner image? `ubuntu-latest` ships `python3` (and `ruby`, `go`) by default — confirm against the runner's documented toolset, don't assume; (2) does the same project already have GREEN tests shelling to the same interpreter? Prior art is the strongest parity signal — baby-name-picker #169 cleared its `python3` subprocess test by confirming 4 existing tests already shell `python3` and CI was green; (3) is the invoked script dependency-free (stdlib-only)? A script importing third-party packages reintroduces the clean-install trap at the interpreter level (`pip install` not run on the runner); (4) does the subprocess call have a timeout so a hung interpreter fails fast instead of stalling the whole suite (#169 added a 30s `subprocess` timeout)? Same root cause as the `ts-node` trap — "the test passes locally" says nothing about whether the runner can supply the dependency — but the surface is broader than node config loaders. <!-- Source: post-mortem, baby-name-picker #169, 2026-06-02 -->
- **Annotate untyped test fixture factories with their target type so a new REQUIRED field fails at compile time, not at runtime.** baby-name-picker #170 added a required `softnessPreference` field to `TasteProfile`; an untyped `makeProfile()` fixture (returning an object literal with no `: TasteProfile` annotation) silently omitted the new field, and the gap only surfaced as a runtime crash inside a test rather than a `tsc` error. The critic caught and fixed the latent crash, but the durable fix is structural: annotate every fixture factory with its return type (`function makeProfile(): TasteProfile { ... }`), so the next required-field addition is caught by the type checker across ALL fixtures at once. Untyped fixtures are a silent exemption from the "grep every constructor of a widened type" sibling-sweep — the compiler can't help you if the fixture isn't typed. When widening a type, also grep for untyped factories producing it (`makeX`, `createX`, `buildX` returning object literals) and annotate them. <!-- Source: post-mortem, baby-name-picker #170, 2026-06-02 -->
- **Verify mock targets match the production code path.** When mocking a service method for a test, trace the test's assertion back to the production code to confirm the mock intercepts the correct method. PR #159 mocked `findTodosForDate` when the tested feature used `findAllOpenTodos` — the test would have passed vacuously or failed confusingly. This is especially common when a service has multiple similar-sounding query methods (findForDate, findAllOpen, findByStatus). <!-- Source: post-mortem, second-brain #159, 2026-02-19 -->
- **Assert full object shapes in test expectations, not just IDs or callbacks.** When testing structured output (inline buttons, API response objects, data integrity), assert the complete object shape including labels/text and field types, not just identifiers or key presence. Use `toMatchObject` with `expect.any(String)` / `expect.any(Array)` type matchers over `toHaveProperty` loops — the former catches type regressions and missing fields, the latter only checks existence. Partial assertions miss label regressions and field omissions. <!-- Source: post-mortem, second-brain #159, 2026-02-19; strengthened: PR review, summer-camps #3, 2026-02-28 -->
- **Test boundary values explicitly for threshold/gap logic.** When testing any algorithm that splits, groups, or compares against a threshold (time gaps, count limits, size limits), always include three test cases: (1) exactly at the threshold, (2) one unit below, (3) clearly above. A test covering only "clearly above" and "clearly below" misses off-by-one bugs at the boundary. This is the minimum required for gap-grouping, session-splitting, rate-limiting, and any comparison using `>`, `>=`, `<`, or `<=`. <!-- Source: PR review, command-center #23, 2026-02-19 -->

- **When a deterministic placer honors per-item preferences AND ordering constraints, test the COLLISION, not each in isolation.** An algorithm that both honors a per-item *preference* (time-of-day, affinity, locality) and enforces an *ordering constraint* (dependencies, precedence, must-run-after) has a latent bug class: the preference pass can satisfy the preference while violating the constraint — e.g. a "morning" dependent gets placed in a morning slot that falls *before* its afternoon-placed blocker ends. The fix is structural: enforce the constraint as a HARD FLOOR at PLACEMENT time (clamp each candidate's start to `max(slot_start, constraint_floor)` and reject slots that can't satisfy it), not merely as sort order — topological sort alone guarantees the blocker is *processed* first, not that the dependent is *positioned* after it in time. The test that catches this is the one where preference and constraint PULL IN OPPOSITE DIRECTIONS (dependent prefers an earlier-of-day slot than its blocker occupies); a suite that tests dependency ordering and time-of-day preference in separate, non-conflicting fixtures passes while the collision regresses. Assert the placed start times satisfy `dependent.start >= max(blocker.end)` across day boundaries, in the same fixture where the preference would otherwise win. <!-- Source: adversarial review, second-brain #709 (schedule-todos packer), 2026-06-24 -->

- **Test fixture must omit the property being tested for defaults.** When testing "defaults X to Y", the test fixture must NOT include property X. If `makeSession()` already sets `source: "agent"`, a test titled "defaults source to agent" is tautological — it tests the fixture, not the code. Delete the property from the fixture before calling the function under test so the defaulting logic is actually exercised. <!-- Source: PR review, command-center #34, 2026-02-21 -->

- **Fake timers with `shouldAdvanceTime: true` for React Testing Library.** Vitest fake timers (`vi.useFakeTimers()`) hang indefinitely with `@testing-library/react` because RTL uses `setTimeout`/`setInterval` internally for `waitFor` and cleanup. Pass `vi.useFakeTimers({ shouldAdvanceTime: true })` to let RTL's internal timers progress while still controlling time in your tests. Always pair with `vi.useRealTimers()` in `afterEach`. Without `shouldAdvanceTime`, tests that render React components with fake timers will freeze. <!-- Source: PR review, second-brain #186, 2026-02-19 -->

- **Test mutually exclusive UI states with both PRESENCE and ABSENCE assertions.** When testing UI states that replace one element with another (e.g., "Explore button" replaced by "badge when research is complete"), test cases must assert BOTH the presence of the new element AND the absence of the old one. Testing only presence misses cases where both render simultaneously. Pattern: assert `getByRole("button", { name: /explore/i })` fails (or use `queryByRole`), AND assert `getByText(/ready/i)` succeeds. This applies to any conditional UI branch where two elements are mutually exclusive (loading spinner vs. content, edit mode vs. view mode, error state vs. success state). <!-- Source: CodeRabbit review, second-brain #213, 2026-02-23 -->
- **When conditionally-rendered UI structure is gated by N independent booleans, enumerate the combinations — the happy path proves nothing about the collapse cases.** plush-press #325 built a grouped toolbar with separators that render only when their following group is non-empty, gated by `canTune × hasBackdrop × canReuse` (8 combinations). Correctness = "no stray leading, trailing, or doubled divider across ALL 8 states," which the happy-path test (all groups present) cannot show. The edge cases that actually guard the invariant were the collapse states: the first child is never a separator (art mode); a reuse-only bar (free group collapsed to one control) has no leading or trailing divider; a minimal `render | Tune` bar has exactly one separator. Rule: for structure driven by K independent gates, either enumerate the 2^K combinations or, at minimum, add a test for each boundary of the invariant (first/last child, single-group collapse, empty-group drop) — not just the fully-populated layout. This is the combinatorial extension of "each conditional UI branch needs its own test": a separator's correctness is a property of the whole gate space, not of one branch. <!-- Source: post-mortem, plush-press #325, 2026-07-19 -->

- **Test every error path in try/catch blocks, not just the primary one.** When a try block contains multiple `await` calls (e.g., `findUser()` then `linkUser()`), each can fail independently. A test for `findUser()` throwing doesn't cover `linkUser()` throwing -- both reach the same catch block but via different code paths. Write a separate test for each `await` that can throw, mocking the preceding calls to succeed and the target call to reject. This is especially important for linking/creation flows where the first call is a lookup and the second is a write. <!-- Source: PR review, second-brain #234, 2026-02-25 -->

- **Use specific patterns in negative assertions, not short substrings.** `not.toContain("View")` will break when any unrelated text contains the word "View" (e.g., "Weekly Review"). Use `not.toMatch(/View \d+ more in dashboard/)` or assert absence of the specific element/pattern you care about. The shorter the negative assertion string, the more likely it matches unintended content. <!-- Source: PR review, second-brain #276, 2026-02-26 -->

- **Test assertion depth: assert behavior, not just rendering.** For each test in a UI component suite, verify it asserts behavior (callback called with correct args, state changed, error displayed) — not just rendering (element in document). Tests that only check `getByText("Button label")` without simulating clicks or asserting callback invocations pass vacuously even when the interaction is broken. Mechanical check: for each `it()` block, verify at least one of: `toHaveBeenCalledWith`, `userEvent.click` + state assertion, `waitFor` + error text assertion. Pure presence-only tests ("renders X") should be the minority, not the majority. <!-- Source: CodeRabbit review, leaflet #36, 2026-03-12 (3 of 12 findings were this class) -->

- **Guard mock array access with `toHaveBeenCalledTimes` before indexing `mock.calls[N]`.** Accessing `vi.mocked(fn).mock.calls[0][0]` without first asserting `expect(fn).toHaveBeenCalledTimes(1)` gives an opaque `TypeError: Cannot read properties of undefined` when the mock wasn't called. The guard assertion gives a clear failure message ("expected 1 call, received 0") with the correct line number. Pattern: always assert call count before indexing into `mock.calls`. This applies to any mock introspection — `calls`, `results`, `instances`. <!-- Source: PR review, second-brain #324, 2026-03-02 -->
- **No non-null assertions (`!`) in tests — use explicit assertions instead.** `find(...)!` and `obj.field!` in tests produce opaque runtime crashes (`Cannot read property of undefined`) instead of clear test failures when data is malformed. Replace with nullable assignment + explicit assertion: `const item = list.find(pred); expect(item).toBeDefined();` then use `item?.field` or `item?.children ?? []` for safe access. This surfaces data problems as assertion failures with proper line numbers and messages. Mechanical check: grep test files for `!;` and `!.` non-null assertions. <!-- Source: PR review, summer-camps #3, 2026-02-28 -->

- **Lint-as-test against stale date constants in production entry points.** When a clock dep defaults to a literal `new Date("YYYY-MM-DD...")` ("simulated now" for test convenience), the CLI silently freezes once real time advances past that date. The fix is a regression test that (a) greps every production entry-point script (`scripts/*.ts`, `src/scheduler/*.ts`) for `new Date("20...")` literals and fails if any exist, and (b) calls the entry point's default factory and asserts the returned timestamp lies between two real-wall-clock samples taken around the call. Test-fixture date literals belong only in `__tests__/`. This converts "spotted by a human when the recap window looked wrong" into a unit-test failure. <!-- Source: post-mortem, family-digest #37, 2026-05-16 -->

- **Assert mock call parameters, not just call counts or response values.** When mocking a DB query or service call, asserting `toHaveBeenCalled()` or checking only the HTTP response is insufficient -- a regression that drops `user_id` scoping from a query would still pass. Assert the SQL shape (`expect.stringContaining('WHERE user_id = $1')`) and bind parameters (`expect.arrayContaining(['user-id'])`) to verify security contracts and data integrity. Pattern: `expect(mockQuery).toHaveBeenCalledWith(expect.stringContaining('INSERT INTO'), [userId, topic, ...])`. This is the DB-layer equivalent of "assert full object shapes" -- response-only tests miss internal contract regressions. <!-- Source: PR review (CodeRabbit), leaflet #22, 2026-03-10 -->

## Async Test Patterns

- **Negative async assertions need settle time.** Polling helpers like `waitFor` pass immediately for negative assertions ("should NOT have been called") because the condition is true from the start. Use an explicit timeout to let promises settle before asserting: `await new Promise(r => setTimeout(r, 50)); expect(mock).not.toHaveBeenCalled();`. Without the settle delay, the assertion passes vacuously even if the mock IS called a microtask later.

- **Hardcoded near-future dates in tests rot into the past and silently vacate assertions that gate on `> new Date()`.** A test that mocks a future due date/time and asserts a reminder/notification *was* created passes only while the hardcoded date is still ahead of the real wall clock. Once the date drifts into the past (production guard `if (remindAt > new Date())`), the side effect no longer fires and the positive assertion fails — or worse, a `not.toHaveBeenCalled()` sibling passes vacuously. Fix: either freeze the clock (`vi.setSystemTime(new Date("2026-02-01T00:00:00Z"))` / `vi.useFakeTimers({ now })`) so the relative offset is stable, or use a far-future sentinel like `2099-12-31` (sibling convention) for the mocked date. Audit sweep: grep test files for hardcoded `YYYY-MM-DD` dates feeding any path gated on `> new Date()` and confirm each is either clock-frozen or sentinel-dated. <!-- Source: adversarial review, second-brain #688 (CI date-rot fix), 2026-06-22 -->

## Mocking Pitfalls

- **Remove copy-pasted `vi.mock()` blocks that the test file doesn't use.** When creating a new test file by copying an existing one, dead mock blocks for unused modules (Firebase, auth providers, etc.) survive because they don't cause test failures. They add false coupling — if the mocked module's API changes, the dead mock breaks the unrelated test. Mechanical check: for each `vi.mock()` in a test file, grep the file for actual usage of the mocked module's exports. If none, remove the mock block. <!-- Source: CodeRabbit review, sleep-tracker #14, 2026-03-03 -->

- **File-injected/mocked tests cannot see bundler-runtime path bugs — any code that resolves paths relative to module location needs one smoke pass against the REAL dev server.** plush-press #25: `resolveRepoRoot` computed the repo root two-levels-up from the module dir; every unit/route test passed because tests injected paths or ran the module from its source location. Under `next dev`, Turbopack relocates the compiled module into `.next/`, so the root resolved inside the build directory and every books/prompts route 404'd — found only by driving the live dev server (Playwright/curl), not by the 175-test suite. Rule: for filesystem-resolution code in bundled apps (Next.js, Vite, webpack), the test gate is a real-server smoke (start `next dev`, hit one route that touches the resolved path); unit tests alone are a false green. Fix pattern lives in typescript-patterns.md (marker-directory walk-up). <!-- Source: post-mortem, plush-press #25, 2026-06-11 -->

- **Hand-rolled mock/recording clients for ASYNC interfaces must fail as rejected promises, never synchronous throws.** second-brain #878 (MCP write tools): a recording ApiClient stub simulated failures with `throw` inside a non-async method; real `fetch`-backed clients always fail as rejected promises. Tool handlers that call the client without an immediate `await` (or pass the promise along) behave differently under a sync throw — the mock exercised an error path the real client can never take, and would have masked a missing `.catch()`/try-scope bug as a passing test. Rule: when stubbing an interface whose real implementation is async, every simulated failure must be `return Promise.reject(err)` (or an `async` method that throws), and the critic should check mock failure MODE realism (sync vs async), not just failure values. <!-- Source: post-mortem, second-brain #878, 2026-07-10 -->

- **`vi.doMock` does not affect already-resolved static imports.** `vi.doMock()` only applies to subsequent dynamic `import()` calls, not modules already loaded via static `import` at the top of the file. If you import `Foo` statically and then `vi.doMock("foo-module", ...)`, the imported `Foo` still points to the real module. Either use `vi.mock()` (hoisted to file top) or manually override the dependency on the instance (e.g., `(obj as any).client = mockClient`). Dead `vi.doMock` blocks are common — they appear to work only because a manual override elsewhere does the real mocking. <!-- Source: PR review, command-center #40, 2026-02-27 -->

## Test Cleanup

- **Restore mutated browser globals in `afterEach` — `vi.restoreAllMocks()` does NOT undo direct property assignments.** When tests assign directly to browser globals (`navigator.clipboard = { writeText: vi.fn() }`, `navigator.share = vi.fn()`, `window.matchMedia = vi.fn()`), `vi.restoreAllMocks()` only restores Vitest-created spies/stubs. Direct assignments persist across tests, causing order-dependent flakiness. Fix: either (A) use `vi.stubGlobal('navigator', ...)` which integrates with Vitest cleanup, or (B) capture the original value in `beforeEach` and restore in `afterEach`. Never restore inside the test body — early failures skip the restore. Pattern: `let origClipboard: Clipboard; beforeEach(() => { origClipboard = navigator.clipboard; }); afterEach(() => { Object.defineProperty(navigator, 'clipboard', { value: origClipboard, writable: true }); });`. <!-- Source: CodeRabbit review, leaflet #36, 2026-03-12 -->

- **`vi.restoreAllMocks()` belongs in `afterEach`, never inside individual tests.** Placing `vi.restoreAllMocks()` at the end of a specific test is fragile — if the test fails or is skipped, mocks leak into subsequent tests. Move to `afterEach(() => { vi.restoreAllMocks(); })`. Same applies to `vi.useRealTimers()`, `vi.unstubAllEnvs()`, and any state restoration. General rule: cleanup that undoes test-specific mutations goes in `afterEach`, not in the test body. <!-- Source: PR review, second-brain #256, 2026-02-25 -->

## Mock Data Type Safety

- **Match exact types in mock data — `vi.fn()` bypasses type checking.** When constructing mock return values (e.g., `vi.mocked(service.query).mockResolvedValue({...})`), match the exact TypeScript type for every field. Common trap: `completedAt: new Date().toISOString()` produces a `string`, but the interface declares `completedAt: Date`. Tests pass because `vi.fn()` and `as unknown as` casts bypass compile-time checking, but the mock shape silently diverges from production data. If the implementation later accesses `.getTime()` or other Date methods, the test will fail with a confusing runtime error instead of catching the mismatch early. <!-- Source: PR review, second-brain #199, 2026-02-21 -->

## Fixtures vs. Live Product Data

- **For a parser/adapter over an EXTERNAL human-edited source (a Google Sheet, a scraped page, a third-party export), unit fixtures encode your ASSUMPTIONS, not reality — the load-bearing validation is a read-only probe against the REAL source before merge.** second-brain #772/#770 added `HouseholdSheetService`, a read-only live reader of the kids' master Google Sheet (nannies/doctors/schedules), modeled on the calendar adapter (batchGet over a `TAB_RANGES` map, 1hr cache, never-throws/`[]`-on-failure). The unit fixtures were all green and all *wrong about the real sheet*: the read-only probe against the LIVE sheet (run after the user enabled the Sheets API + re-minted with `spreadsheets.readonly`) caught THREE real bugs no fixture or code critic could have — (1) all four `TAB_RANGES` tab names were wrong (real tabs: `"Nannies"`, `"Pediatrician / Dentist"`, `"Daily Schedule - School (8-11:20)"`, `"Mira Daily Schedule - No School"`), so every getter would have returned `[]` in prod while every mock stayed green; (2) the Nannies tab has a title BANNER above the header row (header is not row 0), so a "row 0 is the header" parser mis-reads every column; (3) SECTION-BLEED — the Nannies tab continues into a 60+ roster below the 3 hired, so the parser had to stop at the first blank row or return the whole roster as "hired." All fixed pre-merge (TAB_RANGES remapped to the real titles, parser hardened to find the header below the banner + stop at first blank, +4 real-shape tests pinning the corrected behavior). The probe also surfaced a 403 first (Sheets API not enabled on the GCP project) — an environment blocker, fixed before the probe could run. **This is the external-source analogue of the LLM real-model-probe lesson** (see `llm-integration.md`: mocked-LLM tests prove your APPLY logic but assert nothing about the model's interpretation quality): swap "prompt interpretation" for "real source shape" — fixtures prove your parser applies its rules correctly; only a real read proves the rules match the source you don't control. **Rule:** when you build a parser/adapter over an external human-edited source, ship and run a read-only probe against the LIVE source as the explicit pre-merge gate; mocked tests pin the apply logic but can be 100% green and 100% wrong about tab names, header position, and section boundaries. Corollary: a critic reasoning *about code* structurally cannot assert this (it has no access to the real tab titles/banner/layout), so for an external-integration parser the real-data probe — not a code critic — is the load-bearing gate (record `adversarialCatchRate` as unmeasured, not fabricated). <!-- Source: post-mortem, second-brain #772/#770, 2026-06-27; external-source analogue of the llm-integration real-model-probe pattern -->
- **A real-data probe for a feature that GATES on a second live source must explicitly assert that source is NON-EMPTY for the real window — otherwise a "no data → flag everything / flag nothing" degenerate mode passes every unit test and ships silent noise.** second-brain #791 (nightly nanny-coverage gap check) filters timed Home commitments by whether a nanny shift on a SEPARATE coverage calendar overlaps them. The unit suite (29 tests) proves the interval subtraction is correct against fixtures, but it cannot prove the coverage calendar is actually populated in production — and if it were empty, the engine's correct-but-degenerate branch flags EVERY commitment as a gap (one Telegram line each), which no green fixture reveals. The validate-first probe against the LIVE calendar over the real next-7-days (12 commitments + 8 shifts → 3 genuine gaps; every in-shift commitment correctly produced no gap) confirmed three things a fixture cannot: output plausibility on real data, that the gating source is non-empty so the degenerate branch is dormant, and the exact calendar IDs for the PR's setup instructions. **Rule:** when a feature's behavior depends on a second live data source being present (coverage shifts, a busy-calendar, an allowlist, a reference table), the validate-first probe checks not just "does my logic compute the right thing" but "is the gating source populated enough that I'm not silently in its degenerate mode." The "empty gating source" branch deserves its own fixture test AND a real-data confirmation it isn't currently live. This is the gating-source dimension of the #772 probe-vs-fixture rule above. <!-- Source: post-mortem, second-brain #791, 2026-06-27; gating-source dimension of the #772 live-source probe rule -->
- **Validate-first applies to a BUG too, not just a feature: a diagnostic probe that REPRODUCES against real data AND QUANTIFIES before/after under each config both proves the root cause and proves the fix — and it routinely reveals a config-vs-code split the code-only view misses.** second-brain #808 (the "schedule my todos" false "fully booked" bug, #806): before writing the fix, the implementer ran a diagnostic probe against the user's REAL calendar, anchored to next week's actual weekdays, that quantified the 9 AM–6 PM free minutes under four configs — `busy=Home`(default) → 1965 free min (already fine), `busy=EMPTY`(the production trigger) → 0 min (the false "fully booked"), then **fixed**+`busy=EMPTY` → 60 min, **fixed**+`busy=Home` → 1965 min — and printed provenance (the "Shelo 8am–7pm" shifts resolve to a `sourceCalendarId` on the Nannies/coverage calendar, NOT Home). That single probe did four things a unit test cannot: (1) reproduced the exact symptom on live data (0 free min), ruling out a fixture that merely encodes the author's guess; (2) localized the trigger to the `busy=EMPTY` config (an empty/misconfigured `GOOGLE_BUSY_CALENDARS`), proving the bug is config-sensitive; (3) proved the fix lifts the bug under BOTH the broken config and the correct one (60 and 1965, neither is the degenerate 0); (4) surfaced that this is a **config-vs-code split** — the code fix makes coverage-exclusion robust regardless of config, AND the probe yielded a concrete Railway config recommendation (`GOOGLE_BUSY_CALENDARS` should be the Home calendar, or unset→defaults to Home; empty or a broad list including coverage calendars is the trigger). Re-running the same probe after the fix is the confirmation step. **Rule:** for a data-driven bug, the cheapest high-confidence gate is a probe that (a) reproduces the symptom against real data BEFORE the fix, (b) sweeps the relevant config dimension so you learn whether the trigger is code or config, (c) prints provenance (which calendar/source each blocking item came from) so the root cause is observed not inferred, and (d) re-runs post-fix to show the metric moved off the degenerate value under every config. This is the bug-side companion to the #772/#791 feature probes above: there the probe verifies a parser/gate against live shape; here it verifies a fix against a reproduced live symptom and partitions code-fix from config-fix. <!-- Source: post-mortem, second-brain #808, 2026-06-27; bug-side companion to the #772/#791 validate-first probe family -->
- **Never assert hardcoded snapshots of MUTABLE PRODUCT DATA against the live repo — build a controlled fixture instead.** In a local-first / filesystem-as-database app, the content directories ARE the product (the app and the operator add/change them constantly). Any test that reads live content and asserts an exact count, exact roster (`toEqual([...])`), or exact derived number couples the suite to data the product is designed to mutate — so doing the app's core job (adding a character, locking a plate) turns CI red, on `main`, with zero code change. plush-press: `characters.test.ts` asserted `slugs.toEqual(["cat","cow","mira","padmini","rambabu","rami"])` and `scenes.test.ts` asserted `busstop.platesComplete === 0`; committing real studio output (a new Dragon character + a locked bus-stop plate) made both stale and failed the whole `CI / studio` job. **Rule:** a "real repo (read-only)" test block may assert only STABLE INVARIANTS — exclusions (README/subdirs are filtered), structural identities (`slug === dir name` ⇒ slug has no `/`), bounds (`0 <= platesComplete <= 3` where 3 = the fixed angle count), and presence of LONG-STABLE anchors (an established locked backdrop, founding cast with committed hero images). Any assertion about an exact count/roster/derived-number, or about "a newly-added X shows up," belongs in a fixture block that builds its own temp tree via a `REPO_ROOT`/root override (`mkdtempSync` + cleanup) so the test controls the content it checks. Litmus test before committing a data-reading assertion: *"Will this break the next time the operator adds a character or locks a plate?"* If yes, it's an invariant-or-fixture, not a live snapshot. Corollary (caught by the critic on the very fix): a fixture test that mutates a SHARED root is itself latently brittle — give each content-mutating test its own isolated `mkdtempSync` root so sibling exact-roster asserts stay order- and parallelism-independent. **RECURRED 2026-07-20 (`recipeRefs.test.ts`): a live-repo block asserted `orphans.toEqual([])` — every crop key must have its file on disk unless in a hardcoded `DOCUMENTED_UNSEEDED` allowlist. Operator autosave commits added a `shalu-pini` recipe reference without its crop file, turning main red hours before PR #334, whose own CI run then inherited the failure (the PR was merged over a pre-existing red it did not cause — a merge-gate judgment call that only works when the failure is provably pre-existing on main; verify with a main-branch run list before merging over red). The exact-empty-set assert is the same live-snapshot class as the 2026-06-16 roster asserts: ‘no orphans in the live repo’ is a statement about in-progress operator content, not about the code under test. The allowlist escape hatch proves the coupling — each new in-progress character requires a test edit.** **RESOLVED for `recipeRefs.test.ts` by plush-press #335 (2026-07-20, ~20 min after #334's post-mortem recommended it):** the suite was converted to a constructed fixture — `mkdtempSync` facecrops dir + in-memory cast map with a deliberately-orphaned human (`shalu-pini`), a documented-unseeded human, an animal, and a hyphenated crop — proving the guard still flags a real orphan without touching operator data; all live-repo reads removed, and the `DOCUMENTED_UNSEEDED` allowlist treadmill with them. Two hygiene points from the fix worth reusing: (1) when a fixture wraps the guard in a local helper, that helper must still call the REAL production function under test (here `faceCropSlug`) — parameterize the data (dir, allowlist), never re-implement the logic, or the fixture tests a copy; (2) an urgent test-only CI unblock can legitimately declare-skip the production build gate in-worktree when `typecheck` (which compiles the test file, a superset) is green and the diff touches only `*.test.ts` excluded from the bundle. <!-- Source: incident + fix, plush-press CI-red-on-main, 2026-06-16; recurred recipeRefs/#334, 2026-07-20; resolved for recipeRefs by #335, 2026-07-20 -->

## Visual Verification of UI Fixes

- **To Playwright-verify a COMPONENT-level UI fix (layout/overflow/wrapping/spacing) without standing up the full backend/DB/auth, mount the REAL component + the REAL stylesheet in a throwaway Vite harness with mock props, and screenshot before/after.** second-brain #848 (EntryCard header overflow — tags pushing the star/delete icons off the card edge) was verified this way: a disposable Vite entry imported the actual `<EntryCard>` and the actual `App.css`, rendered it with a handful of mock entries (1-tag / 3-tag / narrow-300px), and captured screenshots on the un-fixed vs fixed CSS — the before showed the star clipped, the after showed all icons visible with tags wrapped to a second line, robust down to 300px. This is faster and more isolating than a full-app e2e run: no server, no seeded DB, no login flow, no navigation to the right screen — you exercise the exact component under its real styles, so the screenshot is trustworthy evidence the *rendered* fix works (a jsdom/RTL unit test asserts the DOM structure but CANNOT prove pixels don't overflow — CSS layout is invisible to it). **When to reach for it:** the bug IS the rendering (things overflow / overlap / mis-wrap / mis-align) and the component renders from props alone (no deep context/router/data-fetch coupling). **How:** temp Vite entry that imports the real component + real global CSS, hard-code representative mock props (including the edge shapes that trigger the bug — max tags, narrowest width, empty), `browser_take_screenshot` before and after the fix; delete the harness after (don't commit it). Pair with a unit test that pins the DOM contract (e.g. the new wrapper holds the capped chips + "+N", and renders with 0 tags) so the structural guarantee is permanent even though the screenshot is throwaway. This is the render-layer sibling of the live-data probes above: those prove logic against real *data*; this proves layout against the real *component + stylesheet*. <!-- Source: post-mortem, second-brain #848, 2026-07-03 -->

- **A `vi.mock` factory cannot reference top-level classes/variables declared in the test file — wrap them in `vi.hoisted()`.** `vi.mock` calls are hoisted above all other top-level statements, so a factory like `vi.mock("../api.js", () => ({ ApiError: MockApiError }))` throws `ReferenceError: Cannot access 'MockApiError' before initialization` when `MockApiError` is a top-level `class`/`const` — and the error surfaces confusingly at the *component's import line*, not the mock. Fix: `const { MockApiError } = vi.hoisted(() => { class MockApiError extends Error {...} return { MockApiError }; })` — vi.hoisted runs its callback during the same hoisting pass, so the value exists when the factory executes. Needed whenever a mocked module must export a class the code under test checks with `instanceof` (e.g. mirroring an ApiError so `err instanceof ApiError` branches work in tests). <!-- Source: second-brain #930, 2026-07-22 -->
