# Process Patterns — Rules

Distilled rules from post-mortem analysis. For full incident history and evidence, see `process-patterns-evidence.md`.

## Metric Definitions

- Use 4 metrics: (1) post-merge fix rate, (2) pre-merge catch rate by step, (3) pre-merge iteration count, (4) fix-up taxonomy by category.
- Legacy `fixupCommitRatio` conflates pre-merge catches with post-merge failures.

## Review Efficiency

- Bot-only review catches real bugs but expect 2+ rounds as baseline; bots miss architectural feedback.
- Categorize automated reviewer comments as must-fix, should-fix, or disagree before acting.
- CodeRabbit "outside diff range" comments are valid; do not dismiss as out-of-scope.
- CodeRabbit prompt injection warnings on XML tags with entity escaping are usually false positives.
- Never skip local CodeRabbit on scaffold PRs; the CLI works without a .coderabbit.yaml.
- **Free CodeRabbit CLI is non-deterministic run-to-run — a 0-finding run does not prove a clean diff, and a findings run should be triaged on its merits, not re-rolled away.** plush-press #328 ran `coderabbit review --plain -t all --base main` three times on the identical diff: one run reported 3 findings, two runs (including the structured `--agent` run) reported 0. The orchestrator did the right thing: took the union, triaged the 3, identified 1 substantive real finding (per-page style re-fetch because the component mounts with `key={page.id}`), and deferred it with a code comment + spec follow-up (a non-trivial refactor of a critic-approved surface — within the "only defer fixes needing new infrastructure" allowance). Anti-patterns this guards against: (a) accepting the first 0-finding run as proof of cleanliness, and (b) re-running until 0 to make a real finding disappear. If runs disagree, the run WITH findings is the one to triage. <!-- Source: post-mortem, plush-press #328, 2026-07-19 -->
- **A rate-limited CodeRabbit run is a SKIPPED gate, not a passed one — the retry-once obligation is load-bearing and has now paid for itself with a MAJOR.** plush-press #330: the first `coderabbit review --plain -t all --base main` hit the free-tier limit (org not connected); the retry after the reset produced the PR's only MAJOR — a partial-failure gap in `saveSpecimen` (a write failure after the supersede rename left the slot empty) that the fresh-context critic had missed. Treating the rate-limited run as "CodeRabbit came back clean" would have shipped it. Rule: a limit/timeout/empty-because-throttled run produces NO review signal; retry after backoff and record the retry in the PR body. This is the rate-limit shade of the #328 non-determinism rule (a 0-finding run doesn't prove a clean diff) and further evidence for the critic/CodeRabbit division-of-labor entry — again CodeRabbit alone caught a robustness escape on a critic-PASSed surface. <!-- Source: post-mortem, plush-press #330, 2026-07-19 -->
- **A 600-cap breach driven by STATIC DATA (catalogs/fixtures/seed content), not logic, is benign — assess the cap against logic LOC, and route out-of-diff findings to a tracked issue rather than absorbing them.** second-brain #880 (+1883/-3, 24 files, `/reflect` on-demand reflection) self-merged at ~3x the 600 LOC cap with 0 GitHub comments, 0 fix commits, and 0 post-merge escapes because almost all the bulk was a hand-curated 62-quote Philosopher catalog (data the one handler consumes), not new control flow — mechanically splitting data from its sole consumer would have added risk, not reduced it. Two supporting disciplines held the quality line: (a) the fresh-context critic ran a full pass and returned 0 must-fix — this is the *critic-ran-clean* shade of `adversarialCatchRate: null` (a strong clean signal, record it in the note, never collapse to bare null — see the "two shades" entry); and (b) the one out-of-diff finding (stale `ENUM_VALUES` in `export/docs.ts` missing 5 enum values) was filed as issue #879 rather than scope-crept into the PR, keeping the PR single-concern and the fix-up ratio honest. Reusable rule: when reviewing a cap breach, subtract static-data LOC before judging size; the review-risk denominator is logic surface, not raw diff lines. Pairs with the #693 layered-gate LOC-exception entry. <!-- Source: post-mortem, second-brain #880, 2026-07-10 -->
- **On a large security-sensitive backend PR, layered local-review lenses (per-module critic sub-agents + multi-round CodeRabbit + an explicit sibling-sweep) caught 100% of the real security/correctness issues PRE-merge, with zero post-push escapes — the layering is what made a 600-cap-exceeding PR safe to self-merge.** second-brain #693 (+3186/-11, 16 files, media-download + subprocess-exec + Markdown-rendering) self-merged with 0 GitHub-review comments and 0 post-merge fixes BECAUSE the pre-push gate was multi-lens, not single-pass: (a) **per-module critic sub-agents** reviewed each module against its own dominant risk (media = resource/OOM, pg_dump = credential handling, markdown = injection) rather than one generalist critic skimming all three; (b) **three CodeRabbit rounds** surfaced the two real security MAJORs (media OOM: 25MB cap enforced only AFTER `arrayBuffer()` buffered the whole body, so a hostile/redirecting server could OOM at x5 concurrency; pg_dump credential exposure: connection URL with password as the last argv element, visible via `ps`/`/proc/<pid>/cmdline`); (c) an **explicit sibling-sweep** of the first Markdown-injection fix found 6 MORE injection sites — including LLM-generated content (the inbox `ai_summary` from the email pipeline) where a model-emitted `\n## heading` or `- bullet` could forge document structure in the trusted backup. The lesson pairs with the existing "internal critic catches real bugs the checklist misses" rule: for a multi-concern security-sensitive PR, run a critic lens PER concern and treat the first injection/escaping fix as a sweep trigger, not a point fix. The 0-escape outcome at >600 LOC is evidence the layered gate substitutes for peer review on this risk class (see the LOC-exception and per-wave-lens entries). <!-- Source: post-mortem, second-brain #693, 2026-06-23 -->
- **Fresh-context critic and CodeRabbit have a MEASURABLE division of labor — keep BOTH; neither alone is sufficient.** Across the second-brain admin series (7 PRs, #892–#903, 0 post-merge escapes on any), the two lenses caught structurally different bug classes and each caught what the other missed. The **critic** caught **semantic-correctness** bugs that need a mental model of runtime behavior: env-presence ≠ feature-actually-initialized (#895 — a try/catch construction failure made an env-derived flag lie), classifier `durationMs` misattributed because a shared timer spanned upstream gates (#902), a stage hardcoded OK because `Promise.allSettled` always fulfils (#902), a client/server response-shape type mismatch (#901), and a mock-only SQL test gap where the route tests mocked the service so the real query went untested (#903). **CodeRabbit** caught **robustness / resource / test-quality** classes on a diff-local read: a secondary-fetch error that wiped already-loaded rows (#898 refetch-wipes-grid), an unbounded child process wedging a concurrency guard + a stream EPIPE bubbling to the process guard (#900), and a weak optimistic-assertion test (#892). Notable: on #898 and #900 the critic PASSed clean and CodeRabbit alone caught the escape — so a critic-only gate would have shipped a grid-wipe and a resource-wedge; on #901 CodeRabbit's one finding was a FALSE POSITIVE the critic correctly overrode. Reusable reading: score `adversarialCatchRate` honestly per PR (it ranged 0.0 at n=1..3 where CodeRabbit did all the catching, to 1.0 where the critic did) and DON'T conclude a 0.0 means "the critic is useless" — it means the findings on that slice were CodeRabbit-flavored; over the series the critic caught the class of bugs CodeRabbit structurally cannot. The graceful-degradation gap (critic missed refetch-wipes-grid on #898, then caught its sibling load-more-wipes-list on #903) is now a checklist item in `adversarial-review.md`. **STRENGTHENED — the division of labor recurred on consecutive plush-press Art Styles PRs #330/#333 (2026-07-20): on BOTH, the fresh-context critic caught semantic/latent-landmine findings (a hardcoded `castRefCount` that would silently break numbering when parked recipe refs return; provenance-sidecar loss) while CodeRabbit CLI alone caught the concurrency/consistency MAJOR (a two-snapshot `resolveStyleSpecimens` read that could leave an enumerated slot without its file path on #333; the partial-failure supersede gap on #330). CodeRabbit's diff-local read is reliably the lens that catches read-twice/TOCTOU-shaped races the critic's mental-model pass glosses — keep it mandatory even when the critic returns SHIP.** <!-- Source: post-mortem, second-brain admin series #892–#903, 2026-07-13; STRENGTHENED plush-press #330/#333, 2026-07-20 -->
- **Deliverable-first flow for generated-artifact work: produce and user-verify the physical deliverable BEFORE code review/PR.** When the PR's real product is a generated artifact (print PDFs, rendered exports, compiled assets), generate the artifacts and have the user verify them first, then run the critic on the generating code. The user validates what actually ships; the critic validates the machinery's edge cases (plush-press #7: empty `--only` silent no-op, typography normalization, .gitignore guard) and should independently re-derive critical constants (trim/bleed/spine geometry) so a verified output isn't accidentally right. This also lets content iteration (seven user caption rounds in #7) fold into the build without inflating review rounds — content feedback and code review stay decoupled. Keep the generated outputs untracked (.gitignore) with the regeneration command in the PR body. <!-- Source: post-mortem, plush-press #7, 2026-06-09 -->
- **Risk-graduate the review gate by a PR's blast radius, and pre-commit the escalation in the PRIOR PR's post-mortem.** second-brain #751/#752/#758 (the lean-scheduler A/B/C sequence): the additive/byte-identical slices (A = analysis-only, B = decisions-partition) shipped on the lightweight orchestrator gate with the fresh-context critic deliberately waved off; the slice that crossed into the **irreversible-side-effect path** (C = errand/admin batching that *creates calendar events* and touches the *commit path*) had the full fresh-context critic RE-INSTATED. The discriminator is NOT line count — it's **"does this PR create or mutate an external side effect (calendar event, email, payment, irreversible write)?"**; if yes, the lightweight waiver does not apply no matter how small. The load-bearing process strength was that PR-B's post-mortem **named PR-C as the escalation point in advance** ("PR-C touches the commit path and is being paused for a real critic"), and PR-C honored that written commitment — so the boundary was a pre-registered rule, not an ad-hoc judgment under velocity pressure. On C, the critic verified the four user-impacting invariants of the new code path (no overflow/double-booking — `firstFit` fits only within one free interval so a non-contiguous reclaim falls back to individuals rather than spanning a gap; member-id survival through persist→parse→commit; exactly one create-call per batched run, count==runs not members; byte-identical no-op path) and returned ship-ready / 0 actionable findings. Reusable rule: in a multi-PR sequence, classify each slice as additive/byte-identical vs side-effecting at PLAN time; route the side-effecting slice to a full critic; and write the escalation into the preceding PR's post-mortem so the next cycle inherits it as a commitment rather than re-deciding. <!-- Source: post-mortem, second-brain #758, 2026-06-26 -->
- **Risk-graduation is SYMMETRIC: step the gate back DOWN once the irreversible-side-effect slice is behind you — don't ratchet "once strict, always strict."** second-brain #759 (PR-D, the closing slice of the lean-scheduler A/B/C/D sequence): PR-C #758 had escalated to a full fresh-context critic because it *created calendar events* + touched the commit path; PR-D — which only changes WHICH todos are in the in-flight refine proposal (`numbersToIds` expands a batch number → all its `memberTodoIds`; `parseRefinableMetadata` preserves+validates them; `setDuration`/`addDependency` on a batch are documented intentional no-ops) and creates NO events (events are created later, only on confirm) — correctly returned to the LIGHTWEIGHT orchestrator gate (build/lint/test 2359 passed + adversarial marker + a focused diff verification of the remove-expansion and member-id preservation). The discriminator is the SAME in both directions — *does this PR create or mutate an external side effect?* — so the immediately-prior PR running a full critic does NOT make the next one need one; route each slice by ITS OWN blast radius. The sequence A (lightweight) → B (lightweight) → C (full critic, event-creating) → D (lightweight, refine-internal) is the reusable shape: escalate for the side-effecting slice, de-escalate for the internal ones that consume its seam. (The seam itself — PR-C persisting `memberTodoIds` on `numberMap` a PR in advance precisely so PR-D could expand a batch id → its members — is the multi-PR contract-first hand-off paying off as designed.) Outcome: 0 post-merge escapes; lean-scheduler complete (51→29 calendar items, −43% on real data). This is the de-escalation counterpart to line 19's escalation rule. <!-- Source: post-mortem, second-brain #759, 2026-06-26 -->
- **`unmeasured` adversarialCatchRate has two distinguishable shades — record WHICH in the note, never collapse them to a bare null.** Both "the fresh-context critic RAN and found 0 actionable findings" (`0/(0+0)` undefined, a STRONG clean signal) and "the critic was SKIPPED entirely" (no signal at all) correctly map to `adversarialCatchRate: null` per the metric-integrity rule (don't fabricate 1.0). But they mean opposite things about review coverage, so the `adversarialCatchRateNote` must state which case it is. second-brain #758 was the critic-ran-clean shade (full critic on the event-creating slice, 0 blockers / 2 NITs, 0 post-merge escapes); #751/#752 were the critic-skipped shade (lightweight gate). Without the note, a dashboard reader sees a run of `null`s and wrongly concludes "we never review." <!-- Source: post-mortem, second-brain #758, 2026-06-26 -->
- **Persistent agent-pair delta review for revision rounds: resume the SAME author + critic agents (via SendMessage) instead of spawning fresh ones.** When an already-reviewed artifact gets revised (resequenced spec, post-directive rework), resuming the original product/implementer agent and the original critic gives a cheap, targeted DELTA review rather than a full re-review — the critic knows what it already verified and reviews only the change. plush-press #8: the resumed critic ruled the v2 "strictly better than v1", found 5 real delta findings (2 majors/3 minors), and — notably — RETRACTED its own earlier severity call (the two-key-MVP risk it had flagged in round 1 was overstated), something a fresh critic re-deriving from scratch wouldn't know to do. Scope boundary: fresh context remains mandatory for the FIRST review of any artifact (author-reviewer identity collapse); the resumed pair is for subsequent rounds on the same artifact, where retained context is signal rather than bias. <!-- Source: post-mortem, plush-press #8, 2026-06-09 -->

## Session Start Discipline

- Run `/project-setup` on projects with code but no CLAUDE.md before any code changes.
- **A "main is broken" claim from continuation context must be verified against CI reality BEFORE acting — rebuild gitignored workspace deps first, then distinguish local-artifact failures from real ones.** second-brain #688: a "broad pre-existing break on main" (phantom `hasAiResponse does not exist on ApiFeedEntry` tsc errors + a `VITE_*` env build error) was reported and RE-REPORTED across PRs #683/#687 by successive agents reading it from continuation summaries instead of verifying — but MOST of it was a **stale local build artifact, not a real break**: `packages/shared/dist/` is gitignored, so a dependent package's local `tsc` compiled against an old `dist/` while CI (which rebuilds `shared` fresh) was always green. The genuinely-CI-affecting issues were only three small ones (an a11y biome rule, a stale test mock missing `starred`, a hardcoded reminder date rotted into the past). Concrete verification protocol when inheriting a "main is red" premise: (1) **rebuild every gitignored workspace dependency** (`npm run build -w <dep>` / the monorepo's `dist`-producing package) before trusting ANY local `tsc`/build failure in a dependent — a gitignored `dist/` goes stale silently and produces phantom type errors the CI never sees; (2) **check whether CI actually shows the failure** (`gh run list`/`gh pr checks`) rather than equating "my local gate is red" with "main is red"; (3) only failures that survive a clean rebuild AND appear in CI are real. This is the global "Do NOT trust continuation summaries about repo state — verify it yourself" rule made concrete for monorepos: a false "main is broken" premise survived three PRs purely by inheritance. Companion code-level lessons (date-rot sentinel, stale-dist rebuild, chained-`&&`-lint short-circuit) are in `docs/BUGS.md` BUG-034 on the project. <!-- Source: post-mortem, second-brain #688, 2026-06-23 -->
- **A stale worktree from a crashed session may hold near-complete, fully-accurate work — inspect and verify before discarding.** baby-name-picker #192: a worktree flagged "abandoned" (uncommitted derived-data changes, zero commits, no PR) turned out to be ~90% complete (43 enriched mythology names, pronunciations, a new test, rebuilt seed.db), and a fresh-context verification pass (deterministic rebuild + 14+ deity attributions independently web-verified + full test suite) found the data 100% accurate — salvaging it cost ~20 min vs. hours to redo. Protocol: on finding a stale worktree, (1) flag to the user, don't touch; (2) if resuming, treat it as untrusted input — verify via fresh rebuild + independent fact-checks + tests before committing; (3) check its allocation space (ids, migration numbers) against in-flight sibling branches before adopting it. <!-- Source: post-mortem, baby-name-picker #192, 2026-06-11 -->

## Planning Discipline

- Thorough planning reduces implementation rework to zero redesign commits.
- **Plans for UI redesigns must enumerate every visible surface by name with a screenshot or mockup reference per surface.** When a feature touches both a card-grid and a lightbox (or any two related-but-distinct UI surfaces), the user's feedback like "X looks bad" cannot disambiguate which surface they mean. The fix: in the plan, list each surface as a row in a table -- name, file path, mockup variant, before/after screenshot URL. During iteration, ask the user to point at a row when reporting a defect. Without this artifact, the agent will lock onto the most recently-changed surface and misroute fixes (PR #83: 2 rounds of "lightbox looks bad" feedback were actually about the CARD GRID, costing 2 extra implementer rounds). **For small PRs (<5 files, single primary surface), a Notes-section paragraph naming each affected surface plus deliberately-untouched siblings is sufficient -- the formal table is the >2-surface threshold (PR #84 used the lightweight version successfully: zero scope creep, zero user-iteration rounds).** **PROMOTED from advisory to MANDATORY at >2 surfaces or >8 files (PR #86 evidence): the orchestrator must refuse to dispatch the implementer for any plan that implies these thresholds without the table. PR #86 touched 16 files / 6 surfaces without the table and the critic's top two findings (cross-surface cache-sync + sibling-feature parity) were exactly the failure modes the table is designed to prevent up-front.** <!-- Source: post-mortem, remodel-hq #83 + #84 + #86, 2026-05-15/16 -->
- **Stacked-PR coordination protocol.** When two features will touch the same hook/files in series, declare them as stacked branches via `gh pr create --update-base` up-front rather than allowing the second branch to absorb a mid-flight rebase against the first's merge. PR #86 had to rebase mid-critic-round because PR #85 merged into main between rounds; both PRs touched `useInspoLibrary` / `useInspoNotes` / `inspoActionIcons`. Stacked branches let the second PR auto-rebase when the first lands. Choose sequential-merges-only (and block work on the second feature until the first merges) when the two features are independent. **Add/add conflicts on NEW files are a foreseeable stacked-PR collision: baby-name-picker #78 and #80 both *created* `NameCard.test.tsx`, forcing a manual add/add merge-conflict resolution on #80's rebase. When two stacked PRs will each add the same new file (common for a per-component test file both touch), base the child's new file on the parent's version up front rather than letting both create it independently.** <!-- Source: post-mortem, remodel-hq #86, 2026-05-16; strengthened baby-name-picker #80, 2026-05-28 -->
- **Mid-flight rebase detection at orchestrator dispatch time.** Before dispatching the implementer on a feature whose files overlap with recent main commits, run `git log HEAD..origin/main -- <shared-files>` and `git log main..HEAD -- <shared-files>` to surface in-flight conflicts. 30-second smoke; would have flagged the #85/#86 overlap before #86's critic round. <!-- Source: post-mortem, remodel-hq #86, 2026-05-16 -->
- **Rebase a stale feature branch onto current origin/main BEFORE running review gates, and re-run tsc afterward — intervening main commits cause silent type-level integration breaks the original author never saw.** A feature branch based on an older main, reviewed in isolation, can be green; but if main advanced and a newer commit added a sibling that depends on the unchanged shape of a type you widened, the merged tree fails to compile. baby-name-picker name-family-tree: the feature added a non-optional `familyJson` field to the `Name` type; an intervening main commit (undo-on-selection) had added a new `Name` mock in `gameStore.undo.test.ts` that the original feature work could not have updated, so post-rebase tsc broke on the missing field. Fix protocol: (1) commit feature work, (2) `git rebase origin/main`, (3) resolve conflicts — for GENERATED artifacts (sqlite `.db`, generated `.sql`) take main's side then re-run the build script rather than hand-merging binaries, (4) sibling-sweep every constructor of the widened type (`grep -rln '<adjacent-required-field>' src | while read f; do grep -q '<new-field>' "$f" || echo "MISSING: $f"; done`), (5) re-run tsc/lint/jest. The PR diff (`git diff origin/main..HEAD`) must show ONLY the feature, never a reversal of intervening main commits — if it shows deletions of unrelated files, the branch base is wrong. **Confirmed downstream: this exact break landed on `main` undetected — `gameStore.perGender.test.ts`'s `makeName` fixture was missing the required `familyJson` field, leaving `tsc` and that jest suite RED on `origin/main`. The #73 post-mortem did not catch that main had gone red; the next feature (baby-name-picker #78, pronunciation) inherited the broken gate and had to carry a one-line `familyJson: null` fixture fix to make the mandated check pass. Lesson: a red main can persist silently with no CI; either configure required `tsc`/jest checks, or run them against `origin/main` itself (not just the feature branch) before declaring a gate green.** <!-- Source: baby-name-picker name-family-tree finisher, 2026-05-28; strengthened baby-name-picker #78, 2026-05-28 -->
- **Mockup-driven UI work needs an explicit "what the mockup covers vs what it does NOT" section in the plan.** The mockup at `docs/mockups/inspo-lightbox-comments/` showed the lightbox redesign but not the grid card layout. When user feedback drifted to the grid (vote pill placement, unicode glyphs), there was no plan artifact saying "grid is out of scope, file a separate issue" -- so the implementer absorbed scope creep into the same PR (3 fix commits for grid concerns). Plans referencing a mockup must declare mockup coverage boundaries. <!-- Source: post-mortem, remodel-hq #83, 2026-05-15 -->
- **An APPROVED mockup can encode a false BEHAVIORAL premise, and mockup-approval is NOT behavior-verification — a mockup is a hypothesis about what a feature does, so verify its premise against real prompts + real data + the live app before (and after) building it.** This extends `verify-premise-before-building` from code to design artifacts. plush-press #318 (scene toolbar): a mockup was designed AND approved by the operator, and the initial implementation faithfully encoded its rule — hide "Reuse this backdrop" when the page used a library-picked backdrop (`!freeScene && !!page.sceneBase`), on the plausible-sounding theory that "the backdrop is already saved." That premise was wrong: Reuse doesn't re-save the picked plate, it sends the RENDERED art to Gemini and paints the cast OUT, producing a NEW backdrop that has drifted from any source plate — valuable even on picked-backdrop pages. The wrong rule would have hidden Reuse on all 11 pages of the operator's real book, destroying the feature's main use. TESTS DID NOT CATCH IT (they were green — they tested the wrong rule faithfully). It was caught only by: (a) inspecting real project data (11 picked-backdrop pages), (b) the implementer flagging the premise unprompted, (c) reading the ACTUAL Gemini extract prompt to learn what Reuse really does. Rule corrected to `canReuse = hasArt && !alreadyReused`. Second, deeper tell: the SAME mockup depicted Save and Reuse coexisting — but the wrong hide-rule was the exact logical complement of Save's show-rule (`Save` gates on `hasBackdrop`; wrong Reuse gated on `!hasBackdrop`), so the approved mockup depicted an UNREACHABLE UI state. A mockup showing two controls together that your gating logic can never co-render is a signal the logic misunderstands the feature. Reusable checks: (1) before implementing a hide/show/enable gate lifted from a mockup, write down in one sentence WHAT the gated feature actually does at runtime and confirm it against the real prompt/handler, not the mockup's caption; (2) for any two controls a mockup shows together, verify your predicates permit that combination — a mockup depicting an unreachable state means either the mockup or a predicate is wrong; (3) green tests over a mockup-derived rule prove only internal consistency with the mockup, never that the mockup's premise is true. <!-- Source: post-mortem, plush-press #318, 2026-07-19 -->
- **Verifying a UI WORKS at one convenient state is not verifying it MATCHES INTENT across the state space — a design's visual/responsive correctness lives in a *space* (viewport widths, gate/prop combinations), so drive the axes that pressure the layout AND render the result side-by-side with the approved mockup before calling it done.** plush-press #325 fixed a regression #318 shipped, and BOTH escaped defects were the same root: single-state, works-not-matches verification. (a) The fused `✨ Re-render page` pill blobbed into a tall ellipse at narrow widths (label lacked `white-space: nowrap`, so under width pressure it wrapped to 3 lines and `border-radius: 999px` clamped the tall box) — but #318 was checked live at ONE wide viewport where the label happened to fit on one line, so the width-pressure-only blob was never seen. (b) #318 shipped the toolbar as loose pills instead of the approved mockup's single contained grouped bar — invisible because the result was never held against `docs/mockups/scene-editor-actionbar/toolbar.html`. The #325 fix loop caught both ONLY by (1) rendering the real CSS at 1280/1024/900/768/620px in both modes, and (2) rendering side-by-side with the mockup. This layers onto the "populated-state / N render-contexts" rule (#28/#31/#37 above) and the mockup-false-premise rule (#318 above): the axis here is CONTINUOUS (width) and COMBINATORIAL (independent gates), not a single alternate context. Reusable checks: (1) for any responsive UI, verify at multiple widths that include the narrow/pressured end, never one convenient wide sample — layout blowouts and text-wrap blobs only appear under pressure; (2) hold the built result against the approved mockup pixel-side-by-side, because green tests prove the controls WORK, never that the layout MATCHES the design; (3) when you fix a class of bug (a blob), sibling-sweep every element sharing the susceptible property — the class has more than one entry point (panel-stretch AND label-wrap were two paths to the same blob). <!-- Source: post-mortem, plush-press #325, 2026-07-19 -->
- **Never pipe a gate/CI command (test, lint, typecheck, build) through `tail`/`head`/`grep` — the pipeline's exit code is the LAST command's, so a RED suite exits 0 and reads as PASS.** plush-press #325: the implementer reported "test PASS" while the full vitest suite was actually red (1 failure), because it ran `npm test | tail` — `tail` exited 0 and masked vitest's non-zero exit. A real failure was hidden by a pipe. Rules: (1) run the gate bare (`npm test`) and read ITS exit code / summary line, not a truncated tail; (2) if you must pipe for readability, capture the real status with `set -o pipefail` or check `${PIPESTATUS[0]}` (bash) — never trust `$?` after a pipe; (3) a "PASS" claim from a gate is only credible if the actual pass/fail summary line (e.g. `Tests  N passed`) is quoted, not paraphrased. This is grep-able in a transcript: any `npm (test|run lint|run build|run typecheck) \| (tail|head|grep)` is suspect. <!-- Source: post-mortem, plush-press #325, 2026-07-19 -->
- **Mid-flight spec changes relayed to a running implementer need explicit supersession plus a final-state check against the authoritative pick.** When the user changes a spec mid-implementation (e.g., band vs no-band on a cover), a later message can land while an earlier, now-superseded instruction is still being executed; the implementer has no way to know which wins. plush-press #5: a superseded "bare text" spec message landed mid-run and the cover shipped as bare text before being corrected back to the band the user actually picked — caught only by comparing the implementer's verification report against the user's final mockup pick, costing one extra round. Protocol: (1) when relaying a spec change, state explicitly "this supersedes <prior instruction>"; (2) before dispatching the critic, the orchestrator diffs the implementer's verification report against the authoritative source of truth (the user's final pick / mockup variant), not against the message stream. Rendered mockup variants with a user pick (B + F in #5) are an effective authoritative artifact for this check. **Strengthened at higher volume: when MULTIPLE additions arrive while the implementer is mid-task, individual SendMessage relays repeatedly CROSS with the implementer's progress reports (each side acting on a stale view of the other). plush-press #11: FOUR mid-flight user scope additions crossed with implementer reports; resolved by sending ONE consolidated "outstanding checklist" ping enumerating every open item — the implementer reconciled it against work already done (verified rather than re-built, and correctly no-op'd a duplicate task assignment). Protocol addition: after 2+ scope additions to a running implementer, stop relaying piecemeal; send a single consolidated outstanding-items checklist and have the implementer report per-item DONE/PENDING against it. - **Validate-first MUST run under the ACTUAL failing IDENTITY/credential, not the developer's own — a success under YOUR auth proves nothing about whether the bot/service can do it, and is exactly how you misdiagnose a CODE bug as a permissions/config issue (or vice-versa).** second-brain #837: "delete all shelo events" failed, and the owner could delete those same events by hand from their own Google account — which is the trap, because it *feels* like proof the events are deletable. ## Follow-Up Discipline

- Post-push findings should become their own focused follow-up PR rather than being deferred to a tracker or bundled into the next feature.
- Multi-finding follow-up PRs work just as well as single-finding ones; fix all post-mortem findings atomically.
- Infrastructure gaps identified in post-mortems should be addressed in dedicated, same-day tooling PRs.
- **Recommendation drift across consecutive PRs is the dominant post-mortem failure mode.** When a post-mortem recommendation does not land before the next PR ships in the same project, escalate it from prose recommendation to a project artifact (PR template file at `.github/PULL_REQUEST_TEMPLATE.md`, CI workflow file, lint rule, hook). ## Scope Decisions

- **A feature-removal PR's grep sweep is a NAME collision surface, not a work list — before deleting any hit, partition the sweep by OWNING FEATURE and state which partitions are out of scope.** plush-press #312 (remove the ✨ Variations feature, +30/−638, 7 files, 0 post-merge fixes) swept for "variation" and got ~100 hits — **the majority of which belonged to `descVariation` / "same-place backdrop variation" in `CreateScene`, a SEPARATE and still-live feature that merely shares the English word.** A keyword-blind delete (the natural failure mode when the task is phrased as "remove everything named X") would have destroyed a shipped, unrelated feature. The sibling-sweep convention caught it, and the PR body named the surviving partition explicitly so a reviewer could confirm the boundary. Reusable rule: on any removal PR, the sweep output must be triaged into (a) hits owned by the doomed feature → delete, (b) hits owned by a DIFFERENT feature that shares the token → **explicitly out of scope, named in the PR body**, and (c) hits on genuinely SHARED infrastructure → keep, with the sharers enumerated (see the shared-CSS rule in UI/CSS Gaps). Deletion tasks invert the usual sibling-sweep risk: normally the sweep exists to find MORE places to fix, but on a removal it exists to find places you must NOT touch — the same grep, the opposite conclusion. The tell that triage is needed: the hit count is wildly larger than the feature's own file count (~100 hits for a 5-file feature). <!-- Source: post-mortem, plush-press #312, 2026-07-16 -->
- **On a removal PR, the shared-infrastructure question ("what else uses this?") must be asked of EVERY artifact the feature touched, and the honest answer is often "delete nothing."** plush-press #312's surprise finding: `scene.module.css` needed **ZERO changes** — every class Variations rendered with (`tunepanel`, `tuneToggle`, `tunenote`, …) is shared with PageTune, ReuseBackdrop, and the candidate picker. The instinct to "clean up the orphaned CSS/helpers/routes the dead feature left behind" is exactly how a pure-subtraction PR turns into a regression: the artifacts weren't orphaned, they were shared, and the dead feature was merely one of several callers. Same logic spared the `/api/projects/[id]/tune` route + `lib/api/pageTuneOp.ts` (shared with 🎛 Tune) and the whole multi-version candidate picker (reached independently via `onRender` with n>1). Rule: for each file/symbol/class the removed feature used, grep for OTHER referents BEFORE deleting; a zero-diff on a file you expected to shrink is a legitimate, reportable outcome — record it in the PR body as a deliberate finding ("no orphaned CSS exists to clean up") rather than hunting for something to delete to make the cleanup feel complete. <!-- Source: post-mortem, plush-press #312, 2026-07-16 -->

- For interface extractions under 10 lines that match established project conventions, include them in the original PR; reserve "scope creep" for behavioral additions.
- Never bundle tooling setup (lint configs, auto-fixes) with feature PRs; create a separate tooling PR.
- When identical logic exists in 2+ files and is under ~30 lines, extract to a shared utility instead of adding "keep-in-sync" comments.
- When a tangential automation idea surfaces during a focused PR, defer it to a separate PR.
- **Ship the `.gitignore` guard for a secrets directory BEFORE the first key exists, as its own config micro-PR.** The ignore rule is the only gate that works by construction (no reliance on review catching a staged key); landing it pre-creation means there is never a window where `git add .` could stage credentials. Verify with `git check-ignore <path>` on the branch as the PR's test. <!-- Source: post-mortem, plush-press #13, 2026-06-10 -->
- **For a derived-signal feature (a new score/column feeding new logic), split into a data PR then a logic PR.** baby-name-picker #169/#170 cleanly split a phonetic-texture taste signal: PR A (#169) shipped ONLY the build-time scorer + the `sound_softness` column for all 1311 names and touched zero classifier code; PR B (#170) wired that column into the taste classifier. Benefits proven here: (a) each PR stayed small and single-concept (A: +1929 data/script LOC mostly generated; B: +272 LOC of actual logic), (b) A's correctness (band separation of scores) was reviewable in isolation without classifier noise, (c) B could calibrate its thresholds against A's ALREADY-SHIPPED real distribution rather than a hypothetical one, (d) zero post-merge fixes on either. The split test: if the new logic's thresholds/behavior depend on the empirical distribution of the new data, ship the data first so the logic PR calibrates against reality. Each PR must still independently pass CI (A added its column + tests; B added classifier tests). <!-- Source: post-mortem, baby-name-picker #169 + #170, 2026-06-02 -->
- **Calibrate heuristic thresholds against the REAL shipped distribution, not a guessed value.** When a feature gates on a numeric threshold for a heuristic signal (a "softness floor," a "confidence floor," a similarity cutoff), compute the threshold from the actual catalog/dataset percentiles rather than picking a round number. baby-name-picker #170 set `SOFT_FLOOR=0.75` deliberately between the catalog's median (0.66) and p75 (0.82) and `SOFT_DELTA_FLOOR=0.12` to require a genuine preference rather than a mild lean — both named, tunable constants justified by the real distribution shipped in #169. A guessed threshold either over-fires (catches noise) or under-fires (never triggers); a percentile-anchored one is defensible and re-tunable. This is only possible when the data exists first (see the data-then-logic split above). <!-- Source: post-mortem, baby-name-picker #170, 2026-06-02 -->
- **A pure copy-rename can ride along in a feature PR when it is the same vocabulary the feature touches; a copy-rename of an UNRELATED surface should be its own PR.** #148 bundled three changes — dual-pronunciation display (feature), 22 pronunciation data corrections (data), and the per-name tag rename EUPHONY→INVENTED (copy). ## Adversarial Review Gaps

### Critic Blind Spots
- **Test-discovery colocation bias.** Critic agents default to assuming Jest/Vitest colocated `*.test.ts` next to source files and report "no tests exist" when projects use the alternative `src/__tests__/<area>/foo.test.ts` mirror-tree, `tests/` directory, language-specific conventions (Go `*_test.go`, Rust `tests/`, pytest `tests/` dir), or any non-colocated layout. Before claiming any test gap, the critic must read the project's test-runner config (`vitest.config.*`, `jest.config.*`, `pyproject.toml`, etc.) AND `find . -type d \( -name __tests__ -o -name tests -o -name test -o -name spec \) -not -path '*/node_modules/*'` to enumerate the actual test layout. The orchestrator-protocol "Critic's Fresh Context" section now mandates this. <!-- Source: post-mortem, family-digest #4, 2026-04-22 -->
- **A fix for a bug class frequently REINTRODUCES the same bug class in its own new code — the critic must re-run the original failure mode against the fix, and author self-review reliably misses it.** second-brain #683 fixed an LLM weekday→date off-by-one by replacing model arithmetic with a deterministic `buildCalendarDateReference` date table. The first implementation of that helper built each date by reformatting a UTC-noon instant back through `Intl.DateTimeFormat(timezone)` — which shifts the date +1 in far-east zones (UTC+13 Tongatapu, UTC+14 Kiritimati), i.e. it re-created an off-by-one date bug while fixing an off-by-one date bug. The fresh-context critic caught TWO execution-verified instances (the table itself AND the all-day inclusive-end display in `formatWhenFromEvent`) plus a missed sibling (the calendar-QUERY prompt still had the single-line nowStr); all fixed in a second pass. The author's own review had not caught them. Two reusable rules: (1) **when a fix replaces a faulty computation, the critic must execute the NEW computation against the exact inputs that triggered the original bug AND its known adversarial extremes** — for date/time math that means a far-east-zone (UTC+13/+14) and a DST-boundary case, run for real, not reasoned about; (2) **author self-review systematically under-tests the fix's own new code against the failure mode being fixed** (tunnel vision on "I removed the old broken path"), so this re-verification is precisely the fresh-context critic's job, not something to fold back into the implementer. Generalizes beyond timezones: any fix that swaps one algorithm for another (parsing, rounding, pagination, dedup) should have the critic replay the original repro against the replacement. <!-- Source: post-mortem, second-brain #683, 2026-06-22 -->
- **"LLM doing computation it shouldn't" is now a confirmed THREE-STRIKE recurring root cause in second-brain — promote it to a pre-implementation premise check on any LLM-touching feature.** The same anti-pattern (delegating deterministic arithmetic to the model instead of having the model extract parameters + narrate while code does the math) has produced three separate user-visible calendar bugs in one week, each surfaced by manual Telegram testing and NOT by review: #681 (LLM weekday→date arithmetic, off-by-one), #683 (the deterministic fix REINTRODUCED the same off-by-one class in far-east zones), and #685 (LLM doing free/busy interval-subtraction — reported a day "fully booked 8am–8pm" when the only event ended at 7pm, hiding a free 7–8pm slot). ## Iteration Velocity

- Full local review loop achieves 0% fix-up ratio for well-planned PRs under 600 LOC.
- **User-perceived-latency feedback is a process smell, not a feature request.** When the user reports "this feels slow" on a write path (vote, favorite, comment) and the fix is a one-line optimistic-update swap, the root cause is that the write-path hook (`useAtelierData`, `useInspoFavorites`, `useInspoNotes`) did not default to optimistic updates. PR #83: 1 fix commit ("optimistic vote/favorite updates") could have been preempted if the hook factory enforced optimistic-by-default with an explicit `pessimistic: true` opt-out. Treat repeated "feels slow" feedback across multiple write paths as a hook-factory design gap, not per-call optimization. <!-- Source: post-mortem, remodel-hq #83, 2026-05-15 -->
- **Surface-misidentification during iteration is an avoidable rework category.** When user feedback references a feature area ("the lightbox") but actually concerns a sibling surface (the card grid), each misidentified round costs ~1 implementer cycle. Mitigations: (1) plan-time surface table (see Planning Discipline), (2) ask the user "which screen -- card grid or lightbox?" before dispatching the implementer, (3) capture a screenshot in the feedback channel. PR #83 lost 2 implementer rounds to this. <!-- Source: post-mortem, remodel-hq #83, 2026-05-15 -->
- 0% fix-up ratio can mask ignored CHANGES_REQUESTED findings; always verify they were addressed.
- Copy-and-adapt is higher-risk for review quality than greenfield.
- Marker/infrastructure commits inflate fix-up ratio; exclude from calculations.
- Net-deletion refactor PRs have lowest review friction; custom UI with portals has highest.
- Scaffolding PRs benefit from sequential additive commits for high shift-left rates.
- Copilot "suppressed low-confidence" findings can be 100% legitimate; always read them.
- Fix commits touching React state cause cascading reviews; budget extra time.
- Test LOC should be factored into PR sizing at ~1.5x feature LOC.
- CSS theme PRs need automated WCAG contrast checks, not manual "verified" claims.

If it still produces nothing, record the failure + substitution in the PR body's `Steps skipped:` line (per the tracked-skip rule) — #23 lost ~50 minutes to an unbounded wait that a `timeout` wrapper would have capped.** <!-- Source: post-mortem, plush-press #23, 2026-06-10 -->

## Multi-PR Feature Coordination

- Grep sibling packages for endpoint paths during internal review; unit tests won't catch contract mismatches.
- **In a multi-PR feature whose later PRs depend on a NEW persisted field surviving a read-modify-write round trip, ship that persistence contract FIRST as a byte-identical, no-op PR with a mandatory round-trip regression test — before any consumer exists.** second-brain #751 (PR-A of the lean smart-scheduler #749) added two optional `TodoAnalysis` fields (`actionMode`, `batchKey`) tagged by the LLM + an archetype table, but **nothing in the scheduler reads them** — `buildProposal`/packer/formatter/commit path are untouched, so scheduler output is byte-identical (verified: zero `actionMode`/`batchKey` references in any scheduler file; all pre-existing proposal/refine tests pass unchanged). The load-bearing change is that the refine `coerceAnalysis` re-validates + re-normalizes the fields on the persisted-analysis round-trip with logic IDENTICAL to the main coercion, so the LLM's grouping survives every refine round instead of being silently erased on the first refine — guarded by a mandatory round-trip test (`actionMode:"errand", batchKey:"baby-kids"` survives `Object.fromEntries`→`parseRefinableMetadata`→`coerceAnalysis` verbatim). **Why this ordering wins:** the "silent field-drop on the round trip" failure class (a coercer on the read-back path that doesn't know about a new field strips it) is real and invisible — it only manifests after a downstream consumer relies on the field, by which point the data was already being dropped. Landing the contract as a no-op PR (a) makes the persistence + coercion-symmetry the WHOLE diff so it's the entire review focus, (b) lets the round-trip test fail loudly the instant the symmetry breaks, and (c) de-risks PR-B/C (the grouping consumers) so they can assume the field is present and correct rather than re-litigating persistence. Reusable recipe for any field a later PR will consume across a persist→refine/re-read boundary: ship the schema + BOTH coercion sites (main + round-trip read-back) + a round-trip regression test as PR-A with zero behavioral change, prove byte-identity of the existing pipeline, THEN build consumers on top. The mandatory test is the contract; the no-op scope is what makes the contract reviewable in isolation. **STRENGTHENED — the same recipe works for parameterizing hardcoded PROMPT/STRING language behind a default constant:** plush-press #327 (Art Styles Stage 1) factored soft-watercolor language (7 hardcoded sites) into an optional `StylePromptText` param defaulting to `WATERCOLOR_STYLE_TEXT`, with NO consumer wired (Stage 2 does resolution). Byte-identity proofs: full-output golden fixtures per builder, default-equals-explicit-default assertions, POSITIVE custom-style assertions in both branches (so dropping the custom path fails loudly, not just an absence-of-old-language check), an unchanged pre-existing byte-pin test in the consumer component, and executing origin/main's module against the branch across the input matrix. Result: 1 local CodeRabbit cycle (test/doc strengthening only, zero behavior changes), merged in 5 min, 0 post-merge fixes. The CodeRabbit finding worth keeping: an absence assertion ("no 'watercolor' remains") is weaker than a positive assertion ("custom medium + closing line present in both branches") — pin the new path positively. <!-- Source: post-mortem, plush-press #327, 2026-07-19 -->

- **When a PR is superseded by a sibling that shipped a LEANER version of the same feature, diff the two for a dropped security/hardening detail before closing the loser — extract just that delta into its own PR.** second-brain #665 (scope `updateBotResponseMetadata` to the authenticated user) was superseded by sibling #666, which shipped the calendar-write feature #665 was attached to — but #666 shipped the feature WITHOUT #665's `AND user_id = $3` user-scoping. "Superseded" was true for the feature and false for the hardening: closing #665 as a dup would have silently discarded a real cross-user-write fix. The salvage was to extract ONLY the dropped delta — the `userId` param threaded through the shared commit/refine fns to all 3 call sites + the WHERE-clause scope + a cross-user isolation test — into a focused follow-up PR (#782), keeping it independently reviewable rather than re-opening the whole superseded branch. Reusable rule: when closing PR-A as superseded by PR-B, don't just confirm B ships the FEATURE — diff A→B for any defensive/validation/scoping/test detail A carried that B dropped (a leaner reimplementation often sheds exactly the "boring" hardening), and if found, ship that delta alone. The general failure class: a feature can be re-shipped intact while a security invariant attached to it is quietly lost in the re-write, and a supersede-and-close that only checks feature parity won't see it. Pairs with the stale-PR triage rule (verify against main before closing) and the no-op-hardening-PR shape above (a single user-scoping delta is exactly the kind of small, totally-reviewable security PR that benefits from isolation). <!-- Source: post-mortem, second-brain #665→#666/#782, 2026-06-27 -->

## Data Quality / Audits

- **Brand-rename safety when the brand string collides with domain data: carve out the data surfaces in the brief and require grep-proof before push.** baby-name-picker #195 renamed the app Sona→Ria, but "Sona" is also a real Hindi baby name living in the catalog (`scripts/seed-data.sql`, the rebuilt binary `assets/seed.db`, and `seed-additions.test.ts`). A blind find/replace would have silently corrupted product data on a "data is the product" app. The change shipped clean because the brief **explicitly enumerated the keep-vs-change boundary** (rename every *brand* surface; preserve the *catalog* name) and the critic verified it with two greps: `grep "Sona"` must still hit the seed/test data (proof of preservation) AND must NOT hit any active brand surface (proof of completeness). **Reusable recipe for any rename where the token also appears as domain data:** (1) list the data surfaces that must NOT change in the spawn brief; (2) require a paired grep at review — one asserting the data token survives, one asserting it's gone from brand surfaces; (3) prefer routing brand strings through a single source (here `web/lib/brand.ts` `BRAND_NAME`) so the brand surface is a small, greppable set distinct from the data. This is the same keep/change-boundary test as the #148 copy-rename ride-along, sharpened for the case where the cost of getting the boundary wrong is corrupted user-facing data, not just stale comments. <!-- Source: post-mortem, baby-name-picker #195, 2026-06-16 -->

- **Multi-agent, web-grounded, adversarially-verified audit is the reusable pattern for data-quality at scale — and the antidote to the "audit on a flattened view shipped wrong data" failure (#87).** baby-name-picker's native-pronunciation initiative built a harness that researched ~465 names and is the model to copy whenever a large bundled dataset needs correcting: (1) **source-grounded, never model-opinion** — every proposed change is backed by an external authority (Wiktionary IPA / Behind the Name / Forvo / Wikipedia); a change with no citable source is NOT made; (2) **adversarial verification per change** — each proposed change goes to an *independent skeptic* agent whose job is to refute it, and only un-refutable changes survive as confirmed corrections; (3) **conservative `uncertain` flag on source disagreement** — where authorities conflict, the harness does NOT guess, it flags the name and routes it to a human; (4) **human-in-the-loop gate** — an interactive review tool (approve/reject/keep/change + JSON export) ratifies decisions before anything touches the seed source; (5) **critic verifies the SHIPPED structured artifact, not a flattened view** — "exactly N rows changed in column X (matching the N ids), every other column byte-identical, row count unchanged." This is the structural opposite of #87, which trusted a derived view + model judgment and shipped wrong etymology data silently. <!-- Source: post-mortem, baby-name-picker native-pronunciation initiative (#92/#95/#98/#110/#111/#113), 2026-05-29 -->
- **A standing "merge it" / pre-authorization authorizes the MECHANISM, not any specific change the mechanism emits — automated applies must be checked against known prior human decisions before applying.** In the pronunciation sweep the user pre-authorized "merge batch 4 when done"; batch 4's audit mechanically proposed reverting **Esha `EE-shah` → `AY-shah`** — re-introducing the *exact* user-reported bug that PR #92 had fixed earlier the same day. The audit wasn't wrong by its own rules; it had no memory of the human decision. Lesson: **even verified, source-grounded, human-pre-approved automated changes must diff against the set of recorded prior decisions and hard-fail on a contradiction.** Pre-authorization must be scoped ("apply the batch EXCEPT where it contradicts a recorded decision"). Don't let the safety net depend on the same agent happening to hold the prior session in context. Concrete fix: maintain a machine-readable **decision ledger** (id + value + do-not-revert + PR ref); any apply step diffs proposed changes against it and blocks on conflict. The id-based regression test that guarded Esha is the first ledger row. Generalizes to ANY pre-authorized automated-apply pipeline (data sweeps, codemods, dependency bumps). <!-- Source: post-mortem, baby-name-picker native-pronunciation initiative (#111 vs #92), 2026-05-29 -->

## PR Sizing

## Process Rule Enforcement

- **When a critic commits a post-PASS fix, the adversarial-review marker must be refreshed for the NEW head before push.** The push hook (`require-adversarial-review.sh`) keys the marker to `md5(worktree-path)` and verifies it matches `HEAD`. If the critic returns PASS, then commits its own one-line fix on top, `HEAD` advances past the reviewed commit and the marker no longer matches — the hook correctly blocks the push. In baby-name-picker #195 the critic's footer-copyright fix (`© Ria` → `© Keya LLC`) landed after its PASS, stranding the marker. Resolution: the orchestrator self-eyeballed the trivial one-line delta (the "self-eyeball" tier of the Critic Round Tiers) and re-wrote the marker keyed to the new HEAD. **Reusable fix: make the critic write/refresh the review marker as the LAST step of any fix it commits, not at PASS time — so the marker always tracks the actual reviewed head.** Until that's automated, the orchestrator must re-issue the marker after any post-PASS critic commit. **RECURRED in baby-name-picker #197 (2026-06-17): the critic's contained fix (filter dominance-asserting tells out of the open-ended Free Spirit read + 2 regression tests) was committed AFTER its PASS, again stranding the marker; the orchestrator self-eyeballed the contained delta and re-wrote the marker. Two consecutive baby-name-picker PRs (#195, #197) now confirm this is structural, not incidental — the prose "re-issue manually" mitigation is being followed but the root cause (critic writes the marker at PASS time, then commits on top) keeps recurring. Per the line-221 escalation rule, prioritize the automated fix: have the critic refresh the marker as the FINAL action of any post-PASS commit.** **NEW TRIGGER — a MERGE-TIME MECHANICAL REBASE strands the marker the same way (second-brain #823, 2026-06-27): the marker root cause is "HEAD advanced past the reviewed commit," and a critic post-PASS fix is only ONE way that happens. Here the branch was fully gate-PASS'd (critic APPROVE → its one should-fix UUID-guard applied → adversarial gate green → marker stamped), and THEN, at merge time, a concurrent session merged an unrelated completed-todos feature that touched the HOT shared `hooks.ts` imports — forcing a rebase onto current `origin/main`. The conflict was a clean import-UNION (keep BOTH sides' new imports: `fetchCompletedTodayTodos` from the concurrent feature + `dismissRelatedEntry` from this PR), but the rebase rewrote this branch's HEAD SHA, so the stamped marker no longer matched and the push hook correctly blocked. Resolution = the SAME shape as the post-PASS-fix and the docs-amend re-stamp precedents: re-run the FULL gate stack from the worktree to prove the rebased tree is still green (lint clean, shared+server tsc clean, web build, server 113 test-files / web 23 — the test COUNTS confirm the rebased tree, per the line-184 wrong-tree check), then re-stamp the marker for the NEW post-rebase HEAD and force-push-with-lease. The discriminator for "is a bare re-stamp safe?" is whether the head moved by a MECHANICAL operation (a clean import-union conflict resolution, a docs amend, a trivial critic one-liner) on top of an already-certified commit — if the logical content the critic certified is unchanged and the new delta is mechanically verifiable, re-stamp after a green re-gate; if the rebase pulled in semantic changes, the prior certification is stale and a fresh review is owed (line-36 stale-base + line-300 rebase-after-squash). Reinforces: re-stamp-keyed-by-HEAD (this entry), rebase-a-stale-branch-before-gates (line 36), and the wrong-tree gate-verification tautology (line 184). The automated-fix recommendation stands and now generalizes: whatever advances HEAD after a PASS — a critic commit OR a merge-time rebase — must re-stamp the marker for the new head as its final action.** <!-- Source: post-mortem, baby-name-picker #195, 2026-06-16; recurred #197, 2026-06-17; merge-time-rebase trigger second-brain #823, 2026-06-27 -->

- **Promote prose recommendations to enforceable artifacts after 3 consecutive violations.** When the same prose process rule is violated in 3+ PRs in a row (e.g., missing Local Review / Steps skipped / Perf & Cost annotations across #603, #606, #609), escalate from prose to artifact (PR template, lint rule, hook). Prose alone is insufficient at violation rate >2/window. <!-- Source: post-mortem, second-brain #614, 2026-05-06 -->

- **Before implementing an issue, check for parked-but-unshipped work (existing worktrees, branches, and commits referencing the issue) — reuse a vetted parked commit instead of re-implementing it.** In second-brain #766 the orchestrator was about to implement #703 (worktree-aware adversarial-review hook) and DISCOVERED the fix was already implemented and committed (`9ed7539`) in a parked worktree ~2 days old with no PR. Reusable pre-implementation check, run BEFORE dispatching an implementer for any issue: `git worktree list` (look for a worktree whose branch name matches the issue/feature), `git branch -a | grep -i <slug>`, and `git log --all --oneline --grep '#<issue>'` (and grep commit bodies for the issue number) — if a parked commit exists, verify it against current `main` (rebase/cherry-pick cleanly, re-run the gates) rather than re-writing it. This is the work-discovery analogue of the stale-base checks below: those prevent building on a stale base; this prevents building something that already exists. Caveat: a parked commit is a *claim* of correctness, not a guarantee — re-verify (tests + adversarial gate) on current main before trusting it, exactly as #766 did (test re-run 4/4, deep no-weakening gate review). <!-- Source: post-mortem, second-brain #766, 2026-06-27 -->

- **Before merging OR closing an old open PR, VERIFY its bug against current `main` — "looks superseded" is a hunch, not evidence, and it is wrong most of the time.** In a 4-PR second-brain stale-PR triage batch, 3 of 4 PRs first read as "probably already fixed / superseded by later work" — and 3 of those 4 guesses were WRONG: the bugs were still live on `main` (#627 digest expanded-gap regression, #538 reflection inferring family relationships, #654 native sub-task date input). Only the 4th (#665) was genuinely superseded (its sibling #666 had shipped the feature). Acting on the supersede-hunch would have CLOSED three real, still-reproducing bugs unfixed. What made the triage correct was a `git`/code check against current `main` per PR, not the gut read: for a "superseded" claim, confirm the later PR/commit actually fixed THIS bug on main (grep the fix into the current source); for a "still relevant" claim, reproduce the defect against current source. The cheap, parallelizable form: dispatch one read-only triage agent per stale PR (each answers superseded? / mergeable? / conflicts? against current `main`), then merge/rebase/re-author the still-live ones and close only the proven-superseded. Two consequences flow from this: a still-relevant stale PR whose branch is only lightly behind is REBASED (#654: 67 commits stale, one trivial App.css conflict) or merged clean (#627: CSS-only, 20-day wall-clock); one whose anchor code was refactored out from under it is RE-AUTHORED against current `main`, not rebased (#538→#783: branch 122 commits behind after `response.ts` moved to a `contextPreamble`+JSON-citation structure, so the old anchor lines no longer existed). Decision rule: branch behind but anchors intact → rebase; anchors refactored away → re-author from the issue against current source; bug proven fixed on main → close as superseded with the fixing PR/commit cited. This is the open-PR sibling of the parked-commit rule above (verify a stale *claim of correctness* against current main) — here the stale claim is "this is no longer needed," and it fails the same way: silently, by trusting a summary instead of the tree. <!-- Source: post-mortem, second-brain #627/#538/#654/#665 stale-PR batch (#628/#783/#655/#782), 2026-06-27 -->

## Stale-Base Detection

- **Detect stale base before push, not at critic-time.** When `main` advances during the implementation window, the resulting spurious diff is currently caught only by the critic agent's review pass. Two occurrences in one session (#614 and prior) indicate the manual catch path is leaky. Add a Tier 0 pre-push check: `git fetch && [ "$(git merge-base HEAD origin/main)" = "$(git rev-parse origin/main)" ]`.
- **Parallel features touching the same low-level files will conflict at merge — sequence them or expect a resolution + re-test pass.** #146 (Euphony) and #145 (`spellings_json`) developed in parallel and both edited `src/types/name.ts`, `src/db/queries.ts`, and `src/db/__tests__/queries.test.ts`; #145 merged first, so #146 absorbed a 3-file conflict resolved in its own merge commit (both features coexist, test count rose to 833). The conflict was benign here only because both changes were additive to the same files. When two in-flight branches are known to touch shared schema/type/query files, either land them strictly sequentially (rebase the second after the first merges) or budget for a conflict-resolution + full-suite re-run before merging the second. The pre-push stale-base check above would have surfaced this before the critic pass. <!-- Source: post-mortem, baby-name-picker #146 vs #145, 2026-06-01 --> <!-- Source: post-mortem, second-brain #614, 2026-05-06 -->
- **Catalog/seed PRs are a recurring serial-collision hotspot — serialize them, or expect rebuild+rebase as the standard resolution.** Every PR that adds or edits names in baby-name-picker touches the same fixed set: the rebuilt binary `assets/seed.db`, the source `scripts/seed-data.sql`, the catalog count-constants embedded in test fixtures (`src/db/__tests__/seed-*.test.ts`), and the coverage baseline JSON (`docs/research/seed-coverage-baseline.json`). Because that set is identical for *any* catalog change, two catalog PRs open at once WILL collide — this has now recurred across **#149, #155, and the Option-C/#163 stale-base note** (#155 sat open ~15h while #160-162 + #166/Anavi advanced main, forcing a merge-up + seed.db rebuild + id renumber 1320-1322 before it could land; #163 likewise needed a merge-up off a base stale behind #161). The collision is structural, not incidental: a generated SQLite binary cannot be hand-merged, and the count-constants must be recomputed against the *final* catalog size. **Reusable mitigations, in priority order:** (1) **Serialize catalog PRs** — treat the catalog as a single-writer resource; open the next catalog PR only after the prior one merges, so each branches off a current main and never collides. (2) **If parallel is unavoidable, merge catalog PRs promptly** — the conflict probability scales with how long the branch sits open; #155's 15h open window is exactly when 3 sibling catalog PRs landed. (3) **Standard resolution recipe when a collision happens:** merge-up `origin/main` → take main's side for the generated artifacts (`assets/seed.db`, never hand-merge the binary) → re-run the deterministic build script → renumber the new rows' ids to follow main's now-higher max id → recompute every count-constant → re-run tsc/lint/jest. This is the same generated-artifact protocol as the rebase entry above (take-theirs-then-rebuild for `.db`/`.sql`), specialized to the catalog. The orchestrator should run the pre-dispatch stale-base check (`git log HEAD..origin/main -- assets/seed.db scripts/seed-data.sql`) before starting ANY catalog implementer, and explicitly sequence catalog work in the task queue. **Recurred with a new dimension in #192/#193 (2026-06-11): two catalog branches developed in PARALLEL collided not just on the generated artifacts but on the id ALLOCATION SPACE itself (both started at id 1425), forcing a renumber + amend + one `reset --hard` reflog recovery. Resolution followed the standard recipe (disjoint ranges 1425-1504 / 1505-1547, second-merger rebased with union merge + counts recomputed + orchestrator independently re-verified the rebuilt DB before merge — clean, ~4 min conflict-to-merge). When parallel catalog branches are unavoidable, reserve disjoint id ranges in each implementer's SPAWN BRIEF (see orchestrator-protocol Communication Flow #8) — mid-flight range reassignments race in-flight commits.** <!-- Source: post-mortem, baby-name-picker #155 (+ recurrence #149, #163), 2026-06-02; strengthened #192/#193, 2026-06-11 -->
- **Local-ahead-of-remote is the mirror of stale-base — verify the pushed head equals the local tip before merging.** A silently failed push + squash-merge orphans commits: plush-press #12's second commit existed locally but never reached GitHub, the squash-merge shipped the stale head, and the content had to be recovered by cherry-pick in a focused restore PR (#14). "Push command exited" is unverified until the remote SHA is confirmed. Pre-merge check: `git rev-parse <branch>` must equal `gh pr view N --json headRefOid` (or `git ls-remote origin refs/heads/<branch>`). <!-- Source: post-mortem, plush-press #14, 2026-06-10 -->
- **Run CodeRabbit (`coderabbit review --base main`) against an UP-TO-DATE base, or ~90% of the findings are noise about already-merged code.** In second-brain #831 the CLI was invoked with `--base main` while the LOCAL `main` was 10 commits behind `origin/main`, so the review surface was `LOCAL-main..HEAD` (the feature diff PLUS those 10 already-merged commits). Result: ~21 of 23 raw findings were about code that had already landed on `origin/main` — pure noise — and only 2 were in-scope to the actual PR diff (both legit and fixed: keyword filter narrowing availability/agenda fetches; generic planner keywords not validated server-side). The noise both buries real findings and wastes the operator's triage budget. Fix protocol BEFORE running 4b: `git fetch origin && git merge-base --is-ancestor origin/main main` (or just `git fetch && git rev-parse origin/main` vs `git rev-parse main`); if local `main` is behind, fast-forward it (`git fetch origin main:main`) or point CodeRabbit at the remote tip directly (`coderabbit review --plain -t all --base origin/main`) so the diff equals the true PR surface. This is the review-tool analogue of the stale-base push check above — the pre-push stale-base guard catches a stale *branch*; this catches a stale *review base*, which silently inflates 4b noise rather than failing loudly. When recording metrics, count only the in-scope/actionable findings (here 2), not the raw total (23). **REINFORCED with a triage discipline in second-brain #841 (2026-07-01): when a stale-base (or otherwise mixed-surface) CodeRabbit run seeds a bug batch, CLASSIFY EACH FINDING BY PROVENANCE into three buckets before fixing anything — (1) real bugs on current `main` (verify against `origin/main`; these become the PR), (2) FALSE POSITIVES that don't reproduce against current source (drop with evidence, do NOT "fix" — #841 correctly discarded a `fetchRelatedEntries` response-envelope finding), and (3) findings about ANOTHER feature's IN-FLIGHT code (route to the owning branch/issue, don't drag into this PR — #841 filed the todo-scheduling correctness findings as OPEN issue #842 against `feat/schedule-todos-propose` rather than bundling them into a 40-LOC frontend fix). Acting on the raw list would either ship a non-bug or blow scope. #841 actioned only bucket 1 (four verified web bugs, #839), shipped clean, 0 escapes. Provenance classification is the discovery-run analogue of the metrics rule above: there you count only in-scope findings; here you FIX only in-scope findings.** <!-- Source: post-mortem, second-brain #831, 2026-06-30; reinforced #841, 2026-07-01 -->
- **A worktree whose `node_modules` is SYMLINKED to the root repo's resolves workspace packages against the MAIN CHECKOUT's source — which is STALE if main sits on a divergent branch, yielding phantom local-tsc errors CI never sees.** Distinct from the gitignored-`dist/` trap above (that's stale *within* one checkout): here the symlink makes the worktree's own copy of an internal workspace package (e.g. `@second-brain/shared`) physically resolve through `node_modules/@scope/pkg` → the ROOT checkout's `packages/shared`, not the worktree's. So when the main checkout is parked on an unrelated feature/spike branch (second-brain #726: `spike/todo-schedule-probe`) that lacks a type the worktree's *own* `packages/shared` already has, the worktree's server `tsc` reports spurious "property/type does not exist" errors against the wrong (root-checkout) sources. These are NOT real bugs and do NOT occur in CI, which does a fresh `npm ci` per checkout and resolves the package locally. Diagnosis: when a worktree tsc fails ONLY on types that the worktree's own `packages/<pkg>/src` clearly defines, check `ls -l <worktree>/node_modules/@scope/<pkg>` — if it's a symlink pointing outside the worktree, the errors are a resolution artifact of the root checkout's branch, not the diff. Don't "fix" them; either point the main checkout back at main, or build/install the worktree's deps in isolation. Pairs with the global "verify a local-gate failure against CI reality" rule (line 24) — phantom monorepo tsc errors have (at least) two independent causes now: stale `dist/`, and a cross-checkout `node_modules` symlink. <!-- Source: post-mortem, second-brain #726, 2026-06-24 -->

## Review Discipline

- **An implementer that CONTRADICTS the orchestrator's spawn brief on a specific code citation is doing its job — the brief's line numbers are a hypothesis, and the implementer is the one holding the file.** plush-press #312: the orchestrator's brief cited `SceneCanvas.tsx:2293` as "the render gate" for the shared `tuneBusy`; the implementer read the file, found 2293 is the **prop gating whether Tune can OPEN**, identified the actual gate as line **643** (`const busy = renderBusy || tuneBusy || savingBackdrop`), pinned its replacement test to 643, and **said so in its report** rather than silently following the brief or silently fixing it. Verified post-merge: line 643 on `origin/main` is exactly that composition. Had it deferred to the brief, the replacement test would have pinned the wrong seam and the coverage gap the test existed to close would have stayed open while LOOKING closed — the worst outcome, since a green test on the wrong line is more dangerous than no test. Two rules: (1) **spawn briefs should cite code as "I believe X is at line N — verify"**, never as fact, and the orchestrator should expect and welcome correction; (2) **implementer briefs must instruct: if the brief's citation disagrees with the file, the FILE wins — fix it and report the discrepancy explicitly.** This is the downstream sibling of the "verify a diagnosing agent's root-cause claim against `origin/main`" rule (Planning Discipline) and the "verify a critic's cited finding against the diff" rule below — same family (a claim about code must be checked against the code), new direction: here the unreliable citation flows DOWN from the orchestrator to the implementer, rather than up from a subagent. An orchestrator's brief gets no more epistemic credit than a critic's finding. <!-- Source: post-mortem, plush-press #312, 2026-07-16 -->

- **A data-enrichment critic must enforce REJECTION PRECEDENTS, not just per-item accuracy — "is this addition consistent with what we already rejected?" is a distinct check.** In #176 the surface pass proposed Otto+Finnish; it's individually defensible (Otto IS a popular Finnish name). - **Before implementing data enrichments, RECONCILE the proposed additions against the AUTHORITATIVE current DB state — not the surface/verify agent's assumed state — to catch same-root duplicates the upstream agents couldn't see.** In baby-name-picker #178 (the two-origin→third-origin completeness pass, the repeatable sibling of #176), the surface and verification agents were given each name's "current origins" as context, but those strings were lossy/approximate for a few names. - **A parallel-build agent that dies on a transient rate-limit is recoverable from its on-disk WIP — don't restart from zero.** During the #33/#34 parallel build, one implementer agent died mid-task on a transient API rate-limit. Rather than re-running the whole task (wasting work already on disk and risking divergence from the sibling agent's assumptions), the orchestrator recovered from the dead agent's partial working-tree state and finished forward. Both PRs landed clean (0 post-merge fixes). Rule: when a backgrounded/parallel agent dies on a transient failure (rate-limit, network, OOM), first inspect its worktree — `git -C <worktree> status` + diff — and resume from the WIP if it's coherent; only restart from scratch if the partial state is inconsistent or unidentifiable. Transient infra deaths are not logic failures; the work product is usually salvageable. **EXTENDED to the SILENT-STALL (not death) case + WIP-COMMIT-AS-HANDOFF, second-brain #693 (2026-06-23): an implementer doesn't have to die to need recovery — it can go DORMANT. #693's implementer committed partial WIP, then went idle across multiple no-progress cycles (hours) without erroring or reporting done — a liveness failure, not a crash. The finished PR landed clean (3 CodeRabbit rounds caught 2 security + 6 injection issues pre-merge; 0 post-merge fixes), so the handoff cost nothing in quality.
